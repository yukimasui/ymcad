## ADR-0001: IME 検証結果 (Phase 0)

- **状態**: 確定 — **合格**。egui / eframe を採用し Phase 1 へ進む。
- **日付**: 2026-08-11

### 背景

ymcad は AutoCAD ライクなコマンドラインを持つ。テキストエンティティ自体は非スコープだが、コマンド入力欄とレイヤ名で日本語入力を受ける可能性がある。`egui` の IME サポートが Ubuntu で成立しないなら GUI の技術選定そのものを見直す必要があるため、実装に先立って検証する。

### 検証環境

| 項目 | 値 |
|---|---|
| OS | Ubuntu 24.04.4 LTS |
| セッション | Wayland (`XDG_SESSION_TYPE=wayland`)、`DISPLAY=:0` あり (XWayland 利用可) |
| IME | ibus (`QT_IM_MODULE=ibus`, `XMODIFIERS=@im=ibus`, `GTK_IM_MODULE` は未設定) |
| toolchain | rustc / cargo 1.96.0 |
| GUI | eframe / egui 0.36.1、winit 0.30.13 |

`GTK_IM_MODULE` が未設定でも問題ない。winit は IME に GTK を経由しない。

### ソース調査で確定した事実

egui 0.36.1 / egui-winit 0.36.1 / winit 0.30.13 のソースを直接確認した結果:

1. **アプリ側の IME API 呼び出しは不要。**
   `egui-winit-0.36.1/src/lib.rs:1152` が `window.set_ime_allowed()` を、同 `:1177` が
   `window.set_ime_cursor_area()` を自動で呼ぶ。トリガーは `PlatformOutput::ime` で、これは
   フォーカスを持つ `TextEdit` 自身が毎フレーム書き込む。`NativeOptions` の opt-in も環境変数も不要。

2. **`ImeEvent::Enabled` / `Disabled` は届かない。**
   egui 0.36 で両者は `#[deprecated = "No longer used by egui"]`
   (`egui-0.36.1/src/data/input/ime_event.rs:8,35`)。egui-winit は winit の該当イベントを
   意図的に捨てている（winit#2498「X11 と Wayland で意味が異なる」ため）。
   生きているのは `Preedit` / `Commit` / `DeleteSurrounding` の 3 つ。

3. **候補ウィンドウは `IMEOutput::rect`（ウィジェット全体）にアンカーされる。**
   `cursor_rect`（キャレット位置）も計算されるが egui-winit は使っていない。
   結果として候補ウィンドウは「キャレット直下」ではなく「入力欄の左端」に出る。
   横長のコマンドライン UI では軽微な違和感になりうるが、機能上の欠陥ではない。

4. **未確定文字列はアプリの `&mut String` に直接書き込まれる。**
   `TextEdit` は `ImeEvent::Preedit` を受けて `insert_text_at` でバッファへ挿入し、
   `Commit` 時に `clear_preedit_text` してから確定文字列を入れる。
   → **変換中にコマンドラインのバッファをパースしてはいけない。** Phase 3 の設計制約になる
   （[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3) 参照）。

5. **`WINIT_UNIX_BACKEND` は winit 0.30 で廃止済み。**
   バックエンド選択は `WAYLAND_DISPLAY`／`WAYLAND_SOCKET` が非空なら Wayland、
   でなければ `DISPLAY` を見て X11。X11 で試すには `WAYLAND_DISPLAY= cargo run` とする。
   なお `set_ime_cursor_area` は **X11 では位置のみ有効でサイズが無視される**
   (winit 0.30.13 のドキュメント記載)。Wayland は `zwp_text_input_v3::set_cursor_rectangle`
   で完全に実装されており、この点では **Wayland のほうが X11 より対応が良い**。

6. **既知の ibus + Wayland 不具合は修正済み。**
   egui#7485（ibus + Wayland で 1 文字しか入力できない）は 2026-04-06 に close 済みで、
   修正は egui 0.35 に入っている。egui 0.36.1 時点で ibus + Wayland の未解決 issue は無い。
   未解決なのは fcitx5 系（egui#7975, #2529）で、本環境の構成には該当しない。

7. **egui の同梱フォントは CJK グリフを持たない。**
   これを放置すると日本語がすべて豆腐 (□) になり、「IME が壊れている」という誤判定を招く。
   `/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc` のフェイス index 0
   (`Noto Sans CJK JP`、`fc-query` で確認) を明示的に読み込む必要がある。
   epaint 0.36 は skrifa 経由で `.ttc` の face index 指定に対応している
   (`epaint-0.36.1/src/text/fonts.rs:162`)。

   → **Phase 1 の `cad-app` にもこのフォント読み込みが必須**。スパイクの
   `spikes/ime-check/src/jp_font.rs` をそのまま移植する。

### 手動検証の結果

`spikes/ime-check` をユーザーが起動し、中央の入力欄①と下部の入力欄②（本体のコマンドラインと同じ位置）の両方で `nihongo` → 変換 → 確定を実施した。

| # | 確認項目 | Wayland (ibus + mozc) | 備考 |
|---|---|---|---|
| 1 | 変換候補ウィンドウが表示されるか | ✅ | mozc の候補ポップアップが出る |
| 2 | 候補ウィンドウがカーソル位置に追従するか | ✅ | 入力欄①と②で表示位置が変わることを確認 |
| 3 | 未確定文字列がインライン表示されるか | ✅ | 入力欄の**中に下線付き**で表示された |
| 4 | 確定文字列が正しくバッファに入るか | ✅ | ①②の両方で `Commit` を受信、文字化け・欠落なし |
| 5 | IME 有効化 API の明示呼び出しが必要か | ✅ **不要** | 入力欄クリックで【項目5】が緑化、外すと復帰。アプリ側は IME API を一切呼んでいない |

日本語は豆腐にならず正しく描画された（Noto Sans CJK JP の明示読み込みによる）。

X11 (`WAYLAND_DISPLAY= cargo run`) での IME 比較は未実施。Wayland ネイティブが本命であり、そちらが全項目 PASS のため Phase 0 の判断には不要と判断した。

Phase 1 で `cad-app` の X11 起動は確認済み（`WAYLAND_DISPLAY= cargo run --release` でプロセスがエラーなく継続動作）。**ただし X11 での IME 挙動と描画の見た目は未検証。** 必要になった時点で比較する。

### 決定

**egui / eframe 0.36 を採用し、そのまま Phase 1 へ進む。** IME 回避策（X11 バックエンド強制、外部ダイアログ、独自 IME ブリッジ）はいずれも不要。

派生する実装上の決定:

1. **`cad-app` でも日本語フォントの明示読み込みを必須とする。**
   `spikes/ime-check/src/jp_font.rs` をそのまま `cad-app` へ移植する。
2. **IME 系 API はアプリ側から呼ばない。** egui-winit の自動処理に任せる。
   ただしコマンドライン確定時の変換中断だけは `Memory::interrupt_ime()` を使う
   （[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3) 参照）。
3. **候補ウィンドウが入力欄左端にアンカーされる件は仕様として受け入れる。**
   ymcad のコマンドラインは横長のため候補がキャレットから離れて出るが、
   egui 0.36 の実装に由来するもので、回避には egui 本体の改変が要る。実害は軽微。

## ADR-0002: コマンドラインは変換中にパースしない (Phase 3)

- **状態**: 予定（Phase 3 で実装）
- **日付**: 2026-08-11

### 背景

ADR-0001 の調査 4 のとおり、`TextEdit` は未確定文字列をアプリのバッファへ直接書き込む。加えて:

- IME がかな入力モードのとき、`@100,50` は `＠１００，５０` のように全角で入りうる
- 変換中は winit が `KeyboardInput` を送らないため、Enter によるコマンド確定ハンドラが沈黙し、確定用の Enter で予期せず発火する

座標直接入力（`100,50` / `@100,50` / `@100<45`）を扱う ymcad のコマンドラインでは、これが誤入力に直結する。

### 決定

Phase 3 のコマンドライン実装で以下を守る:

1. アプリ状態に `composing: bool` を持つ。`ImeEvent::Preedit { text, .. }` で `text` が非空なら `true`、`Commit` で `false`。
2. **`composing == true` の間はバッファを一切パースしない。**
3. パース前に ASCII 範囲を NFKC 正規化する（`＠` `，` `＜` `０-９` → 半角）。
4. コマンドを確定する Enter は、IME を確定する Enter とは**別の打鍵**であることを要求する。

## ADR-0003: トレランスは「絶対値下限 + 相対誤差」のハイブリッドにする

- **状態**: 確定（ユーザー承認済み）
- **日付**: 2026-08-11

### 背景

指示書は `EPS_LEN = 1e-9` / `EPS_ANGLE = 1e-12` の一元管理を要求している。
一方で「ズーム倍率 1e-6〜1e6 の範囲で座標精度が破綻しないこと」も要求している。

この 2 つは、素直に絶対値比較 `|a - b| <= EPS_LEN` を実装すると両立しない。
座標が 1e6 に達すると f64 の ULP は約 2e-10 になり、`1e-9` はわずか数 ULP しか
許容しなくなる。つまり **事実上の完全一致判定に化けて**、交点判定やスナップが
その領域で成立しなくなる。

### 決定

長さの比較を次のハイブリッドで行う。

```text
|a - b| <= max(EPS_LEN, EPS_REL * max(|a|, |b|))
```

- `EPS_LEN = 1e-9` は **絶対値の下限（フロア）** として維持する。定数名も指示書のまま。
- `EPS_REL = 1e-12` を追加する。座標の絶対値が大きい領域ではこちらが効く。
- 純粋な相対比較にしないのは、原点近傍（`a ≈ b ≈ 0`）で破綻するため。
- 角度は値域が `[0, 2π)` に収まり桁が暴れないので、`EPS_ANGLE` による絶対値比較のまま。

`geom/tolerance.rs` に `eq_len` / `len_tolerance` / `is_zero_len` / `lt_len` / `gt_len` /
`eq_angle` / `wrap_2pi` / `wrap_signed` を置き、**ソース中にトレランスを直書きしない**
規約を CI で検査する。

### 補足（実装時に踏んだ落とし穴）

`eq_angle` は当初 `wrap_signed(a - b).abs() <= EPS_ANGLE` と実装したが、
`wrap_signed` が内部で `± TAU` の加減算を行うため丸め誤差が約 `9e-17` 混入し、
ちょうど境界の値（`eq_angle(0.0, EPS_ANGLE)`）が誤って不一致になった。
差が既に十分小さい場合は正規化を挟まないよう短絡させて解決した。

## ADR-0004: エンティティストアは slotmap ではなく自前のアリーナにする

- **状態**: 確定
- **日付**: 2026-08-11

### 背景

指示書は世代つきアリーナを要求し、自前実装でも `slotmap` でも可としている。

### 決定

**自前実装にする。**

決め手は `slotmap` に **「呼び出し側が指定したキーで再挿入する API」が無い**こと。
`remove(k)` した後に挿入すると必ず別のキーになる。

CAD では `ERASE` → `UNDO` が日常操作である。Undo でエンティティを戻したときに
`EntityId` が変わると、Undo スタックに積まれた他のコマンド（「エンティティ k を移動」
「エンティティ k のレイヤを変更」など）の参照が一斉に壊れる。
`EntityStore::restore(id, entity)` で **元の ID のまま**書き戻せることが必須。

副次的な理由:

- `slotmap` の `iter()` は順序が未定義。こちらはスロット昇順（= 作成順 = 描画順）で
  走査できるため、DXF の出力順やピック順を決定的にできる。
- DXF ハンドルは 16 進文字列で安定している必要がある。`EntityId::index` から
  素直に導出できる。

### スロット割り当ての方針

**スロット番号は文書の生存期間中に再利用しない（単調増加）。**

空いたスロットを使い回すと、まだ Undo スタックに残っているコマンドが参照している
スロットを別のエンティティが占有し、`restore` が失敗しうる。
スロットの回収は Undo 履歴を捨てるとき（新規作成・ファイル読み込み）にのみ行う。
2D 作図のセッションで消費するメモリは無視できる。

## ADR-0005: ビューポート変換は相似変換で保持する

- **状態**: 確定
- **日付**: 2026-08-11

### 決定

アフィン行列ではなく **モデル空間の中心 `center: Point2` + 一様スケール `scale: f64`**
の 3 スカラで保持する。

理由:

- 逆変換が閉じた形で厳密に求まる。行列式の逆数を取らないので極端なズームで破綻しない。
- 画面上で一定に保ちたい量（スナップの拾い半径、線幅、破線ピッチ、円弧の分割精度、
  グリッド間隔）がすべてスカラ `scale` の関数として書ける。行列だと毎フレーム
  スケールを抽出し直すことになり、非直交成分が混ざると崩れる。
- 平行移動をスクリーン空間ではなくモデル空間の点として持つことで、1e6 のような
  大きな値を f64 側に留められる。
- 2D 作図にせん断は不要。将来 UCS の回転を入れるとしても 4 スカラで済む。

### f64 → f32 の縮小をどこで行うか

`model_to_screen` では **「f64 で引き算 → f64 で掛け算 → 最後に一度だけ f32 へ」**
の順を守る。`(p.x - center.x)` の結果は見えている範囲 `rect.width() / scale` で
抑えられるので、f32 に落としても誤差は 1e-4 px 程度で視認できない。

逆に先に f32 化してから引き算すると、`center` が 1e6 のとき有効数字が引き算の前に
7 桁失われ、完全に破綻する。この順序が守られていることを保つため、
`as f32` を `viewport.rs` だけに閉じ込め、CI で検査する。

## ADR-0006: ホイールズームの倍率は乗算で更新する（整数レベル方式は採らない）

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

Phase 1 の申し送りで「`scale` を直接乗算しているため、ズームイン/アウトを繰り返すと
倍率がドリフトするのではないか」という懸念を挙げていた。
回避策として、整数のズームレベル `level: i32` から
`scale = base * STEP^level` を導出する方式が考えられる。

### 実測

`zoom_about` を **20,000 回**（50 段の出入りを 200 往復）適用して倍率の相対誤差を測った。

```
相対誤差 < 1e-9
```

f64 の乗算 1 回あたりの誤差は数 ULP しかなく、この回数では実用上まったく問題にならない。
テストは `crates/cad-app/src/viewport.rs` の `zoom_roundtrip_does_not_drift`。

### 決定

**乗算による更新を維持する。整数ズームレベル方式は採用しない。**

整数レベル方式には副作用がある。`zoom_to_fit` は任意の倍率を設定するため、
その直後のホイール操作でレベルへの丸めが起きて倍率が不連続に跳ぶ。
実測でドリフトが問題にならない以上、この副作用を負う理由がない。

倍率は `MIN_SCALE = 1e-9` 〜 `MAX_SCALE = 1e9` でクランプしている
（指示書の要求範囲 1e-6〜1e6 より広い）。

## ADR-0007: グリッド線の本数に上限を設ける

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

グリッドの刻みはズームに応じて 1/2/5 系列で選ぶため、通常は画面に 70 本前後しか出ない。
しかし刻みの計算が想定外の値を返した場合（極端な倍率、NaN、ゼロ）に
描画ループが事実上停止するリスクがある。

### 決定

グリッド座標の生成を純粋関数 `grid_coords(min, max, step)` に切り出し、
本数を `MAX_GRID_LINES = 2000` で頭打ちにする。
不正な入力（`step <= 0`、NaN、`min > max`）では空を返す。

これにより **グリッド描画のコストがズーム倍率によらず一定**になり、
60fps の維持がズーム操作に対して保証される。

座標は `x += step` の累積加算ではなく毎回 `(first + k) * step` で計算する。
累積加算は誤差が溜まって格子が歪む。

ズーム倍率 1e-6〜1e6 × 原点/±1e6 の全組み合わせで本数が 200 本以下に収まることを
`crates/cad-app/src/render.rs` の `grid_line_count_stays_sane_across_zoom_range` で検証している。

## ADR-0008: 確定前の図形は Document に入れない

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

作図中のラバーバンド（LINE の次の点までの線、CIRCLE の半径追従など）を
どう扱うかには 2 つのやり方がある。

1. 途中の図形をとりあえず `Document` に入れ、確定時に置き換える／中断時に消す
2. `Document` には入れず、描画時にだけ使う派生データとして持つ

### 決定

**2 を採る。** `Tool::preview` がカーソル位置から `Vec<Geometry>` を返し、
`render::draw_preview` がそれを描く。`Document` には一切入らない。

1 を選ぶと次の問題が起きる。

- カーソルが動くたびにコマンドが積まれ、**Undo 履歴が汚れる**。
  「Undo したら線が 1 本消えるのではなくラバーバンドが 1 フレーム戻る」という
  使い物にならない挙動になる
- 「あとで消すから」という理由で `EditCtx` を経由しない変更経路を作りたくなる。
  Phase 1 で型によって封じた不変条件が、ここで崩れる

ラバーバンドは本質的に **UI の表示状態**であって図面の内容ではない。
`cad-app` 側に置くのが正しい。

## ADR-0009: 交差選択は矩形の 4 辺との交点で厳密に判定する

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

交差選択（右→左ドラッグ）は「矩形に少しでも掛かる要素」を選ぶ。
最も安価な実装は境界ボックス同士の重なり判定だが、これは過剰に拾う。

例: 半径 10 の円の左上の角にある小さな矩形は、円の bbox とは重なるが
円周とは交わらない。bbox 判定だと選ばれてしまい、ユーザーの意図と食い違う。

### 決定

2 段で判定する。

1. 図形の bbox が矩形と重ならなければ確実に掛かっていない（安価な足切り）
2. 図形全体が矩形に収まっていれば掛かっている
3. そうでなければ **矩形の 4 辺と実際に交点を持つか**を `geom::intersect` で調べる

対象が線分・円・円弧・ポリラインだけなので、この判定は厳密になる。
窓選択（完全内包）は bbox の包含で厳密に判定できる（これらの図形の bbox は
すべてタイトなため）。

計算量は最悪でも「要素数 × 4 辺」で、Phase 4 で空間インデックスを入れれば
候補を絞れる。

## ADR-0010: スナップのヒステリシスは「吸着点」を基準にする

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

指示書は「一度スナップしたら、カーソルが多少動いても即座に外れないこと
（これが操作感を決めます）」を要求している。

単一の半径で「近ければ吸着」とすると 2 つの問題が起きる。

1. カーソルが境界上にあるとき吸着と解除が毎フレーム入れ替わり、マーカーがちらつく
2. 狙った点に吸い付いた後に少し手が動くと外れるため「掴んだ感じ」がしない

### 決定

取得と解放で別の半径を使う。

- 未吸着のとき: カーソルから **10px** 以内に候補があれば吸着する
- 吸着中のとき: **吸着点から 16px** を超えて離れるまで保持する

**判定の基準をカーソルではなく吸着点にする**のが肝。カーソル基準にすると
吸着した瞬間に基準が動いてしまい、履歴が効かずヒステリシスにならない。

半径は画面上の px で定義し、`Viewport::px_to_model_len` でモデル空間へ換算する。
これによりズーム倍率によらず操作感が一定になる。

## ADR-0011: 空間インデックスは Document ではなく cad-app 側の派生キャッシュに置く

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

10,000 要素でスナップ検出を 16ms 以内に収めるには空間インデックスが要る。
これを `Document` の中に持つか、`cad-app` の派生キャッシュにするかで
保守コストが大きく変わる。

### 決定

**`cad-app` の派生キャッシュに置き、`Document::revision()` をキーに再構築する。**

`Document` の中に持つと、

- **すべてのコマンドがインデックスの更新と、その巻き戻しを実装する必要がある**。
  コマンド 1 つあたりの実装量が倍になり、しかも間違えても気づきにくい
- Undo でインデックスを正しく戻し損ねると、選択やスナップだけが静かに壊れる

派生キャッシュにすれば、`revision` が変わったら丸ごと作り直すだけで済む。
Undo / Redo でも `revision` は進む（Phase 1 でそう設計した）ので、
巻き戻しでも自動的に無効化される。

10,000 要素程度の一括構築はミリ秒オーダーで、毎編集で作り直しても
体感に影響しない。問題になったら差分更新を検討する。

## ADR-0012: レイヤパネルは Document を変更せずコマンドを返す

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

レイヤの色変更・表示切替・リネーム・削除は、作図と同じく Undo できなければならない
（指示書の受け入れ基準「レイヤ操作が Undo で巻き戻る」）。

GUI パネルは「チェックボックスを押したらその場で値を書き換える」形にしたくなるが、
それをやると `LayerTable` への直接の変更経路ができ、Phase 1 で型によって封じた
不変条件が崩れる。

### 決定

**レイヤパネルは `Document` を一切変更しない。**
`LayerPanel::show()` はユーザー操作を `Vec<Box<dyn Command>>` へ翻訳して返すだけで、
適用は呼び出し側が `Document::apply` で行う。

```rust
let commands = self.layer_panel.show(ui, &self.doc, &self.session.selection);
for cmd in commands {
    self.session.apply_external(cmd, &mut self.doc);
}
```

これにより、レイヤ操作も作図と同じ 1 本の経路を通り、Undo/Redo が自動的に効く。
`LayerTable` の変更系メソッドは `pub(crate)` のままで、`cad-app` からは
名前を呼ぶことすらできない状態を保てる。

## ADR-0013: 破線パターンは図面単位ではなく画面 px で定義する

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

線種（`Dashed` / `Center` / `Hidden`）の破線ピッチをどの空間で定義するか。

- 図面単位で定義すると、拡大したとき破線が伸びて実線に見え、
  縮小すると点の集まりに見える
- 画面 px で定義すると、ズーム倍率によらず破線の見え方が一定になる

本プロトタイプでは線種は **画面表示のみ**（指示書の明示的な制約）で、
DXF へは書き出さない。

### 決定

`LineType::dash_pattern_px()` が **画面上の px** で「描く長さ, 空ける長さ, …」を返す。
描画はスクリーン空間で行い、パターンを順に消費しながら線分を分割する。

1 本の線分に描く破線の本数は 2000 で頭打ちにする。極端なズームで
1 本の線が画面を何度も横切っても描画が止まらないようにするため。

`cad-core` は f64 しか持たないためパターンは `&[f64]` で返る。
f64 → f32 の縮小は `viewport.rs` に閉じ込める規約があるので、
そこに `px_to_f32` を用意して唯一の入り口とした。

## ADR-0014: DXF は外部クレートを使わず自前で読み書きする

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

Rust には `dxf` クレートがあり、多数のバージョンとエンティティに対応している。
一方で本プロトタイプが必要とするのは **R12 の 4 種類のエンティティだけ**。

### 決定

**外部クレートを使わず、R12 を自前で読み書きする。**

理由:

- R12 は「グループコード行 + 値行」の繰り返しという単純な行指向フォーマットで、
  必要な範囲なら数百行で書ける
- `dxf` クレートは既定で **新しいバージョンを書き出す**。`header.version` の指定を
  忘れると R2013 が出力され、R12 を期待する読み手が拒否する。この事故は
  静かに起きて気づきにくい
- 何を出力するかを完全に制御できる。R12 に無い `LWPOLYLINE` を誤って書かない、
  `$EXTMIN`/`$EXTMAX` を必ず出す、といった制約を確実に守れる
- `cad-core` の「依存は std のみ」という状態を保てる

読み込み側は寛容にする。理解できないセクションやエンティティは読み飛ばし、
他のプログラムが作ったファイルでも失敗しないようにする。

## ADR-0015: 未保存確認では「保存する」選択肢を必ず用意する

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

指示書は「未保存変更がある状態での終了時に確認ダイアログ」を要求している。
最小限の実装は「破棄しますか？ はい / いいえ」だが、これはユーザーに
**作業を失うか操作を諦めるかの二択**しか与えない。

### 決定

確認ダイアログは **「保存する」/「保存しない」/「キャンセル」** の 3 択にする。

- 「保存する」… 保存してから元の操作（新規 / 開く / 終了）へ進む。
  保存ダイアログがキャンセルされた場合は元の操作も行わない
- 「保存しない」… 変更を捨てて元の操作へ進む
- 「キャンセル」… 何もしない

確認が必要な操作は即座に実行せず `PendingAction` として保留し、
ユーザーが選んでから実行する。ウィンドウの ✕ ボタンについては
`ViewportCommand::CancelClose` で一旦終了を止めてから確認する。

## ADR-0016: コマンド表を `match` からデータに変える

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #1](https://github.com/yukimasui/ymcad/issues/1)

### 背景

コマンドの解決は `crates/cad-app/src/tools/mod.rs` の `create()` / `immediate()` にある
**文字列リテラルの `match` 文**だった。動くが、**コマンドを列挙できない**。

候補表示は「全コマンドを走査して先頭一致を探す」操作なので、`match` のままでは実装できない。

### 決定

`match` をやめて静的な表 `COMMANDS: &[CommandSpec]` にする。
`CommandSpec` は名前・エイリアス・一行説明・実体（ツール生成関数 or 即時コマンド）を持つ。

`create()` / `immediate()` は `lookup()` の薄いラッパとして残す。
**既存の呼び出し側とテストがそのまま通る**ようにして、変更の波及を抑えた。
リファクタが解決結果を変えていないことは、既存の
`aliases_resolve_to_expected_tools` / `canonical_names_resolve` が通ることで担保される。

副次的な効果として、表にしたことで

- 名前とエイリアスの重複を検査するテストが書けるようになった
  （重複すると先に書いた方が勝ち、後のコマンドが起動できなくなる）
- 全コマンドに説明文があることを機械的に確認できるようになった

### 候補のキー操作

- `↑` `↓` … 選択を動かす。**端では未選択へ戻る**（一覧から抜けられるように）
- `Tab` … 選択中（未選択なら先頭）の候補を入力欄へ補完する
- `Enter` / `Space` … **候補が出ていれば必ず候補を実行する**。
  優先順位は「明示的な選択 → 入力と完全一致 → 先頭候補」。
  候補が 1 件も無いときだけ打った文字列をそのまま確定する
  （→ **2026-08-12 に方針を変更。下記「未選択 Enter の扱いを撤回した経緯」を参照**）
- `Esc` … 候補が出ていればまず候補だけを閉じる。いきなりコマンドを中断すると
  打ち間違いのやり直しが面倒になるため

候補の操作キーは **`TextEdit` を描く前に消費する**。あとから処理すると
`TextEdit` にカーソル移動として取られてしまう。
これらは既存の `if self.composing { ... }` ブロックの中にあるので、
**日本語変換中は自動的に無効**になる（ADR-0002）。

### 未選択 Enter の扱いを撤回した経緯（2026-08-12、[Issue #5](https://github.com/yukimasui/ymcad/issues/5)）

当初は **「打った通りに実行される」のが既定**とし、
未選択で `Enter` を押すと候補ではなく入力文字列を確定していた。
候補を使うには `↑` `↓` で明示的に選ぶ必要があった。

**この判断は実際に使うと間違いだった。**
候補が出ている時点で目的のコマンドは先頭にいることがほとんどで、
そこからさらにカーソル操作を要求するのは冗長だった。
`L` と打った時点で `LINE` が先頭に出ているのに `Enter` で実行されないのは、
候補表示を入れた意味を損なう。

**変更後**: 候補が出ていれば必ず候補を実行する。優先順位は

1. `↑` `↓` で明示的に選ばれていればそれ
2. 入力と完全一致する候補があればそれ
3. どちらでもなければ先頭候補

**2 を挟むのが肝。** 候補の並び順は「エイリアス完全一致 → 名前の先頭一致 → …」なので
3 だけでも今は同じ結果になるが、`COMMANDS` の並びを変えた瞬間に壊れる。
完全一致を明示的に優先しておけば並び順に依存しない
（`SAVE` は `SAVEAS` の接頭辞でもあるので、これが効く場面が実際にある）。

**引き換えに「打った文字列と違うコマンドが走る」ことが起きうる**ので、
候補一覧で `Enter` の対象を必ず見せる。行頭の `⏎` と背景の 2 つで示し、
明示選択（濃い背景）と既定選択（薄い背景）を区別する。
`⏎` は背景色とは別の視覚チャンネルなので、テーマや配色に関わらず読み取れる。

この経緯を残しておくのは、**同じ議論を繰り返さないため**。
「打った通りに実行されるべきでは」という考えは筋が通っているが、
実際の打鍵数の前では割に合わなかった。

## ADR-0017: STRETCH の範囲は「選択に使われた交差窓」を蓄積して持つ

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #2](https://github.com/yukimasui/ymcad/issues/2)

### 背景

STRETCH は他の編集コマンドと違い、**選ばれた要素だけでなく「どの範囲で選んだか」**を
必要とする。範囲に入った点だけが動くのがこのコマンドの本質だからである。

しかし `Session::handle_rect_select` は矩形をその場で使い捨てており、
`Selection` には要素の ID しか残らなかった。

### 決定

`Session` に `crossing_rects: Vec<Aabb>` を持ち、
**交差選択のときだけ**矩形を追加する。`ToolCtx` 経由でツールへ渡す。

- **`Vec` にした理由**: AutoCAD は交差窓を複数回重ねて選択範囲を広げられる。
  1 つしか覚えないと 2 回目の窓で 1 回目が消え、意図と違う結果になる
- **窓選択（左→右）は数えない**: 完全内包の選択なので「範囲の内側だけ動かす」意味がない
- **`Shift` での選択解除では追加しない**: 動かす対象を広げてしまうため
- **クリック選択では範囲が空のまま**: このとき STRETCH は丸ごと移動になる。
  これは AutoCAD と同じ挙動で、意図的にそうしている

範囲は `cancel()`（`Esc`）と、選択をやり直すコマンド開始時にクリアする。
前のコマンドの範囲を引きずらないため。

### 円と円弧の扱い

**中心が範囲に入っていれば図形ごと動かし、入っていなければ動かさない。**
半径と角度は変えない。

AutoCAD は円をこの規則で扱う。円弧は本来は端点を引っ張って形状が変わるが、
中心と半径の再計算が必要になり、3 点が同一直線上になる退化ケースの処理も要る。
プロトタイプの範囲としては割に合わないと判断し、円と同じ規則にした
（ユーザーと合意済み）。

円周が範囲を横切っていても中心が外なら動かない点は、読み手が最も疑いそうなので
`geometry_stretched_circle_center_outside_is_unchanged_even_when_circumference_crosses_region`
というテストで明示的に固定してある。

## ADR-0018: クリック判定は `clicked_by()` ではなく「ボタンが離されたか」で行う

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #4](https://github.com/yukimasui/ymcad/issues/4)

### 背景

「マウスが動いている状態でクリックすると点が置けない」という不具合報告があった。

調べると egui が押下〜解放を **クリックと認めるのは次の両方を満たすときだけ**だった。

| 条件 | 既定値 | 場所 |
|---|---|---|
| 押した位置から動いた距離 | **6.0 px** 以内 | `egui::InputOptions::max_click_dist` |
| ボタンを押していた時間 | **0.8 秒** 未満 | `egui::InputOptions::max_click_duration` |

どちらかを外れると `Response::clicked_by()` は `false` になり、egui はドラッグとして扱う。

**時間の条件が盲点だった。** 距離だけの問題だと思い込むと直しきれない。
CAD の作図では狙いを定めてゆっくり押すのが普通で、0.8 秒はすぐ超える。

さらに悪いことに、`handle_pointer` は **点の入力待ち中は矩形ドラッグのブロックごと飛ばす**
作りだったため、クリックと認められなかった解放は **どこでも処理されず黙って捨てられていた**。

選択のクリックも同じ理由で取りこぼしていた。矩形選択には
「`DRAG_THRESHOLD_PX`（4.0px）未満ならクリック扱い」という復帰路があったが、
その先が `clicked_by()` なので結局拾えない。
しかも **4.0 は egui の 6.0 より小さい**ので、この閾値では egui の判定を肩代わりできていなかった。

### 決定

**「キャンバス上で主ボタンが離された」ことを入力の合図にする。**

```rust
let released = response.clicked_by(Primary) || response.drag_stopped_by(Primary);
```

`drag_stopped_by()` は距離超過でも時間超過でも発火するので、両方の原因を一度に塞げる。

- **点の入力待ち中**: 矩形選択に入らない状態なので、離されたら常に点として拾う。
  距離の閾値は設けない（手が動いていても拾えるようにするのが目的）
- **選択時**: 矩形ドラッグのブロックで、ドラッグ量が閾値未満なら
  `clicked_by()` へ流さず**その場でクリックとして処理する**

座標は **ボタンを離した位置**（`interact_pointer_pos()`）を使う。
スナップはその時点のカーソル位置から計算されているので、離した位置なら
**マーカーが出ている点と実際に入る点が一致する**。押した位置を使うとずれる。

### 採らなかった案

`ctx.options_mut` で egui の閾値自体を緩める案は採らない。
ダブルクリック判定にも影響し、時間の条件は別途上げる必要があるため、
副作用の範囲が読みにくい。

### テストできないこと

この判定は `egui::Response` の状態に依存するため単体テストで再現できない。
その旨を `handle_pointer` のドキュメントコメントに書き、変更時は手動確認するよう促している。

## ADR-0019: 変換コマンドは「その場で変換」と「複製を追加」を別コマンドに分ける

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 1）

### 背景

ROTATE / SCALE / MIRROR には AutoCAD 準拠の「元図形を残す」オプションがある
（ROTATE・SCALE は `C`、MIRROR は最後の「元を消しますか？」で `N`）。

1 つのコマンドにフラグを持たせて分岐させることもできる。

### 決定

**`RotateEntities` / `RotateCopyEntities` のように別のコマンド型に分ける。**

理由は **Undo の中身が根本的に違う**こと。

| | execute | undo |
|---|---|---|
| その場で変換 | 既存要素の `Geometry` を書き換える | **控えておいた変換前の `Geometry` を戻す** |
| 複製を追加 | 新しい要素を追加する | **作った要素を削除する** |

1 つの型にまとめると `execute` も `undo` もフラグによる分岐だらけになり、
「全部成功するか、何も変えずに失敗するか」という契約の検証が難しくなる。
既存の `MoveEntities`（前者）と `CopyEntities`（後者）が既に別型なので、
そこに倣うのが一貫している。

### 尺度の 0 と負値を拒否する理由

`SCALE` で 0 を許すと図形が点に潰れ、負値を許すと鏡像になる。
どちらも「拡大縮小」としては事故なので、ツール側で拒否してエラーを出す。
鏡像が欲しい場合は `MIRROR` を使うよう案内する。

`Geometry::scaled` 自体も 0 と非有限な倍率では `self` を返す安全網を持つが、
**検証はツールの責務**で、コア側は最後の防波堤という位置づけ。

## ADR-0020: 円弧の鏡像は開始角と終了角を入れ替える

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 1）

### 問題

`Arc` は「`start_angle` から `end_angle` へ**反時計回り**」という約束で定義している。

鏡像反転は**回転の向きを反転させる**（反時計回り → 時計回り）。
そのため、両方の角度を反射するだけでは足りず、**開始角と終了角を入れ替える**必要がある。

```text
new_start = 2 * axis_angle - end_angle      ← end から作る
new_end   = 2 * axis_angle - start_angle    ← start から作る
```

### なぜ厄介か

入れ替えを忘れても**円弧は描かれる**。ただし元の弧ではなく
**補角の弧（円の残りの部分）**になる。
図面上では「なんとなく違う」程度にしか見えず、レビューでも気づきにくい。

そのためテストで明示的に固定した。

- `geometry_mirrored_arc_swaps_start_and_end` … 具体的な角度で期待値を書く
  （X 軸まわりに 0 → π/2 の四分円を鏡像すると −π/2 → 0 になる）
- `geometry_mirrored_arc_twice_is_identity` … 同じ軸で 2 回鏡像すると元に戻る

同じ罠は円弧を含むあらゆる変換に潜むので、
回転・拡大縮小についても恒等変換（360° 回転、倍率 1.0）のテストを置いている。

## ADR-0021: DXF は R12 のまま据え置き、往復ロスは警告で伝える

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 2）、[ADR-0014](#adr-0014-dxf-は外部クレートを使わず自前で読み書きする)

### 背景

XLINE（作図線）と GROUP は **DXF R12 (AC1009) に存在しない**。
XLINE は R13 以降、GROUP は R13 以降の `OBJECTS` セクションの `ACAD_GROUP` 辞書にある。

「後のバージョンにあるなら DXF のバージョンを上げるのもありでは」という問いが出たので、
背反を洗い出したうえで判断した。

### 検討した 3 案

| 案 | 往復ロス | 実装量 | 互換性 |
|---|---|---|---|
| **A: R12 のまま + 警告** | XLINE → 線分、GROUP 消失 | 小 | 最強 |
| B: R12 + XDATA | ymcad 同士なら無し | 中 | 最強（他ソフトは無視） |
| C: R2000 以降へ移行 | 無し | **大** | 下がる |

### 決定

**A を採る。** 実用上問題になった時点で B への移行を検討する。

#### C（バージョンアップ）を今は採らない理由

R13 以降はファイル構造が段違いに重い。R2000 準拠には最低でも次が要る。

- `CLASSES` セクション
- `OBJECTS` セクションとルート辞書
- **ハンドルが必須**になり全体で一意 + `$HANDSEED`
- 各エンティティに `100` サブクラスマーカー（`AcDbEntity` / `AcDbLine` …）
- エンティティが `BLOCK_RECORD` 配下に属するため、`TABLES` に `BLOCK_RECORD`、
  `BLOCKS` に `*Model_Space` / `*Paper_Space`
- 各オブジェクトに所有者ポインタ（`330`）

現状の `dxf/write.rs` は約 500 行で、R2000 準拠はこの数倍になる。
そして **構造を 1 つ落とすと読み手が黙ってファイルを拒否する**。
これは ADR-0014 で外部クレートを避けた理由（「指定漏れで R12 でないファイルが静かに出る事故」）と
同じ罠で、規模だけが大きくなる。

R12 は古い CAD・CAM・レーザーカッターまでほぼ何でも読める。上げると読めない相手が出る。

#### B（XDATA）を将来の選択肢として残す理由

**R12 にも XDATA（拡張データ、グループコード 1000〜1071）はある。**
`APPID` を登録すればエンティティに独自データを付けられる。

- `LINE` として書き出しつつ「これは本当は作図線」という印を XDATA で付ける
- グループ所属も XDATA に入れる
- **ymcad で開き直せば完全に復元**でき、他のソフトでは普通の線分として読める

R12 の互換性を保ったまま往復のロスを無くせる。コストは writer / reader 双方への
XDATA 対応で、C よりずっと軽い。

**移行を検討する条件**: ユーザーが作図線やグループを保存して失うことを実際に不便に感じたとき。
それまでは警告で十分とする。

### 警告の仕組み

黙って情報を落とさないよう、書き出しは警告を返す。

```rust
pub struct WriteReport { pub text: String, pub warnings: Vec<String> }
pub fn write_to_string(doc: &Document) -> WriteReport;
pub fn write_to_file(doc: &Document, path: &Path) -> Result<Vec<String>>;
```

呼び出し側（`cad-app`）はこれをコマンドラインへ表示する。
作図線が何本あっても警告は 1 行にまとめ、本数を添える。

### 補足: R12 出力の実地検証

2026-08-12、ユーザーが書き出した DXF を **LibreCAD で開けることを確認済み**。
Phase 6 の受け入れ基準がこれですべて埋まった。

## ADR-0022: グループの所属はエンティティ側だけが持つ

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 2）

### 背景

GROUP / UNGROUP を実装するにあたり、「どのエンティティがどのグループに属するか」を
どちら側に持たせるかを決める必要があった。

| 案 | 持ち方 |
|---|---|
| A | エンティティが `group: Option<GroupId>` を持つ |
| B | グループが `members: Vec<EntityId>` を持つ |
| C | 両方持つ（相互参照） |

### 決定

**A を採る。** `GroupTable` は名前と ID の対応だけを持ち、メンバー一覧は持たない。

B や C にすると、**エンティティの削除・Undo のたびに両方の辻褄を合わせる必要がある**。
`ERASE` → `UNDO` → 別の操作 → `UNDO` のような経路で片方だけ直し損ねると、
グループに「もう存在しないエンティティ」が残ったり、逆に所属が消えたりする。
しかもその不整合は選択したときに初めて表面化するので、原因を追いにくい。

**エンティティ側だけが真実なら、メンバーは走査して求めればよい。**
削除や Undo で自動的に整合が保たれ、同期のコードが 1 行も要らない。

10,000 要素規模で毎回走査してもミリ秒に満たないので、性能上の問題もない。
問題になったら派生キャッシュ（ADR-0011 と同じく `Document::revision()` をキーにする）を
`cad-app` 側に置けばよく、`Document` の構造は変えなくて済む。

### Redo でグループ ID を使い回す

`CreateGroup` は Undo したあとも確保した `GroupId` を捨てず、Redo で**同じ ID を再利用**する。

ID が変われば、Undo スタックに残る他のコマンド（そのグループを指す `Ungroup` など）の
参照が壊れる。これは [ADR-0004](#adr-0004-エンティティストアは-slotmap-ではなく自前のアリーナにする) で
エンティティに `restore` を用意したのと同じ理由。
`create_group_redo_reuses_the_same_group_id` で固定している。

### DXF について

DXF R12 に `GROUP` は無い（R13 以降の `OBJECTS` セクション）。
保存するとグループ情報は失われ、書き出し時に警告が出る（[ADR-0021](#adr-0021-dxf-は-r12-のまま据え置き往復ロスは警告で伝える)）。
往復させたい要求が実際に出たら、同 ADR の案 B（R12 + XDATA）を検討する。
