## ADR-0001: IME 検証結果 (Phase 0)

- **状態**: 確定 — **合格**。egui / eframe を採用し Phase 1 へ進む。
- **日付**: 2026-08-11

### 背景

ymcad は AutoCAD ライクなコマンドラインを持つ。テキストエンティティ自体は非スコープだが、コマンド入力欄とレイヤ名で日本語入力を受ける可能性がある。`egui` の IME サポートが Ubuntu で成立しないなら GUI の技術選定そのものを見直す必要があるため、実装に先立って検証する。

### 検証環境

| 項目 | 値 |
|---|---|
| OS | Ubuntu 24.04.4 LTS |
| セッション | Wayland (`XDG_SESSION_TYPE=wayland`)、`DISPLAY=:0` あり (XWayland 利用可) |
| IME | ibus (`QT_IM_MODULE=ibus`, `XMODIFIERS=@im=ibus`, `GTK_IM_MODULE` は未設定) |
| toolchain | rustc / cargo 1.96.0 |
| GUI | eframe / egui 0.36.1、winit 0.30.13 |

`GTK_IM_MODULE` が未設定でも問題ない。winit は IME に GTK を経由しない。

### ソース調査で確定した事実

egui 0.36.1 / egui-winit 0.36.1 / winit 0.30.13 のソースを直接確認した結果:

1. **アプリ側の IME API 呼び出しは不要。**
   `egui-winit-0.36.1/src/lib.rs:1152` が `window.set_ime_allowed()` を、同 `:1177` が
   `window.set_ime_cursor_area()` を自動で呼ぶ。トリガーは `PlatformOutput::ime` で、これは
   フォーカスを持つ `TextEdit` 自身が毎フレーム書き込む。`NativeOptions` の opt-in も環境変数も不要。

2. **`ImeEvent::Enabled` / `Disabled` は届かない。**
   egui 0.36 で両者は `#[deprecated = "No longer used by egui"]`
   (`egui-0.36.1/src/data/input/ime_event.rs:8,35`)。egui-winit は winit の該当イベントを
   意図的に捨てている（winit#2498「X11 と Wayland で意味が異なる」ため）。
   生きているのは `Preedit` / `Commit` / `DeleteSurrounding` の 3 つ。

3. **候補ウィンドウは `IMEOutput::rect`（ウィジェット全体）にアンカーされる。**
   `cursor_rect`（キャレット位置）も計算されるが egui-winit は使っていない。
   結果として候補ウィンドウは「キャレット直下」ではなく「入力欄の左端」に出る。
   横長のコマンドライン UI では軽微な違和感になりうるが、機能上の欠陥ではない。

4. **未確定文字列はアプリの `&mut String` に直接書き込まれる。**
   `TextEdit` は `ImeEvent::Preedit` を受けて `insert_text_at` でバッファへ挿入し、
   `Commit` 時に `clear_preedit_text` してから確定文字列を入れる。
   → **変換中にコマンドラインのバッファをパースしてはいけない。** Phase 3 の設計制約になる
   （[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3) 参照）。

5. **`WINIT_UNIX_BACKEND` は winit 0.30 で廃止済み。**
   バックエンド選択は `WAYLAND_DISPLAY`／`WAYLAND_SOCKET` が非空なら Wayland、
   でなければ `DISPLAY` を見て X11。X11 で試すには `WAYLAND_DISPLAY= cargo run` とする。
   なお `set_ime_cursor_area` は **X11 では位置のみ有効でサイズが無視される**
   (winit 0.30.13 のドキュメント記載)。Wayland は `zwp_text_input_v3::set_cursor_rectangle`
   で完全に実装されており、この点では **Wayland のほうが X11 より対応が良い**。

6. **既知の ibus + Wayland 不具合は修正済み。**
   egui#7485（ibus + Wayland で 1 文字しか入力できない）は 2026-04-06 に close 済みで、
   修正は egui 0.35 に入っている。egui 0.36.1 時点で ibus + Wayland の未解決 issue は無い。
   未解決なのは fcitx5 系（egui#7975, #2529）で、本環境の構成には該当しない。

7. **egui の同梱フォントは CJK グリフを持たない。**
   これを放置すると日本語がすべて豆腐 (□) になり、「IME が壊れている」という誤判定を招く。
   `/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc` のフェイス index 0
   (`Noto Sans CJK JP`、`fc-query` で確認) を明示的に読み込む必要がある。
   epaint 0.36 は skrifa 経由で `.ttc` の face index 指定に対応している
   (`epaint-0.36.1/src/text/fonts.rs:162`)。

   → **Phase 1 の `cad-app` にもこのフォント読み込みが必須**。スパイクの
   `spikes/ime-check/src/jp_font.rs` をそのまま移植する。

### 手動検証の結果

`spikes/ime-check` をユーザーが起動し、中央の入力欄①と下部の入力欄②（本体のコマンドラインと同じ位置）の両方で `nihongo` → 変換 → 確定を実施した。

| # | 確認項目 | Wayland (ibus + mozc) | 備考 |
|---|---|---|---|
| 1 | 変換候補ウィンドウが表示されるか | ✅ | mozc の候補ポップアップが出る |
| 2 | 候補ウィンドウがカーソル位置に追従するか | ✅ | 入力欄①と②で表示位置が変わることを確認 |
| 3 | 未確定文字列がインライン表示されるか | ✅ | 入力欄の**中に下線付き**で表示された |
| 4 | 確定文字列が正しくバッファに入るか | ✅ | ①②の両方で `Commit` を受信、文字化け・欠落なし |
| 5 | IME 有効化 API の明示呼び出しが必要か | ✅ **不要** | 入力欄クリックで【項目5】が緑化、外すと復帰。アプリ側は IME API を一切呼んでいない |

日本語は豆腐にならず正しく描画された（Noto Sans CJK JP の明示読み込みによる）。

X11 (`WAYLAND_DISPLAY= cargo run`) での IME 比較は未実施。Wayland ネイティブが本命であり、そちらが全項目 PASS のため Phase 0 の判断には不要と判断した。

Phase 1 で `cad-app` の X11 起動は確認済み（`WAYLAND_DISPLAY= cargo run --release` でプロセスがエラーなく継続動作）。**ただし X11 での IME 挙動と描画の見た目は未検証。** 必要になった時点で比較する。

### 決定

**egui / eframe 0.36 を採用し、そのまま Phase 1 へ進む。** IME 回避策（X11 バックエンド強制、外部ダイアログ、独自 IME ブリッジ）はいずれも不要。

派生する実装上の決定:

1. **`cad-app` でも日本語フォントの明示読み込みを必須とする。**
   `spikes/ime-check/src/jp_font.rs` をそのまま `cad-app` へ移植する。
2. **IME 系 API はアプリ側から呼ばない。** egui-winit の自動処理に任せる。
   ただしコマンドライン確定時の変換中断だけは `Memory::interrupt_ime()` を使う
   （[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3) 参照）。
3. **候補ウィンドウが入力欄左端にアンカーされる件は仕様として受け入れる。**
   ymcad のコマンドラインは横長のため候補がキャレットから離れて出るが、
   egui 0.36 の実装に由来するもので、回避には egui 本体の改変が要る。実害は軽微。

## ADR-0002: コマンドラインは変換中にパースしない (Phase 3)

- **状態**: 予定（Phase 3 で実装）
- **日付**: 2026-08-11

### 背景

ADR-0001 の調査 4 のとおり、`TextEdit` は未確定文字列をアプリのバッファへ直接書き込む。加えて:

- IME がかな入力モードのとき、`@100,50` は `＠１００，５０` のように全角で入りうる
- 変換中は winit が `KeyboardInput` を送らないため、Enter によるコマンド確定ハンドラが沈黙し、確定用の Enter で予期せず発火する

座標直接入力（`100,50` / `@100,50` / `@100<45`）を扱う ymcad のコマンドラインでは、これが誤入力に直結する。

### 決定

Phase 3 のコマンドライン実装で以下を守る:

1. アプリ状態に `composing: bool` を持つ。`ImeEvent::Preedit { text, .. }` で `text` が非空なら `true`、`Commit` で `false`。
2. **`composing == true` の間はバッファを一切パースしない。**
3. パース前に ASCII 範囲を NFKC 正規化する（`＠` `，` `＜` `０-９` → 半角）。
4. コマンドを確定する Enter は、IME を確定する Enter とは**別の打鍵**であることを要求する。

## ADR-0003: トレランスは「絶対値下限 + 相対誤差」のハイブリッドにする

- **状態**: 確定（ユーザー承認済み）
- **日付**: 2026-08-11

### 背景

指示書は `EPS_LEN = 1e-9` / `EPS_ANGLE = 1e-12` の一元管理を要求している。
一方で「ズーム倍率 1e-6〜1e6 の範囲で座標精度が破綻しないこと」も要求している。

この 2 つは、素直に絶対値比較 `|a - b| <= EPS_LEN` を実装すると両立しない。
座標が 1e6 に達すると f64 の ULP は約 2e-10 になり、`1e-9` はわずか数 ULP しか
許容しなくなる。つまり **事実上の完全一致判定に化けて**、交点判定やスナップが
その領域で成立しなくなる。

### 決定

長さの比較を次のハイブリッドで行う。

```text
|a - b| <= max(EPS_LEN, EPS_REL * max(|a|, |b|))
```

- `EPS_LEN = 1e-9` は **絶対値の下限（フロア）** として維持する。定数名も指示書のまま。
- `EPS_REL = 1e-12` を追加する。座標の絶対値が大きい領域ではこちらが効く。
- 純粋な相対比較にしないのは、原点近傍（`a ≈ b ≈ 0`）で破綻するため。
- 角度は値域が `[0, 2π)` に収まり桁が暴れないので、`EPS_ANGLE` による絶対値比較のまま。

`geom/tolerance.rs` に `eq_len` / `len_tolerance` / `is_zero_len` / `lt_len` / `gt_len` /
`eq_angle` / `wrap_2pi` / `wrap_signed` を置き、**ソース中にトレランスを直書きしない**
規約を CI で検査する。

### 補足（実装時に踏んだ落とし穴）

`eq_angle` は当初 `wrap_signed(a - b).abs() <= EPS_ANGLE` と実装したが、
`wrap_signed` が内部で `± TAU` の加減算を行うため丸め誤差が約 `9e-17` 混入し、
ちょうど境界の値（`eq_angle(0.0, EPS_ANGLE)`）が誤って不一致になった。
差が既に十分小さい場合は正規化を挟まないよう短絡させて解決した。

## ADR-0004: エンティティストアは slotmap ではなく自前のアリーナにする

- **状態**: 確定
- **日付**: 2026-08-11

### 背景

指示書は世代つきアリーナを要求し、自前実装でも `slotmap` でも可としている。

### 決定

**自前実装にする。**

決め手は `slotmap` に **「呼び出し側が指定したキーで再挿入する API」が無い**こと。
`remove(k)` した後に挿入すると必ず別のキーになる。

CAD では `ERASE` → `UNDO` が日常操作である。Undo でエンティティを戻したときに
`EntityId` が変わると、Undo スタックに積まれた他のコマンド（「エンティティ k を移動」
「エンティティ k のレイヤを変更」など）の参照が一斉に壊れる。
`EntityStore::restore(id, entity)` で **元の ID のまま**書き戻せることが必須。

副次的な理由:

- `slotmap` の `iter()` は順序が未定義。こちらはスロット昇順（= 作成順 = 描画順）で
  走査できるため、DXF の出力順やピック順を決定的にできる。
- DXF ハンドルは 16 進文字列で安定している必要がある。`EntityId::index` から
  素直に導出できる。

### スロット割り当ての方針

**スロット番号は文書の生存期間中に再利用しない（単調増加）。**

空いたスロットを使い回すと、まだ Undo スタックに残っているコマンドが参照している
スロットを別のエンティティが占有し、`restore` が失敗しうる。
スロットの回収は Undo 履歴を捨てるとき（新規作成・ファイル読み込み）にのみ行う。
2D 作図のセッションで消費するメモリは無視できる。

## ADR-0005: ビューポート変換は相似変換で保持する

- **状態**: 確定
- **日付**: 2026-08-11

### 決定

アフィン行列ではなく **モデル空間の中心 `center: Point2` + 一様スケール `scale: f64`**
の 3 スカラで保持する。

理由:

- 逆変換が閉じた形で厳密に求まる。行列式の逆数を取らないので極端なズームで破綻しない。
- 画面上で一定に保ちたい量（スナップの拾い半径、線幅、破線ピッチ、円弧の分割精度、
  グリッド間隔）がすべてスカラ `scale` の関数として書ける。行列だと毎フレーム
  スケールを抽出し直すことになり、非直交成分が混ざると崩れる。
- 平行移動をスクリーン空間ではなくモデル空間の点として持つことで、1e6 のような
  大きな値を f64 側に留められる。
- 2D 作図にせん断は不要。将来 UCS の回転を入れるとしても 4 スカラで済む。

### f64 → f32 の縮小をどこで行うか

`model_to_screen` では **「f64 で引き算 → f64 で掛け算 → 最後に一度だけ f32 へ」**
の順を守る。`(p.x - center.x)` の結果は見えている範囲 `rect.width() / scale` で
抑えられるので、f32 に落としても誤差は 1e-4 px 程度で視認できない。

逆に先に f32 化してから引き算すると、`center` が 1e6 のとき有効数字が引き算の前に
7 桁失われ、完全に破綻する。この順序が守られていることを保つため、
`as f32` を `viewport.rs` だけに閉じ込め、CI で検査する。

## ADR-0006: ホイールズームの倍率は乗算で更新する（整数レベル方式は採らない）

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

Phase 1 の申し送りで「`scale` を直接乗算しているため、ズームイン/アウトを繰り返すと
倍率がドリフトするのではないか」という懸念を挙げていた。
回避策として、整数のズームレベル `level: i32` から
`scale = base * STEP^level` を導出する方式が考えられる。

### 実測

`zoom_about` を **20,000 回**（50 段の出入りを 200 往復）適用して倍率の相対誤差を測った。

```
相対誤差 < 1e-9
```

f64 の乗算 1 回あたりの誤差は数 ULP しかなく、この回数では実用上まったく問題にならない。
テストは `crates/cad-app/src/viewport.rs` の `zoom_roundtrip_does_not_drift`。

### 決定

**乗算による更新を維持する。整数ズームレベル方式は採用しない。**

整数レベル方式には副作用がある。`zoom_to_fit` は任意の倍率を設定するため、
その直後のホイール操作でレベルへの丸めが起きて倍率が不連続に跳ぶ。
実測でドリフトが問題にならない以上、この副作用を負う理由がない。

倍率は `MIN_SCALE = 1e-9` 〜 `MAX_SCALE = 1e9` でクランプしている
（指示書の要求範囲 1e-6〜1e6 より広い）。

## ADR-0007: グリッド線の本数に上限を設ける

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

グリッドの刻みはズームに応じて 1/2/5 系列で選ぶため、通常は画面に 70 本前後しか出ない。
しかし刻みの計算が想定外の値を返した場合（極端な倍率、NaN、ゼロ）に
描画ループが事実上停止するリスクがある。

### 決定

グリッド座標の生成を純粋関数 `grid_coords(min, max, step)` に切り出し、
本数を `MAX_GRID_LINES = 2000` で頭打ちにする。
不正な入力（`step <= 0`、NaN、`min > max`）では空を返す。

これにより **グリッド描画のコストがズーム倍率によらず一定**になり、
60fps の維持がズーム操作に対して保証される。

座標は `x += step` の累積加算ではなく毎回 `(first + k) * step` で計算する。
累積加算は誤差が溜まって格子が歪む。

ズーム倍率 1e-6〜1e6 × 原点/±1e6 の全組み合わせで本数が 200 本以下に収まることを
`crates/cad-app/src/render.rs` の `grid_line_count_stays_sane_across_zoom_range` で検証している。

## ADR-0008: 確定前の図形は Document に入れない

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

作図中のラバーバンド（LINE の次の点までの線、CIRCLE の半径追従など）を
どう扱うかには 2 つのやり方がある。

1. 途中の図形をとりあえず `Document` に入れ、確定時に置き換える／中断時に消す
2. `Document` には入れず、描画時にだけ使う派生データとして持つ

### 決定

**2 を採る。** `Tool::preview` がカーソル位置から `Vec<Geometry>` を返し、
`render::draw_preview` がそれを描く。`Document` には一切入らない。

1 を選ぶと次の問題が起きる。

- カーソルが動くたびにコマンドが積まれ、**Undo 履歴が汚れる**。
  「Undo したら線が 1 本消えるのではなくラバーバンドが 1 フレーム戻る」という
  使い物にならない挙動になる
- 「あとで消すから」という理由で `EditCtx` を経由しない変更経路を作りたくなる。
  Phase 1 で型によって封じた不変条件が、ここで崩れる

ラバーバンドは本質的に **UI の表示状態**であって図面の内容ではない。
`cad-app` 側に置くのが正しい。

## ADR-0009: 交差選択は矩形の 4 辺との交点で厳密に判定する

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

交差選択（右→左ドラッグ）は「矩形に少しでも掛かる要素」を選ぶ。
最も安価な実装は境界ボックス同士の重なり判定だが、これは過剰に拾う。

例: 半径 10 の円の左上の角にある小さな矩形は、円の bbox とは重なるが
円周とは交わらない。bbox 判定だと選ばれてしまい、ユーザーの意図と食い違う。

### 決定

2 段で判定する。

1. 図形の bbox が矩形と重ならなければ確実に掛かっていない（安価な足切り）
2. 図形全体が矩形に収まっていれば掛かっている
3. そうでなければ **矩形の 4 辺と実際に交点を持つか**を `geom::intersect` で調べる

対象が線分・円・円弧・ポリラインだけなので、この判定は厳密になる。
窓選択（完全内包）は bbox の包含で厳密に判定できる（これらの図形の bbox は
すべてタイトなため）。

計算量は最悪でも「要素数 × 4 辺」で、Phase 4 で空間インデックスを入れれば
候補を絞れる。

## ADR-0010: スナップのヒステリシスは「吸着点」を基準にする

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

指示書は「一度スナップしたら、カーソルが多少動いても即座に外れないこと
（これが操作感を決めます）」を要求している。

単一の半径で「近ければ吸着」とすると 2 つの問題が起きる。

1. カーソルが境界上にあるとき吸着と解除が毎フレーム入れ替わり、マーカーがちらつく
2. 狙った点に吸い付いた後に少し手が動くと外れるため「掴んだ感じ」がしない

### 決定

取得と解放で別の半径を使う。

- 未吸着のとき: カーソルから **10px** 以内に候補があれば吸着する
- 吸着中のとき: **吸着点から 16px** を超えて離れるまで保持する

**判定の基準をカーソルではなく吸着点にする**のが肝。カーソル基準にすると
吸着した瞬間に基準が動いてしまい、履歴が効かずヒステリシスにならない。

半径は画面上の px で定義し、`Viewport::px_to_model_len` でモデル空間へ換算する。
これによりズーム倍率によらず操作感が一定になる。

## ADR-0011: 空間インデックスは Document ではなく cad-app 側の派生キャッシュに置く

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

10,000 要素でスナップ検出を 16ms 以内に収めるには空間インデックスが要る。
これを `Document` の中に持つか、`cad-app` の派生キャッシュにするかで
保守コストが大きく変わる。

### 決定

**`cad-app` の派生キャッシュに置き、`Document::revision()` をキーに再構築する。**

`Document` の中に持つと、

- **すべてのコマンドがインデックスの更新と、その巻き戻しを実装する必要がある**。
  コマンド 1 つあたりの実装量が倍になり、しかも間違えても気づきにくい
- Undo でインデックスを正しく戻し損ねると、選択やスナップだけが静かに壊れる

派生キャッシュにすれば、`revision` が変わったら丸ごと作り直すだけで済む。
Undo / Redo でも `revision` は進む（Phase 1 でそう設計した）ので、
巻き戻しでも自動的に無効化される。

10,000 要素程度の一括構築はミリ秒オーダーで、毎編集で作り直しても
体感に影響しない。問題になったら差分更新を検討する。

## ADR-0012: レイヤパネルは Document を変更せずコマンドを返す

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

レイヤの色変更・表示切替・リネーム・削除は、作図と同じく Undo できなければならない
（指示書の受け入れ基準「レイヤ操作が Undo で巻き戻る」）。

GUI パネルは「チェックボックスを押したらその場で値を書き換える」形にしたくなるが、
それをやると `LayerTable` への直接の変更経路ができ、Phase 1 で型によって封じた
不変条件が崩れる。

### 決定

**レイヤパネルは `Document` を一切変更しない。**
`LayerPanel::show()` はユーザー操作を `Vec<Box<dyn Command>>` へ翻訳して返すだけで、
適用は呼び出し側が `Document::apply` で行う。

```rust
let commands = self.layer_panel.show(ui, &self.doc, &self.session.selection);
for cmd in commands {
    self.session.apply_external(cmd, &mut self.doc);
}
```

これにより、レイヤ操作も作図と同じ 1 本の経路を通り、Undo/Redo が自動的に効く。
`LayerTable` の変更系メソッドは `pub(crate)` のままで、`cad-app` からは
名前を呼ぶことすらできない状態を保てる。

## ADR-0013: 破線パターンは図面単位ではなく画面 px で定義する

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

線種（`Dashed` / `Center` / `Hidden`）の破線ピッチをどの空間で定義するか。

- 図面単位で定義すると、拡大したとき破線が伸びて実線に見え、
  縮小すると点の集まりに見える
- 画面 px で定義すると、ズーム倍率によらず破線の見え方が一定になる

本プロトタイプでは線種は **画面表示のみ**（指示書の明示的な制約）で、
DXF へは書き出さない。

### 決定

`LineType::dash_pattern_px()` が **画面上の px** で「描く長さ, 空ける長さ, …」を返す。
描画はスクリーン空間で行い、パターンを順に消費しながら線分を分割する。

1 本の線分に描く破線の本数は 2000 で頭打ちにする。極端なズームで
1 本の線が画面を何度も横切っても描画が止まらないようにするため。

`cad-core` は f64 しか持たないためパターンは `&[f64]` で返る。
f64 → f32 の縮小は `viewport.rs` に閉じ込める規約があるので、
そこに `px_to_f32` を用意して唯一の入り口とした。

## ADR-0014: DXF は外部クレートを使わず自前で読み書きする

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

Rust には `dxf` クレートがあり、多数のバージョンとエンティティに対応している。
一方で本プロトタイプが必要とするのは **R12 の 4 種類のエンティティだけ**。

### 決定

**外部クレートを使わず、R12 を自前で読み書きする。**

理由:

- R12 は「グループコード行 + 値行」の繰り返しという単純な行指向フォーマットで、
  必要な範囲なら数百行で書ける
- `dxf` クレートは既定で **新しいバージョンを書き出す**。`header.version` の指定を
  忘れると R2013 が出力され、R12 を期待する読み手が拒否する。この事故は
  静かに起きて気づきにくい
- 何を出力するかを完全に制御できる。R12 に無い `LWPOLYLINE` を誤って書かない、
  `$EXTMIN`/`$EXTMAX` を必ず出す、といった制約を確実に守れる
- `cad-core` の「依存は std のみ」という状態を保てる

読み込み側は寛容にする。理解できないセクションやエンティティは読み飛ばし、
他のプログラムが作ったファイルでも失敗しないようにする。

## ADR-0015: 未保存確認では「保存する」選択肢を必ず用意する

- **状態**: 確定
- **日付**: 2026-08-12

### 背景

指示書は「未保存変更がある状態での終了時に確認ダイアログ」を要求している。
最小限の実装は「破棄しますか？ はい / いいえ」だが、これはユーザーに
**作業を失うか操作を諦めるかの二択**しか与えない。

### 決定

確認ダイアログは **「保存する」/「保存しない」/「キャンセル」** の 3 択にする。

- 「保存する」… 保存してから元の操作（新規 / 開く / 終了）へ進む。
  保存ダイアログがキャンセルされた場合は元の操作も行わない
- 「保存しない」… 変更を捨てて元の操作へ進む
- 「キャンセル」… 何もしない

確認が必要な操作は即座に実行せず `PendingAction` として保留し、
ユーザーが選んでから実行する。ウィンドウの ✕ ボタンについては
`ViewportCommand::CancelClose` で一旦終了を止めてから確認する。

## ADR-0016: コマンド表を `match` からデータに変える

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #1](https://github.com/yukimasui/ymcad/issues/1)

### 背景

コマンドの解決は `crates/cad-app/src/tools/mod.rs` の `create()` / `immediate()` にある
**文字列リテラルの `match` 文**だった。動くが、**コマンドを列挙できない**。

候補表示は「全コマンドを走査して先頭一致を探す」操作なので、`match` のままでは実装できない。

### 決定

`match` をやめて静的な表 `COMMANDS: &[CommandSpec]` にする。
`CommandSpec` は名前・エイリアス・一行説明・実体（ツール生成関数 or 即時コマンド）を持つ。

`create()` / `immediate()` は `lookup()` の薄いラッパとして残す。
**既存の呼び出し側とテストがそのまま通る**ようにして、変更の波及を抑えた。
リファクタが解決結果を変えていないことは、既存の
`aliases_resolve_to_expected_tools` / `canonical_names_resolve` が通ることで担保される。

副次的な効果として、表にしたことで

- 名前とエイリアスの重複を検査するテストが書けるようになった
  （重複すると先に書いた方が勝ち、後のコマンドが起動できなくなる）
- 全コマンドに説明文があることを機械的に確認できるようになった

### 候補のキー操作

- `↑` `↓` … 選択を動かす。**端では未選択へ戻る**（一覧から抜けられるように）
- `Tab` … 選択中（未選択なら先頭）の候補を入力欄へ補完する
- `Enter` / `Space` … **候補が出ていれば必ず候補を実行する**。
  優先順位は「明示的な選択 → 入力と完全一致 → 先頭候補」。
  候補が 1 件も無いときだけ打った文字列をそのまま確定する
  （→ **2026-08-12 に方針を変更。下記「未選択 Enter の扱いを撤回した経緯」を参照**）
- `Esc` … 候補が出ていればまず候補だけを閉じる。いきなりコマンドを中断すると
  打ち間違いのやり直しが面倒になるため

候補の操作キーは **`TextEdit` を描く前に消費する**。あとから処理すると
`TextEdit` にカーソル移動として取られてしまう。
これらは既存の `if self.composing { ... }` ブロックの中にあるので、
**日本語変換中は自動的に無効**になる（ADR-0002）。

### 未選択 Enter の扱いを撤回した経緯（2026-08-12、[Issue #5](https://github.com/yukimasui/ymcad/issues/5)）

当初は **「打った通りに実行される」のが既定**とし、
未選択で `Enter` を押すと候補ではなく入力文字列を確定していた。
候補を使うには `↑` `↓` で明示的に選ぶ必要があった。

**この判断は実際に使うと間違いだった。**
候補が出ている時点で目的のコマンドは先頭にいることがほとんどで、
そこからさらにカーソル操作を要求するのは冗長だった。
`L` と打った時点で `LINE` が先頭に出ているのに `Enter` で実行されないのは、
候補表示を入れた意味を損なう。

**変更後**: 候補が出ていれば必ず候補を実行する。優先順位は

1. `↑` `↓` で明示的に選ばれていればそれ
2. 入力と完全一致する候補があればそれ
3. どちらでもなければ先頭候補

**2 を挟むのが肝。** 候補の並び順は「エイリアス完全一致 → 名前の先頭一致 → …」なので
3 だけでも今は同じ結果になるが、`COMMANDS` の並びを変えた瞬間に壊れる。
完全一致を明示的に優先しておけば並び順に依存しない
（`SAVE` は `SAVEAS` の接頭辞でもあるので、これが効く場面が実際にある）。

**引き換えに「打った文字列と違うコマンドが走る」ことが起きうる**ので、
候補一覧で `Enter` の対象を必ず見せる。行頭の `⏎` と背景の 2 つで示し、
明示選択（濃い背景）と既定選択（薄い背景）を区別する。
`⏎` は背景色とは別の視覚チャンネルなので、テーマや配色に関わらず読み取れる。

この経緯を残しておくのは、**同じ議論を繰り返さないため**。
「打った通りに実行されるべきでは」という考えは筋が通っているが、
実際の打鍵数の前では割に合わなかった。

## ADR-0017: STRETCH の範囲は「選択に使われた交差窓」を蓄積して持つ

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #2](https://github.com/yukimasui/ymcad/issues/2)

### 背景

STRETCH は他の編集コマンドと違い、**選ばれた要素だけでなく「どの範囲で選んだか」**を
必要とする。範囲に入った点だけが動くのがこのコマンドの本質だからである。

しかし `Session::handle_rect_select` は矩形をその場で使い捨てており、
`Selection` には要素の ID しか残らなかった。

### 決定

`Session` に `crossing_rects: Vec<Aabb>` を持ち、
**交差選択のときだけ**矩形を追加する。`ToolCtx` 経由でツールへ渡す。

- **`Vec` にした理由**: AutoCAD は交差窓を複数回重ねて選択範囲を広げられる。
  1 つしか覚えないと 2 回目の窓で 1 回目が消え、意図と違う結果になる
- **窓選択（左→右）は数えない**: 完全内包の選択なので「範囲の内側だけ動かす」意味がない
- **`Shift` での選択解除では追加しない**: 動かす対象を広げてしまうため
- **クリック選択では範囲が空のまま**: このとき STRETCH は丸ごと移動になる。
  これは AutoCAD と同じ挙動で、意図的にそうしている

範囲は `cancel()`（`Esc`）と、選択をやり直すコマンド開始時にクリアする。
前のコマンドの範囲を引きずらないため。

### 円と円弧の扱い

**中心が範囲に入っていれば図形ごと動かし、入っていなければ動かさない。**
半径と角度は変えない。

AutoCAD は円をこの規則で扱う。円弧は本来は端点を引っ張って形状が変わるが、
中心と半径の再計算が必要になり、3 点が同一直線上になる退化ケースの処理も要る。
プロトタイプの範囲としては割に合わないと判断し、円と同じ規則にした
（ユーザーと合意済み）。

円周が範囲を横切っていても中心が外なら動かない点は、読み手が最も疑いそうなので
`geometry_stretched_circle_center_outside_is_unchanged_even_when_circumference_crosses_region`
というテストで明示的に固定してある。

## ADR-0018: クリック判定は `clicked_by()` ではなく「ボタンが離されたか」で行う

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #4](https://github.com/yukimasui/ymcad/issues/4)

### 背景

「マウスが動いている状態でクリックすると点が置けない」という不具合報告があった。

調べると egui が押下〜解放を **クリックと認めるのは次の両方を満たすときだけ**だった。

| 条件 | 既定値 | 場所 |
|---|---|---|
| 押した位置から動いた距離 | **6.0 px** 以内 | `egui::InputOptions::max_click_dist` |
| ボタンを押していた時間 | **0.8 秒** 未満 | `egui::InputOptions::max_click_duration` |

どちらかを外れると `Response::clicked_by()` は `false` になり、egui はドラッグとして扱う。

**時間の条件が盲点だった。** 距離だけの問題だと思い込むと直しきれない。
CAD の作図では狙いを定めてゆっくり押すのが普通で、0.8 秒はすぐ超える。

さらに悪いことに、`handle_pointer` は **点の入力待ち中は矩形ドラッグのブロックごと飛ばす**
作りだったため、クリックと認められなかった解放は **どこでも処理されず黙って捨てられていた**。

選択のクリックも同じ理由で取りこぼしていた。矩形選択には
「`DRAG_THRESHOLD_PX`（4.0px）未満ならクリック扱い」という復帰路があったが、
その先が `clicked_by()` なので結局拾えない。
しかも **4.0 は egui の 6.0 より小さい**ので、この閾値では egui の判定を肩代わりできていなかった。

### 決定

**「キャンバス上で主ボタンが離された」ことを入力の合図にする。**

```rust
let released = response.clicked_by(Primary) || response.drag_stopped_by(Primary);
```

`drag_stopped_by()` は距離超過でも時間超過でも発火するので、両方の原因を一度に塞げる。

- **点の入力待ち中**: 矩形選択に入らない状態なので、離されたら常に点として拾う。
  距離の閾値は設けない（手が動いていても拾えるようにするのが目的）
- **選択時**: 矩形ドラッグのブロックで、ドラッグ量が閾値未満なら
  `clicked_by()` へ流さず**その場でクリックとして処理する**

座標は **ボタンを離した位置**（`interact_pointer_pos()`）を使う。
スナップはその時点のカーソル位置から計算されているので、離した位置なら
**マーカーが出ている点と実際に入る点が一致する**。押した位置を使うとずれる。

### 採らなかった案

`ctx.options_mut` で egui の閾値自体を緩める案は採らない。
ダブルクリック判定にも影響し、時間の条件は別途上げる必要があるため、
副作用の範囲が読みにくい。

### テストできないこと

この判定は `egui::Response` の状態に依存するため単体テストで再現できない。
その旨を `handle_pointer` のドキュメントコメントに書き、変更時は手動確認するよう促している。

## ADR-0019: 変換コマンドは「その場で変換」と「複製を追加」を別コマンドに分ける

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 1）

### 背景

ROTATE / SCALE / MIRROR には AutoCAD 準拠の「元図形を残す」オプションがある
（ROTATE・SCALE は `C`、MIRROR は最後の「元を消しますか？」で `N`）。

1 つのコマンドにフラグを持たせて分岐させることもできる。

### 決定

**`RotateEntities` / `RotateCopyEntities` のように別のコマンド型に分ける。**

理由は **Undo の中身が根本的に違う**こと。

| | execute | undo |
|---|---|---|
| その場で変換 | 既存要素の `Geometry` を書き換える | **控えておいた変換前の `Geometry` を戻す** |
| 複製を追加 | 新しい要素を追加する | **作った要素を削除する** |

1 つの型にまとめると `execute` も `undo` もフラグによる分岐だらけになり、
「全部成功するか、何も変えずに失敗するか」という契約の検証が難しくなる。
既存の `MoveEntities`（前者）と `CopyEntities`（後者）が既に別型なので、
そこに倣うのが一貫している。

### 尺度の 0 と負値を拒否する理由

`SCALE` で 0 を許すと図形が点に潰れ、負値を許すと鏡像になる。
どちらも「拡大縮小」としては事故なので、ツール側で拒否してエラーを出す。
鏡像が欲しい場合は `MIRROR` を使うよう案内する。

`Geometry::scaled` 自体も 0 と非有限な倍率では `self` を返す安全網を持つが、
**検証はツールの責務**で、コア側は最後の防波堤という位置づけ。

## ADR-0020: 円弧の鏡像は開始角と終了角を入れ替える

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 1）

### 問題

`Arc` は「`start_angle` から `end_angle` へ**反時計回り**」という約束で定義している。

鏡像反転は**回転の向きを反転させる**（反時計回り → 時計回り）。
そのため、両方の角度を反射するだけでは足りず、**開始角と終了角を入れ替える**必要がある。

```text
new_start = 2 * axis_angle - end_angle      ← end から作る
new_end   = 2 * axis_angle - start_angle    ← start から作る
```

### なぜ厄介か

入れ替えを忘れても**円弧は描かれる**。ただし元の弧ではなく
**補角の弧（円の残りの部分）**になる。
図面上では「なんとなく違う」程度にしか見えず、レビューでも気づきにくい。

そのためテストで明示的に固定した。

- `geometry_mirrored_arc_swaps_start_and_end` … 具体的な角度で期待値を書く
  （X 軸まわりに 0 → π/2 の四分円を鏡像すると −π/2 → 0 になる）
- `geometry_mirrored_arc_twice_is_identity` … 同じ軸で 2 回鏡像すると元に戻る

同じ罠は円弧を含むあらゆる変換に潜むので、
回転・拡大縮小についても恒等変換（360° 回転、倍率 1.0）のテストを置いている。

## ADR-0021: DXF は R12 のまま据え置き、往復ロスは警告で伝える

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 2）、[ADR-0014](#adr-0014-dxf-は外部クレートを使わず自前で読み書きする)

### 背景

XLINE（作図線）と GROUP は **DXF R12 (AC1009) に存在しない**。
XLINE は R13 以降、GROUP は R13 以降の `OBJECTS` セクションの `ACAD_GROUP` 辞書にある。

「後のバージョンにあるなら DXF のバージョンを上げるのもありでは」という問いが出たので、
背反を洗い出したうえで判断した。

### 検討した 3 案

| 案 | 往復ロス | 実装量 | 互換性 |
|---|---|---|---|
| **A: R12 のまま + 警告** | XLINE → 線分、GROUP 消失 | 小 | 最強 |
| B: R12 + XDATA | ymcad 同士なら無し | 中 | 最強（他ソフトは無視） |
| C: R2000 以降へ移行 | 無し | **大** | 下がる |

### 決定

**A を採る。** 実用上問題になった時点で B への移行を検討する。

#### C（バージョンアップ）を今は採らない理由

R13 以降はファイル構造が段違いに重い。R2000 準拠には最低でも次が要る。

- `CLASSES` セクション
- `OBJECTS` セクションとルート辞書
- **ハンドルが必須**になり全体で一意 + `$HANDSEED`
- 各エンティティに `100` サブクラスマーカー（`AcDbEntity` / `AcDbLine` …）
- エンティティが `BLOCK_RECORD` 配下に属するため、`TABLES` に `BLOCK_RECORD`、
  `BLOCKS` に `*Model_Space` / `*Paper_Space`
- 各オブジェクトに所有者ポインタ（`330`）

現状の `dxf/write.rs` は約 500 行で、R2000 準拠はこの数倍になる。
そして **構造を 1 つ落とすと読み手が黙ってファイルを拒否する**。
これは ADR-0014 で外部クレートを避けた理由（「指定漏れで R12 でないファイルが静かに出る事故」）と
同じ罠で、規模だけが大きくなる。

R12 は古い CAD・CAM・レーザーカッターまでほぼ何でも読める。上げると読めない相手が出る。

#### B（XDATA）を将来の選択肢として残す理由

**R12 にも XDATA（拡張データ、グループコード 1000〜1071）はある。**
`APPID` を登録すればエンティティに独自データを付けられる。

- `LINE` として書き出しつつ「これは本当は作図線」という印を XDATA で付ける
- グループ所属も XDATA に入れる
- **ymcad で開き直せば完全に復元**でき、他のソフトでは普通の線分として読める

R12 の互換性を保ったまま往復のロスを無くせる。コストは writer / reader 双方への
XDATA 対応で、C よりずっと軽い。

**移行を検討する条件**: ユーザーが作図線やグループを保存して失うことを実際に不便に感じたとき。
それまでは警告で十分とする。

### 警告の仕組み

黙って情報を落とさないよう、書き出しは警告を返す。

```rust
pub struct WriteReport { pub text: String, pub warnings: Vec<String> }
pub fn write_to_string(doc: &Document) -> WriteReport;
pub fn write_to_file(doc: &Document, path: &Path) -> Result<Vec<String>>;
```

呼び出し側（`cad-app`）はこれをコマンドラインへ表示する。
作図線が何本あっても警告は 1 行にまとめ、本数を添える。

### 補足: R12 出力の実地検証

2026-08-12、ユーザーが書き出した DXF を **LibreCAD で開けることを確認済み**。
Phase 6 の受け入れ基準がこれですべて埋まった。

## ADR-0022: グループの所属はエンティティ側だけが持つ

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 2）

### 背景

GROUP / UNGROUP を実装するにあたり、「どのエンティティがどのグループに属するか」を
どちら側に持たせるかを決める必要があった。

| 案 | 持ち方 |
|---|---|
| A | エンティティが `group: Option<GroupId>` を持つ |
| B | グループが `members: Vec<EntityId>` を持つ |
| C | 両方持つ（相互参照） |

### 決定

**A を採る。** `GroupTable` は名前と ID の対応だけを持ち、メンバー一覧は持たない。

B や C にすると、**エンティティの削除・Undo のたびに両方の辻褄を合わせる必要がある**。
`ERASE` → `UNDO` → 別の操作 → `UNDO` のような経路で片方だけ直し損ねると、
グループに「もう存在しないエンティティ」が残ったり、逆に所属が消えたりする。
しかもその不整合は選択したときに初めて表面化するので、原因を追いにくい。

**エンティティ側だけが真実なら、メンバーは走査して求めればよい。**
削除や Undo で自動的に整合が保たれ、同期のコードが 1 行も要らない。

10,000 要素規模で毎回走査してもミリ秒に満たないので、性能上の問題もない。
問題になったら派生キャッシュ（ADR-0011 と同じく `Document::revision()` をキーにする）を
`cad-app` 側に置けばよく、`Document` の構造は変えなくて済む。

### Redo でグループ ID を使い回す

`CreateGroup` は Undo したあとも確保した `GroupId` を捨てず、Redo で**同じ ID を再利用**する。

ID が変われば、Undo スタックに残る他のコマンド（そのグループを指す `Ungroup` など）の
参照が壊れる。これは [ADR-0004](#adr-0004-エンティティストアは-slotmap-ではなく自前のアリーナにする) で
エンティティに `restore` を用意したのと同じ理由。
`create_group_redo_reuses_the_same_group_id` で固定している。

### ロック・非表示のレイヤにある一員は選択に入らない（Issue #51）

グループの一員を選ぶと全体が選ばれるが、**ロック・非表示のレイヤにある一員は選択に入らない**
（ユーザー判断 A。AutoCAD と同じ）。`expand_to_group` が `is_editable` と同じ判定で絞る。
クリック直後の選択と、パネル操作・UNDO / REDO 後の `retain_editable`（ADR-0039）の結果が
一致する。以前は、クリック直後はロックされた一員まで入り、MOVE などで動いてしまった。

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| A（採用） | 編集できない一員だけ外す | 選ぶ・確かめ直すの 2 経路が同じ結果になる。ロックの意味（動かさない）を守る |
| B | 編集できない一員が 1 つでもあればグループ全体を選ばない | クリックしても何も選ばれず、理由が見えない。グループの他の一員を編集する手段が無くなる |
| C | グループをロックより優先する | ロックされたレイヤの図形が動く。ロックの約束を破り、`retain_editable` とも食い違う |

グループの一部だけが選ばれることになるが、GROUP / UNGROUP / EXPLODE は選択された要素から
所属を引くだけなので影響しない（UNGROUP は一員が選ばれていればグループ全体を解除する）。

### DXF について

DXF R12 に `GROUP` は無い（R13 以降の `OBJECTS` セクション）。
保存するとグループ情報は失われ、書き出し時に警告が出る（[ADR-0021](#adr-0021-dxf-は-r12-のまま据え置き往復ロスは警告で伝える)）。
往復させたい要求が実際に出たら、同 ADR の案 B（R12 + XDATA）を検討する。

## ADR-0023: TRIM / EXTEND は切断エッジを選ばせず、図面上の全図形を暗黙のエッジにする

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 3）

### 背景

古い AutoCAD の TRIM / EXTEND は 2 段階だった。

```
TRIM → 切断エッジを選択 → Enter → 切る部分をクリック
```

近年の AutoCAD は既定が**クイックモード**に変わり、エッジの選択フェーズが消えている。
どちらに寄せるかをユーザーに確認し、**クイックモードで合意した**。

### 決定

**エッジの選択フェーズを設けない。** `TR` と打ったらすぐ「切り取る部分をクリック」で始まり、
図面上の**対象自身を除く可視図形すべて**が切断エッジになる（`cutters_except`）。

理由は 2 つ。

1. **対話が半分になる。** 実務で切りたいのはたいてい「見えている線の交点」で、
   エッジを選び直す場面は少ない
2. **エッジ選択の状態を持たなくて済む。** 選択フェーズを設けると、
   ツールが「選ばれたエッジ集合」を抱えたまま `ApplyAndContinue` で回り続けることになり、
   途中で図形が消えたとき（Undo など）にエッジ集合が腐る。
   毎回その場の図面から集めれば、そもそも腐らない

**非表示レイヤの図形はエッジにならない。** 見えていないものが切断に効くと理由が分からなくなる。
ロックレイヤの図形は「見えているので切れるべき」なのでエッジには**なる**が、
ロックされた図形自体は対象に選べない（`is_entity_editable` と `is_entity_visible` の使い分け）。

### 代償

図面上の全図形と交点を取るので、要素数に比例したコストがかかる。
10,000 要素でもクリック 1 回あたりミリ秒の桁なので、当面は素直な全走査でよい。
問題になれば `cad-app` 側の四分木（[ADR-0011](#adr-0011-空間インデックスは-document-ではなく-cad-app-側の派生キャッシュに置く)）で
候補を絞ってから `Vec<Geometry>` を組み立てる形に変えられる。
`TrimEntity` / `ExtendEntity` の外形は変わらない。

### 対象を線分に限る

`Line` のみを対象とする。円弧・円・ポリラインは**エッジにはなるが、切られる側にはならない**。

ポリラインの部分トリムは頂点列の再構成（分割・再結合）が必要で、別の問題になる。
`EXPLODE`（`X`）で線分に分解してから使う道があるので、実用上の穴は塞がっている。

## ADR-0024: コマンド実行中の図形ピックは `Session` が担い、ツールには拾い半径を渡さない

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 3）

### 背景

段階 2 まで、`StepInput` には点しか無かった。コマンドが動いている間、
キャンバスのクリックはすべて `StepInput::Point` になる。

TRIM / EXTEND / FILLET / CHAMFER は「どの図形か」を指す必要があるので、
これを埋める必要が出た。案は 2 つあった。

| 案 | 仕組み |
|---|---|
| A | `ToolCtx` に拾い半径を持たせ、**ツールが自分で図形を探す** |
| B | `Tool::wants_entity()` で申告させ、**`Session` が拾って `StepInput::Entity` で渡す** |

段階 2 の XLINE のオフセットでは、暫定として A（`nearest_line_at`）を使っていた。

### 決定

**B を採る。** A の暫定実装は段階 3 で削除した。

A だと、拾い方が**ツールごとにばらける**。XLINE の暫定実装は「最も近い線分」を選んでいたが、
`selection::pick_at` は拾い半径の内側で最も近いものを選ぶ。前者は半径を無視するので、
図形から遠く離れた場所をクリックしても拾えてしまう。同じ「クリックで図形を指す」操作が
コマンドによって違う挙動になるのは、使う側から見て説明できない。

B なら拾い方は `selection::pick_at` の 1 箇所だけになり、
コマンド無しのピック選択とも自動的に同じ挙動になる。

```rust
// Session::handle_click
if self.wants_entity() {
    if let Some(id) = selection::pick_at(doc, model, pick_tolerance) {
        self.feed_tool(StepInput::Entity { id, at: model }, doc);
        return;
    }
}
self.feed_tool(StepInput::Point(model), doc);
```

**拾えなかったクリックは `StepInput::Point` のまま渡す。** 握り潰すと無反応になり、
外したのか受け付けていないのか分からない。ツール側で「図形の上をクリックしてください」と案内する。

`wants_entity()` は**状態で切り替わってよい**。`CornerTool` は半径や距離の入力待ちの間だけ
`false` を返し、数値入力を図形ピックに取られないようにしている。

### `at` を一緒に渡す理由

`StepInput::Entity { id, at }` は ID だけでなく**クリック位置**も持つ。
TRIM は「どちら側を切るか」、FILLET は「角のどちら側を残すか」をクリック位置で決めるので、
ID だけでは足りない。

## ADR-0025: FILLET の半径と CHAMFER の距離は `Session` が持つ

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #7](https://github.com/yukimasui/ymcad/issues/7)（段階 3）

### 背景

AutoCAD は FILLET の半径と CHAMFER の距離を**コマンドをまたいで覚えている**。
一度 `R` で半径を決めたら、次からは線分をクリックするだけで済む。

ところが `CommandKind::Tool(fn() -> Box<dyn Tool>)`（[ADR-0016](#adr-0016-コマンド表を-match-からデータに変える)）は
**引数を取らない関数ポインタ**なので、ツールを作るときに前回の値を渡せない。

### 決定

**値は `Session` が `ToolSettings` として持ち、`ToolCtx` で読ませ、
`StepOutcome::Setting(ToolSettings)` で書き戻させる。**

コマンド表の形（データ駆動）を崩さずに済むのが決め手。
`fn() -> Box<dyn Tool>` を `fn(&ToolSettings) -> Box<dyn Tool>` に変えると、
値を必要としない 20 個以上のツールにも引数が付いて回る。

**`Document` には入れない。** これは図面の内容ではなく操作の状態で、
Undo の対象でもなければ DXF に保存するものでもない。
`Document` に入れると `Command` 経由でしか変えられなくなり（[ADR-0003](#adr-0003-エンティティを変更する経路は-command-だけにする)）、
「半径を 5 にした」が Undo スタックに積まれてしまう。

**既定値は 10.0。** `ToolSettings::default()` に置いてある。

### 値の妥当性検査はツール側

0 以下と非有限値はツールが弾く（`corner_values_must_be_positive`）。
半径 0 の角丸めは何も起きず、負の半径は幾何的に意味がない。

## ADR-0026: ネイティブ形式 `.ymc` を導入し、DXF を交換専用に降格する

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #11](https://github.com/yukimasui/ymcad/issues/11)、[ADR-0014](#adr-0014-dxf-は外部クレートを使わず自前で読み書きする)、[ADR-0021](#adr-0021-dxf-は-r12-のまま据え置き往復ロスは警告で伝える)

### 背景

DXF R12 を**保存形式そのもの**として使っていた。しかし DXF は Autodesk が
**データ交換のために**定義した形式で、アプリが自分の図面を保持する器ではない。
AutoCAD 自身のネイティブ形式も DWG（バイナリ）で、DXF は交換用と役割が分かれている。

役割が合っていないことが、保存の非可逆性として表に出た。

| 落ちていたもの | 原因 |
|---|---|
| `XLINE`（作図線） | R12 に無く、長い `LINE` に化けた |
| グループ所属 | R12 に無い |
| 線種 | `CONTINUOUS` 固定で書き出していた |
| レイヤ名 | R12 向けに大文字化・空白除去していた（**日本語名が壊れる**） |

ADR-0021 では「往復ロスは警告で伝える」ことにしたが、**警告が出ること自体が
「保存形式として使うには向いていない」ことの証拠**だった。
ユーザーが自分の作業を保存するだけで図面が劣化するのは受け入れられない。

### 検討した器

| 案 | `cad-core` の依存 | wasm | SQL の利点 | 差分保存・永続 Undo |
|---|---|---|---|---|
| **A: 自前バイナリ** | **ゼロを維持** | 維持 | — | 不可 |
| B: serde + postcard | 2 つ増える | 維持 | — | 不可 |
| C: SQLite (`rusqlite`) | C 約 25 万行 | 事実上閉じる | ほぼ無い | 可能 |
| D: 現状維持（DXF） | ゼロ | 維持 | — | 不可 |

### 決定

**A を採る。** 自前バイナリのネイティブ形式 `.ymc` を作り、DXF は
インポート / エクスポート専用にする。

**C（SQLite）を却下した理由。** 「データベースを使う案はどうか」という問いが
出たので、背反を洗い出したうえで判断した。

- **永続化すべき状態が小さくて単純すぎる。** 実質 3 種
  （`Entity { geom(5種), layer, color, group }` / `Layer` / `Group`）で
  関係は各 1 本、しかも全部メモリに読む。**これはデータベースではなく
  `Vec` のシリアライズ**
- **SQL クエリの利点がほぼ幻。** 空間索引はすでに `cad-app` 側の四分木にある
  （[ADR-0011](#adr-0011-空間インデックスは-document-ではなく-cad-app-側の派生キャッシュに置く)）。
  データは全部メモリに載っているので `Vec` を走査するほうが速い。
  SQLite で空間検索するなら R\*Tree モジュールが必要で、それは今の四分木より遅い。
  **今のアプリに「SQL でないと書けないクエリ」は 1 つも無い**
- **`cad-core` の依存パッケージゼロと wasm ビューアの道を失う。**
  CI が「`cad-core` は UI 非依存」を機械検査しているのは
  `docs/ROADMAP.md` で意図的に残しているその道を守るため。
  C 25 万行を入れる対価が「ファイル形式が変わる」だけでは釣り合わない
- **「ファイル = 生きた DB」にすると [ADR-0003](#adr-0003-エンティティを変更する経路は-command-だけにする) /
  [ADR-0004](#adr-0004-エンティティストアは-slotmap-ではなく自前のアリーナにする) に直撃する。**
  Undo が DB を書くのか、`dirty` は何なのか、「名前を付けて保存」は何なのかを
  作り直す必要がある。逆に load-into-memory を保つなら、SQL エンジンを
  `SELECT *` 1 回のために抱えることになり、フラットなバイナリに対する利点が消える

**SQLite が本当に効く条件は 3 つ**で、いずれも要件になっていない。
要件化したら再検討する。

- メモリに載らない図面の部分読み込み
- セッションを超えて残る Undo 履歴
- 形式を壊さずテーブルを足せる拡張性（唯一まともな論拠だが、今回は動機に含めない）

**B（serde）を採らなかったのは、書く量の差が依存 2 つに見合わなかったから。**
永続化する型が少なく、手書きでも約 200 行で済んだ。将来エンティティの種類が
増えて手書きが辛くなったら移る余地はある（形式は変えずに実装だけ差し替えられる）。

### 今回やらないこと

動機として選ばれなかったので意図的に範囲外にした。

- **差分保存** — 速度は動機ではない。全体を書き切る
- **移行フレームワーク** — バージョン番号だけ持ち、未知のバージョンは明示的に拒否する。
  中途半端に読んで壊れた図面を見せるより、開けないと言うほうがよい
- **Undo 履歴の永続化**

### `EntityId` を永続化しない

当初は `slot_index` / `generation` を書いて `EntityId` を保つ案だったが撤回した。

- `entity/store.rs` のモジュールドキュメントが「スロットの回収は Undo 履歴を
  捨てるとき（**新規作成・ファイル読み込み**）にのみ行う」と明示している。
  疎なスロットを再現すると、この方針に反して穴が永久に残る
- 空きスロットが世代番号を持たない設計は「`insert` はスロットを再利用しない」ことに
  依存している。ID 値を外から与えるとこの前提の外に出る
- **Undo 履歴を永続化しないので、読み込み後に古い `EntityId` を参照する者はいない**

意味を持つのは ID の値ではなく**走査順（= スロット昇順 = 作成順 = 描画順）**で、
これはファイル順に順次挿入すれば正確に保たれる。CAD では後に描いたものが上に来るので、
順序は見た目を決める。`entity_order_is_preserved` で固定した。

### レイヤ・グループは ID 値ではなくファイル内の添字で参照する

読み込み側が「ファイル添字 → 実際の ID」の対応表を作って解決する。
ID の再現に依存しないので、将来 ID の割り当て方が変わっても壊れない。

### 角度はラジアンで書く

DXF ライタは度へ変換している。これは `docs/PROGRESS.md` の「既知の落とし穴」に
挙がっている π/180 ずれの温床なので、ネイティブ形式では内部表現のまま書いて
変換を 1 つ減らした。

### 読み込みも `Command` 経由で組み立てる

`Document` のフィールドは private で、変更経路は `Command` だけ（ADR-0003）。
`dxf/read.rs` の `build_document` がすでにその形なので、**読み込みを例外にしない**。

### 実装中に見つけた非可逆性

**作図線の方向ベクトルを `Xline::new` で復元すると 1 ULP ずれる。**
中の `normalized()` が除算をやり直すため、既に正規化済みの値が
`0.7071067811865475` → `0.7071067811865476` に動く。
往復が非可逆になり形式の存在理由に反するので、値はそのまま使い
**「単位ベクトルであること」を検査する**形にした。
`Xline::new` は非ゼロなら何でも受け取って正規化してしまうので、
壊れたファイルに対する検査としてはこちらのほうが強い。

`Document::clear_history()` の呼び忘れも同様に、書いたテストが見つけた。
忘れると読み込みに使ったコマンド（`AddLayer` 等）が Undo できてしまう。

### 形式は拡張子だけで決める

`.dxf` かどうかだけを見る（大文字小文字は無視）。「前回の形式を覚える」等の
隠れた状態を作ると、同じ操作が状況によって別の形式で保存される。
`.dxf` で開いたファイルの上書き保存は **`.dxf` のまま**にする。
勝手に別の形式へ移すほうが驚きが大きく、非可逆であることは警告で伝わり続ける。

### 残るリスク

**DXF の相互運用は LibreCAD での閲覧しか確認できていない。**
今回 DXF の書き出しロジック自体は変えていないが、交換専用になったことで
DXF の重要度が「唯一の保存形式」から「他の CAD へ渡す手段」に変わった。
他の CAD での読み込み確認は引き続き未検証（`docs/PROGRESS.md`）。

## ADR-0027: 保存は一時ファイル + `rename` でアトミックに行う

- **状態**: 確定
- **日付**: 2026-08-12
- **関連**: [Issue #11](https://github.com/yukimasui/ymcad/issues/11)

### 背景

保存が `std::fs::write` だった。これは**既存ファイルを切り詰めてから書く**ので、
書き込み中にクラッシュ・電源断・ディスク満杯が起きると
**保存前の正常なファイルまで失われる**。図面は失うと作り直しになる。

形式の議論とは無関係な単独のバグだったので、ネイティブ形式の導入より先に直した。

### 決定

`atomic_write::write_atomic` を作り、両方の書き出しモジュールから使う。
**3 手順の順序それぞれに理由がある。**

1. **保存先と同じディレクトリに**一時ファイルを作る
2. 書いて `sync_all()`
3. `rename` で置き換える

- **一時ファイルを `std::env::temp_dir()` に作ってはいけない。**
  別のファイルシステムだと `rename` が「コピー + 削除」に退化してアトミック性を失う
- **`sync_all()` を省いてもいけない。** `rename` 自体はアトミックだが、
  中身がまだページキャッシュにあるだけの状態で電源断が起きると
  **中身が空のファイルが正しい名前で残る**。名前だけ正しくて中身が無いのは、
  書き換えに失敗するより悪い

守る性質は「**`path` は常に、書き終わった状態か元の状態のどちらか**」だけ。
書きかけの中間状態が `path` から見えることはない。

### 一時ファイル名

`.<元の名前>.tmp-<pid>-<連番>` にする。

- **連番が必要。** プロセス ID だけだと同じプロセスからの 2 回目の保存で衝突する
- **名前を作り直す retry が必要。** クラッシュで取り残された一時ファイルと
  プロセス ID が偶然一致した場合、これが無いと隠しファイルを手で消すまで
  保存が一切できなくなる
- 元の名前を含めておくと、万一取り残されたときに何の一時ファイルか分かる
- 先頭の `.` で隠しファイルにしてファイル一覧を汚さない

### 何を保証しないか

**アプリのクラッシュで「未保存の変更」が失われることは、これでは防げない。**
守れるのは「保存済みのファイルが壊れないこと」だけ。
未保存の変更の保護（自動保存とクラッシュ復帰）は別の課題として
`docs/PROGRESS.md` に残してある。

## ADR-0028: ブロックを「パラメトリックなコンポーネント」として再定義する

- **状態**: 確定（段階 1 完了、段階 2・3 は未着手）
- **日付**: 2026-08-13
- **関連**: [Issue #13](https://github.com/yukimasui/ymcad/issues/13)

### 背景

ブロック機能の依頼を受けたが、**「ブロックは古いので現代的に再定義してほしい」**
という要求付きだった。何が本当に古いのかを整理したうえで設計した。

### 前提 — ブロックの「核」は古くない

**定義 + インスタンス（インスタンシング）という核は古くない。**
むしろ現代のツールが揃って同じ形に収束している。

| ツール | 呼び名 |
|---|---|
| Figma | Component / Instance |
| ゲームエンジン | Prefab |
| SVG | `<symbol>` + `<use>` |
| USD（映像業界標準） | Reference |
| React | Component |

**ここを捨てたら退化になる。** 古いのは 1990〜2000 年代の実装の選択の部分。

### 本当に古い部分と、その置き換え

| 古い部分 | 何が問題か | 答え |
|---|---|---|
| **ダイナミックブロックの「アクション」** | **GUI によるマクロ記録**。作るのが難しく、デバッグがもっと難しく、読めない。`幅 = 高さ×2+10` のような合成ができない | **型付きパラメータ + テキストの式**（段階 2） |
| 属性（ATTDEF）が文字列べったり | 型も検証もデフォルト継承も無い | **型付きパラメータに統合**（段階 2） |
| インスタンス個別の上書きが無い | 「定義を編集（全部変わる）」か「EXPLODE（リンクが永久に切れる）」の二択 | **個別上書き + リセット**（段階 2） |
| 編集がモーダル（BEDIT） | 図面から出て別世界で編集する | **インプレース編集**（段階 3） |
| X/Y 別倍率 | 円が円でなくなる | **一様倍率のみ**（段階 1 で確定） |
| `BLOCK` が選択を消す | 作った直後に画面から図形が消える | **その場でインスタンスに置き換える**（段階 1 で確定） |

**主眼はアクションの置き換え。** ここが唯一「古い」とはっきり言える部分。

### 採らなかった選択肢

**幾何拘束ソルバ（Fusion / SolidWorks のスケッチ拘束）。**
いちばん「モダン」に聞こえるが、**ブロックとは直交した別問題**。
未知数と拘束式の非線形連立方程式、ニュートン法 / 最小二乗による反復解法、
ヤコビアンのランクからの過小 / 過剰拘束の判定、初期値依存で解が飛ぶ問題の対策、
拘束の可視化 UI — 数ヶ月規模で、しかも数値的頑健性が本質的に難しい。
**抱き合わせたら両方未完成で終わる。** `docs/ROADMAP.md` に独立項目として残した。

**ノードベースのビジュアルパラメータエディタ。**
Grasshopper / Blender 風で現代的に見えるが、
**ダイナミックブロックのアクションと同じ罠**（GUI でプログラミングさせる形）。
この規模ではテキストの式のほうが厳密に優れている
（読める / 合成できる / `git diff` で意味が読める / テストできる）。

**`Geometry` を式化した並行型階層（`ParamLine` / `ParamCircle` …）。**
素直に見えるが、**定義の中で既存の作図・編集ツールが使えなくなる。**
LINE / CIRCLE / ARC / TRIM / EXTEND / FILLET / CHAMFER / レイヤ機能を
全部作り直すことになる。→ ADR-0029 の「実エンティティ + 疎な束縛」を採る。

**X/Y 別倍率（AutoCAD 準拠）。**
`Circle` → `Ellipse`、`Arc` → `EllipticArc` が必要になり、描画・スナップ・
交点計算・選択・DXF の全経路に新しい幾何型を通すことになる
（しかも DXF R12 に `ELLIPSE` は無い）。
**一様倍率なら既存の 5 変種が変換で閉じる。**
そもそも X/Y 別倍率は円を壊す失敗機能なので、捨てるべき違いと判断した。

### 制約 — 文字要素が無いので「属性」は範囲外

文字要素（TEXT）が未実装（`docs/ROADMAP.md` で非スコープ）なので、
古典的な「属性」= インスタンスごとの可視テキスト（ドア記号のタグ、図面枠の
タイトル、集計表）は**表示すらできない**。今回は幾何のパラメトリ化に絞る。
パラメータの仕組みは先に作るので、文字要素が入ったら表示を後から載せられる。

### 反転フラグ（実装中に見つけた）

**鏡像が (基点・回転・正の倍率) では表現できなかった。**
2 次元の相似変換は「平行移動 ∘ 回転 ∘ **反射(任意)** ∘ 一様倍率」に分解されるので、
反射には独立した情報が必要。`Placement` に `flipped` を足した。

AutoCAD は負の倍率で表すが、それは「倍率」と「反転」を 1 つの数に詰めるので、
`SCALE` の入力検証（0 と負値を拒否）と衝突する。**別のフラグに分けるほうが素直。**

導出した合成規則は **回転 = 2θ − φ、反転を反転**。
これは `Arc` の鏡像と同じ形で、偶然ではなく「反射が向きを逆転させる」同じ事情
（[ADR-0020](#adr-0020-円弧の鏡像は開始角と終了角を入れ替える)）。

**負の一様倍率は反射ではなく 180 度回転**（2 次元では行列式が +1）。
反転フラグを立てると別の図形になる。ここも間違えかけた。

**反転は回転より先に適用する。** 反射と回転は交換しない。
一様倍率は回転・反転のどちらとも交換するので、そちらの順序は問わない。
`flipping_happens_before_rotation` で固定した。

### 妥当性はコマンド境界で保証する

入れ子の循環検出（段階 2 では式の型検査とパラメータ間の循環検出も）は
**すべてコマンドの `execute` で行う**。`Document` に入っている定義は常に妥当なので
**`resolve` が infallible** になり、`bbox()` が `Result` にならない。
`Xline::new` が零ベクトルを弾くのと同じ流儀（境界で検証、内側は不変条件を信じる）。

深さ上限（`MAX_NESTING_DEPTH`）は**最後の砦**であって循環検出の代わりではない。
深さで打ち切ると図形が黙って消える。

### 使用中の定義は削除できない

参照だけ残った状態を作ると、解決が空を返して**図形が黙って消える**。
`DeleteDefinition` は図面直下と他の定義の両方から参照を探して拒否する。

### `EXPLODE` は中身のレイヤに戻す

インスタンス側のレイヤを被せると、分解しただけで図面の色分けが崩れる。
AutoCAD もブロックを分解すると中身のレイヤに戻る。
そのため `resolve` をエンティティ単位（`resolve_entities`）に作り直した。
入れ子では内側の属性が勝つ。

## ADR-0029: コンポーネントの定義は「実エンティティ + 疎な式の束縛」にする

- **状態**: 確定
- **日付**: 2026-08-13
- **関連**: [Issue #13](https://github.com/yukimasui/ymcad/issues/13)、ADR-0028

### 背景

パラメトリックにするには、幾何の座標を式で駆動する必要がある。
素直な案は `Geometry` を式化した並行型階層を作ること。

```rust
enum ParamGeometry {
    Line { ax: Expr, ay: Expr, bx: Expr, by: Expr },
    Circle { cx: Expr, cy: Expr, r: Expr },
    // …
}
```

### 決定

**採らない。** 定義の中身は**ふつうの [`Entity`]** にして、式は
「どの座標にどの式を束縛するか」という**疎な上書き**として別に持つ。

```rust
pub struct Definition {
    pub name: String,
    pub origin: Point2,
    pub entities: Vec<Entity>,   // ← ふつうの Entity。式は入っていない
    // 段階 2 で追加:
    // pub params: Vec<ParamDecl>,
    // pub bindings: Vec<Binding>,  // ← 疎な上書き。式を持つ座標だけ
}
```

理由:

- **定義の中身が本物のエンティティなので、既存の作図・編集ツールがそのまま使える。**
  並行型階層にすると LINE / CIRCLE / ARC / TRIM / EXTEND / FILLET / CHAMFER /
  レイヤ機能を全部作り直すことになる
- **パラメトリックが座標単位で任意（additive）。** 束縛が無ければ
  クラシックなブロックに degrade するので、段階 1 と段階 2 が自然に繋がる
  （実際、段階 1 は束縛ゼロのまま動いている）
- `Geometry` 側の変更が `Instance` 変種の追加だけで済む

### 代償

束縛は「エンティティの添字 + どのスカラーか」で座標を指す。
**定義の中身を編集して要素の順序が変わると、束縛の指す先がずれる。**
段階 2 で束縛を入れるときに、`SetDefinitionContents` が束縛を検証・
再マップする責務を持つ必要がある。並行型階層ならこの問題は無い。

要素数が増えて添字の管理が破綻したら、エンティティ側に安定 ID を持たせる
（`Definition` の中で完結するローカル ID）ことで解決できる。形式の変更にはなるが、
`Geometry` の構造は変えなくて済む。

## ADR-0030: `Geometry` の 3 メソッドに定義テーブルを引数で渡す

- **状態**: 確定
- **日付**: 2026-08-13
- **関連**: [Issue #13](https://github.com/yukimasui/ymcad/issues/13)、[ADR-0011](#adr-0011-空間インデックスは-document-ではなく-cad-app-側の派生キャッシュに置く)

### 背景

`Geometry::Instance` は中身を持たず、定義を ID で参照する。
そのため以下の 3 つは定義テーブルを引かないと答えが出ない。

| メソッド | なぜ必要か |
|---|---|
| `bbox()` | 中身の範囲が必要 |
| `dist_to()` | 中身との距離が必要 |
| `is_bounded()` | 中身に作図線があれば無限になる |

変換系（`translated` / `rotated` / `scaled` / `mirrored` / `stretched`）は
`placement` に合成するだけなので**定義を必要としない**。

### 検討した案

| 案 | 内容 |
|---|---|
| A | 3 メソッドに `&DefinitionTable` を渡す |
| B | インスタンスが自分の bbox をキャッシュして持つ |
| C | `Aabb::EMPTY` を返して、必要な場所だけ別経路で計算する |

### 決定

**A を採る。**

**C は XLINE のときと同じ罠。** `EMPTY` を返すと `render` のカリングと
矩形選択から落ちて、**「描画されない・選択できない」図形**になる
（[ADR-0021](#adr-0021-dxf-は-r12-のまま据え置き往復ロスは警告で伝える) の作図線で
一度踏んでいる）。しかも症状が「たまに消える」なので原因を追いにくい。

**B は同期の辻褄合わせが必要になる。** 定義を編集したら全インスタンスの
キャッシュを更新しなければならず、Undo をまたぐと片方だけ直し損ねる。
これは [ADR-0022](#adr-0022-グループの所属はエンティティ側だけが持つ) で
グループのメンバー一覧を却下したのと同じ理由。

**A なら依存が隠れず、コンパイラが全呼び出し元を見つける。**
実際 13 ファイルを指摘してくれた（`snap/detect.rs` の平坦化、
`selection.rs` の交差判定、`render.rs` のカリング、`native` / `dxf` の書き出し、
`EntityStore::bbox`）。1 箇所でも漏らせば静かに壊れていた。

### 重い計算は `cad-app` の派生キャッシュに

解決はパラメータの評価を含むので、毎フレーム毎インスタンスやると重い。
`crates/cad-app/src/resolved.rs` に `Document::revision()` をキーにした
キャッシュを置く（ADR-0011 と同じ仕組み、`snap.rs` の `SpatialIndex` が雛形）。

**「定義を編集すると全インスタンスが追従する」はこれで実現している。**
版が進んでキャッシュが捨てられるだけで、**インスタンス側を書き換える処理は
1 行も無い。**

更新（`refresh`）と読み取り（`get`）は分けてある。描画ループの中で `&mut` を
取ると `Document` の借用と衝突し、毎フレーム複製する羽目になる。

## ADR-0031: パラメータは GUI のアクションではなくテキストの式で書く

- **状態**: 確定
- **日付**: 2026-08-13
- **関連**: [Issue #13](https://github.com/yukimasui/ymcad/issues/13)（段階 2）、ADR-0028

### 背景

ADR-0028 で「ダイナミックブロックのアクションが古い部分」と結論したので、
その置き換えを決める必要があった。

AutoCAD のアクション（ストレッチ・配列・反転・可視性）は
**GUI でパラメータ図形とアクション図形を貼り付けて**作る。実質マクロ記録による
プログラミングで、

- 作るのが難しく、デバッグがもっと難しい
- 読めない（何をするブロックか、開いて突いてみるまで分からない）
- **合成できない**（`幅 = 高さ × 2 + 10` が書けない）

### 決定

**テキストの式**にする。ノードベースのビジュアルエディタは採らない。

| | テキストの式 | ノードエディタ |
|---|---|---|
| 読める | ✅ 式を見れば分かる | ❌ 辿らないと分からない |
| 合成できる | ✅ | △ 配線が増える |
| `git diff` で意味が読める | ✅ | ❌ |
| テストできる | ✅ 文字列 → 期待値 | ❌ |
| 実装量 | 約 600 行 | 大幅に増える |

ノードエディタは現代的に見えるが、**GUI でプログラミングさせる点で
アクションと同じ罠**。この規模ではテキストのほうが厳密に優れている。

### 型は 3 つだけ

`Number` / `Bool` / `Choice`。文字列型は入れない
（文字要素が無いので表示できず、入れても使い道が無い）。

**`Choice` は候補に無い値を拒否する。** 型が合っていても候補外なら不正。
緩めるとパネルに出せない値がファイルに入る。

### 角度は度

式の中の角度は度で、ラジアンが要るときは `rad()` で明示的に変換する。
座標入力の `@100<45` と同じ約束で、`docs/PROGRESS.md` の「既知の落とし穴」に
挙がっている π/180 のずれを、**変換を明示させる**ことで避ける。

束縛のスロット（円弧の開始角、作図線の角度、インスタンスの回転）も度で受け取り、
適用時にラジアンへ直す。**内部表現がラジアンであることを式の書き手に見せない。**

### 識別子に日本語を許す

レイヤ名・グループ名・コンポーネント名が日本語なのと揃える。
Unicode の細かい分類（`XID_Start` 等）を使うと `unicode-ident` の依存が要るので、
**「記号でも空白でもない非 ASCII」**という単純な規則にした
（`cad-core` の依存パッケージゼロを守る / ADR-0026）。

### `NaN` と無限大を作らせない

0 除算・`sqrt(-1)`・オーバーフローは**エラーで止める**。
黙って `NaN` にすると、その座標が図形へ流れて**画面から図形が消え、
原因が分からなくなる**。

**`tan(90)` は `is_finite` では捕まらない。** 90 度をラジアンにしても厳密に
π/2 にならないので、結果は無限大ではなく `1.6e16` という巨大な有限値になる。
`cos` が 0 かどうかで判定する。テストが見つけた。

**型の違う等値比較（`開く == 1`）は `false` ではなくエラー。**
`false` にすると書き間違いが静かに通る。

**`if` の選ばれなかった側は評価しない。**
`if 幅 > 0 then 1/幅 else 0` が 幅 = 0 でエラーにならないために必要。

### 壊れ方を選ぶ

評価に失敗した束縛は**その座標だけ定義のまま**にする。
図形ごと消すと「パラメータを変えたら図形が消えた」という最悪の壊れ方になる。

### 妥当性はコマンド境界で保証する

字句解析・構文解析・型検査・循環検出はすべて `Command` の `execute` で行い、
`Definition` は**解析済みの `Expr` 木**を持つ。文字列は持たない。

そのおかげで評価が「値の種類の取り違え」で失敗しなくなり、
図形の解決が実行時エラーを持ち回らずに済む。
`Xline::new` が零ベクトルを弾くのと同じ流儀。

**永続化も木のまま**（前置記法）。文字列で持つと読み込みのたびに
解析と型検査をやり直すことになり、この約束が保てない。

## ADR-0032: パラメータの操作はパネルへ寄せ、文字入力は名前だけにする

- **状態**: 確定
- **日付**: 2026-08-13
- **関連**: [Issue #13](https://github.com/yukimasui/ymcad/issues/13)、[Issue #15](https://github.com/yukimasui/ymcad/issues/15)、[ADR-0012](#adr-0012-レイヤパネルは-document-を変更せずコマンドを返す)

### 背景

段階 2 の実装当初、パラメータの操作をすべてコマンドラインに載せた
（`PARAM` / `BIND` / `PSET`）。動作確認でユーザーから

> 日本語入力に難がありすぎてものすごく使いづらい。
> ターミナルウィンドウみたいにパラメータ打つのではなくてカーソルで選択みたいに出来ないか

との指摘を受けた。**もっともな指摘だった。**
数値ひとつ変えるのに IME の確定を挟むのは、CAD の操作として重すぎる。

### 決定

**日常操作は打たずに済ませる。** `COMPONENTS`（`CS`）でパネルを開く。

| 型 | 操作 |
|---|---|
| 数値 | ドラッグ（範囲があればスライダ） |
| 真偽 | チェックボックス |
| 選択 | ドロップダウン |
| 配置 | 一覧から「配置」ボタン |
| リセット | 「戻す」ボタン |

**文字を打つのは名前を付けるときだけ**という方針にした。

上書き中のパラメータは名前を太字にする。何が既定で何を変えたかが一目で分かる。

### 段階 3 を前倒しした

パラメータパネルは当初「段階 3（インプレース編集と一緒）」に置いていたが、
**段階 2 が使えないままになる**ので前倒しした。
機能が動くことと使えることは別で、後者が欠けていれば実質未完成。

### 残り

`PARAM` と `BIND` はコマンドラインのまま。特に `BIND` は「要素番号 → スロット名」を
打たせていて一番きつい。**定義の中身を画面に出してクリックで指す**のが本来の形で、
段階 3 のインプレース編集と仕組みが共通なので一緒にやる（Issue #15）。

### パネルは `Document` を変更しない

コマンドを返すだけで、適用は呼び出し側（ADR-0012、レイヤパネルと同じ）。
「配置」ボタンだけはコマンドで表せないので `PanelRequest` として返し、
`Session::start_tool_directly` が**コマンドラインから起動したときと同じ経路**
（`begin_tool`）を通す。

## ADR-0033: インプレース編集は「中身を図面へ出して、印を付けずに追う」

- **状態**: 確定
- **日付**: 2026-08-13
- **関連**: [Issue #13](https://github.com/yukimasui/ymcad/issues/13)（段階 3）、[Issue #15](https://github.com/yukimasui/ymcad/issues/15)、ADR-0029

### 背景

定義の中身を編集する手段が `REDEFINE`（中身を選び直して丸ごと差し替え）しか
無かった。既存の中身を少し直したいだけでも、描き直して選び直す必要があった。

### 決定 1: 中身を実エンティティとして図面へ出す

編集に入るとインスタンスを外し、**定義の中身を実エンティティとして図面へ置く**。
こうすると LINE / TRIM / MOVE といった既存のツールがそのまま使える。
専用の編集モードを作るより経路が 1 本で済む。

置く位置は元のインスタンスの配置なので**画面上の見た目が変わらない**。
「編集に入った瞬間に図形が飛ぶ」ことがない。

**束縛を評価した形ではなく、定義そのままの形を置く。**
評価後の形を置いて書き戻すと、束縛が「いまの値」で固定されてしまう。

### 決定 2: モーダルにしない

AutoCAD の `BEDIT` は別世界へ行くが、こちらは**編集の対象外を淡く描くだけ**。
周りの図形は見えたままで、スナップも効く。位置関係を保ったまま直せる。

消してしまうと位置関係が分からなくなるので、**見えるが目立たない**程度
（`DIMMED_ALPHA = 0.25`）にする。

### 決定 3: 編集中の要素を印なしで追う

規則は 2 つだけ。

1. 入ったときに置かれた要素（消されたものは除く）
2. 入ったあとに作られた要素

2 が判定できるのは、`EntityStore` が**スロット番号を文書の生存期間中に
再利用しない**（単調増加）ため（`entity/store.rs` の方針）。
入った時点の最大スロット番号を覚えておけば、それより大きいものは
すべて「あとから作られた」と分かる。

**印を持たない利点は Undo に出る。** 削除を取り消すと**元の ID のまま**戻るので
（世代つきアリーナ / ADR-0004）、判定が自動的に元へ戻る。
印を持つと、Undo のたびに印の辻褄を合わせる必要が出る
（[ADR-0022](#adr-0022-グループの所属はエンティティ側だけが持つ) で
グループのメンバー一覧を却下したのと同じ話）。

**編集中に描いたものはすべて定義に入る。** AutoCAD の `BEDIT` と同じで、
「編集中の図面」に描いているのだから当然という考え方。

### 決定 4: 束縛は編集セッションが対応表で保つ

ADR-0029 で「インプレース編集では定義内で安定な ID が要る」と書いたが、
**定義の形は変えずに解けた。**

入ったときに「置いた要素 → 元の定義での添字」を記録し、出るときに渡す。

- 順序が入れ替われば添字を付け替える
- 消された要素の束縛は捨てる（指す先が無いので残せない）
- 図形の種類が変わっていたら、その束縛は捨てる

**対応表は編集セッションの間だけ持つ。** 永続化する形を増やさずに済んだ。

### 決定 5: 逆変換は `place` と対で書く

書き戻しには `place` の逆（`unplace`）が要る。
**両方の doc コメントに「対で読むこと」と書いた。**
片方だけ直すと、編集して書き戻すたびに図形が少しずつずれる
（しかも 1 回では気づきにくい）。

恒等になることを、反転・回転・倍率・基点を混ぜた組み合わせで固定した。
わざと壊して落ちることも確認済み（回転の符号 / 反転の戻し忘れ /
反転と回転の順序）。一様倍率と回転は可換なので、その順序を入れ替えても
落ちないのは正しい。

### 決定 6: `BIND` はクリックで指す（Issue #15）

編集中は定義の中身が実エンティティとしてあるので、**クリックで座標を指せる**。

```
BI → 動かしたい点をクリック → X / Y → パラメータの番号
```

- つまみ（端点・中心・半径・角度）から**クリック位置に最も近いもの**を選ぶ
- 軸は `X` / `Y`、パラメータは番号。**すべて ASCII なので日本語入力を通さない**
- 式を打ちたいときはそのまま打てる

編集中でなければ、従来どおり定義名から辿る道が残る。

**編集中に描いた図形はまだ束縛できない。** 定義に入っていないので指す添字が
決まらない。`ENDCOMP` で確定してからになる。

## ADR-0034: 動的入力（段階 A）は本物の `TextEdit` をカーソル横へ動かす

- **状態**: 確定（IME の実機確認はユーザー待ち）
- **日付**: 2026-10-05
- **関連**: [Issue #20](https://github.com/yukimasui/ymcad/issues/20)（段階 A）、[ADR-0001](#adr-0001-ime-検証結果-phase-0)、[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3)、[ADR-0016](#adr-0016-コマンド表を-match-からデータに変える)

### 背景

コマンド入力は画面下のコマンドラインだけで、プロンプト・入力・候補を見るたびに
視線がカーソルから画面下へ往復していた。AutoCAD の Dynamic Input に倣い、
カーソル横にプロンプト・入力欄・候補・エラーを出す。

### 決定 1: カーソル横へ移すのは本物の `TextEdit`

入力のバッファは従来の 1 つのまま、**`TextEdit` を描く場所だけを切り替える**
（画面下 / カーソル横の `egui::Area`）。`TextEdit` の ID を固定して、
切り替えてもフォーカスとキャレットが引き継がれるようにした。

**採らなかった案: `TextEdit` は画面下に置いたまま、カーソル横には中身を写した絵だけを描く。**
日本語入力の扱いは安全だが、IME の候補ウィンドウは**入力欄に付いて出る**
（ADR-0001 調査 3）ので、画面下の左端に出たままになる。変換のたびに視線が往復し、
解きたかった課題が残る。本物を動かす案が IME の実機確認で破綻した場合の退避先とする。

### 決定 2: 何もしていないときは不透明度 0 で描き続ける

ツール非実行・入力が空・変換中でない・エラー表示期間外のときは、カーソル横に何も見せない。
ただし**入力欄は毎フレーム描く**。見た目だけを `Ui::multiply_opacity(0.0)` で消す。

- **描くのをやめる案は採らない。** egui はそのフレームに描かれなかったウィジェットの
  フォーカスを外す（`Focus::end_pass`）。最初の 1 文字が入力欄に届かなくなる
- **`Ui::set_invisible` / `UiBuilder::invisible` で消す案も採らない。**
  `TextEdit` は `ui.is_rect_visible()` が真のときしか `PlatformOutput::ime` を出さない
  （egui 0.36.2 `text_edit/builder.rs`）。不可視にすると IME に入力欄の位置が伝わらず、
  変換が始まらなくなる。不透明度は `Painter::is_visible` に影響しないので IME は生きる
- 文字を打った瞬間・変換が始まった瞬間に、そのフレームから枠ごと見えるようになる

`Area` は `interactable(false)` にしてクリックを素通しする。egui の当たり判定は
前フレームの矩形を使うので、マウスを速く動かすと入力欄の上に乗り、
キャンバスのクリック（点の指定）やホバー（スナップ）を奪いうるため。
キー入力はフォーカスで届くので影響しない。

### 決定 3: 位置

- 基準はキャンバス上のマウス位置。キャンバスの外（パネル・ステータスバー）に出たら
  最後の位置に留める（初回はキャンバス中央）
- カーソルの右下へ 20px ずらす。スナップの解放半径 16px + マーカーの半辺 4.5px より
  外側なので、**スナップマーカーとカーソル十字を覆わない**
- 右端・下端では左側・上側へ回り込み、**キャンバス（ビューポート）の矩形内に収める**。
  入り切らないほど大きくても左上より外には出さない（読み始めが見えるように）
- 大きさは前フレームの `Area` の実寸を使う（このフレームの大きさは描き終わるまで分からない）
- 背景は半透明（不透明度 0.8）。下の図形が透けて見える

配置・表示判定・エラーの表示期限は egui に依存しない純粋関数（`cmdline/dynamic.rs`）にして
単体テストで固定した。見た目は `ui_snapshot.rs` で PNG に撮って確認する。

### 決定 4: 変換中は位置を固定する

Preedit が非空の間は、変換が始まった時点の位置に留める。確定・取り消しで追従を再開する。
毎フレーム追従させると、入力欄に付いて出る候補ウィンドウがマウスの動きで跳ねる。
`[変換中]` の表示と ADR-0002 の制約（変換中はバッファを解釈しない・キーを奪わない）は
そのまま維持する。

### 決定 5: 座標の解釈は変えない

何も付けなければ絶対、`@` で相対。コマンドラインと同じ規則（`Session::interpret` は無変更）。

**採らなかった案: AutoCAD 互換の「2 点目以降は相対」を既定にする。**
世間の不満で最大の事故原因で、コマンドラインと規則が分かれる。ユーザー判断で不採用（Issue #20）。

### 決定 6: オンの間、画面下は履歴 + 現在のプロンプトにする

入力欄と候補はカーソル横だけに出し、画面下は履歴と読み取り専用のプロンプト 1 行にする。

- **入力欄を両方に出す案は採らない。** バッファが 1 つでも `TextEdit` を 2 つ描くと
  フォーカスと IME の出力先が 2 つになり、どちらに候補ウィンドウが付くか定まらない
- **プロンプトは下にも残す。** カーソル横を見落としても履歴の続きとして読めるようにする。
  案内やエラーを見逃す・履歴が追えないのは世間の不満の 1 つ
- エラーはカーソル横に 3 秒出し、履歴には従来どおり必ず残す。次の確定操作
  （`Enter` / `Esc`）でカーソル横からは下げる

### 決定 7: オン/オフはフレームの最初に確定させる

F12 はキャンバスの処理中、ステータスバーの `DYN` のクリックはステータスバーの描画中に起きる。
フレームの途中で切り替わったまま使うと、画面下とカーソル横の両方に入力欄を描いて
確定を二重に処理しうる（または両方とも描かない）。`begin_frame` で状態を写し、
描画と確定はそれに従う。切り替えは次のフレームから効く。

### 構造

`CommandLine::show` を 3 段に分けた。

1. `begin_frame` … IME の追跡とキーの消費（`TextEdit` を描く前でないと Tab や ↑↓ を取られる）
2. `show_bottom` / `show_floating` … 描画。カーソル横はキャンバスの矩形とマウス位置が要るので
   キャンバスの後に描く
3. `finish_frame` … 確定操作の決定。入力欄を描いた後に決める
   （同じフレームで打たれた文字が入ってから確定させる。分ける前と同じ順序）

### 段階 B へ

寸法入力（長さ・角度の欄、Tab での固定、直接距離入力）は段階 B。欄の意味がツールごとに
異なるので、ツールが参加を宣言する形にする。詳細設計は段階 B の着手時に別 ADR で書く。

### 追記: 変換が始まった瞬間に入力欄を動かさない（PR #21 のレビュー）

当初は `[変換中]` を入力欄の**前**に置き、何もしていないときは入力欄だけを描いていた。
そのため変換が始まったフレームで、入力欄が `[変換中]` の幅だけ右へ、何もしていない状態からだと
枠の余白とプロンプト行のぶん右下へずれた（実測 +47px / (+54, +20)px）。Area は固定していても、
入力欄に付いて出る候補ウィンドウが最初の 1 打鍵で跳ねる。

- `[変換中]` は入力欄の**後ろ**に置く
- 何もしていないときも、**枠・プロンプト行・入力欄を見せるときと同じ並びで描き**、
  不透明度 0 で隠す。入力欄より下（候補・エラー）は入力欄の位置に影響しないので出し分けてよい

「何もしていない → 変換開始」「コマンド実行中 → 変換開始」の両方で入力欄の矩形が
変わらないことを、GPU なしの `egui_kittest` のテスト（`app/behavior_tests.rs`）で固定した。

同じレビューを受けて、キャンバスより後で確定を処理したフレームでは `request_repaint()` を呼ぶ
（確定の結果は次のフレームで描かれるので、そのフレームを待たせない）。
また、`Esc` で閉じた候補が次のフレームで作り直されて再び出ていた既存の不具合を直した
（閉じたときの入力を覚え、入力が変わるまで出さない）。これが無いと `Esc` の 2 回目も
「候補を閉じる」になり、候補が出る入力のままでは中断できなかった。

### 追記: 右端寄りでも `[変換中]` で Area を広げない（PR #21 の再レビュー）

`[変換中]` を変換が始まってから足すと、Area がその幅だけ広がる。Area の右端が
キャンバスの右端に近いと、`constrain_to` が次のフレームで Area を左へ押し戻し、
入力欄が跳ねた（実測 -21〜-46px）。**バッジの幅は常に確保し、変換していないときは
`add_visible(false, …)` で見えなくするだけ**にした。配置の計算にバッジの幅を足す案は、
Area の実寸が前フレームの値なので、広がる前と後で 2 重に数えるフレームが出て結局 1 回動く。

## ADR-0035: コマンドラインがキーを扱うのは、フォーカスが自分か無いときだけ

- **状態**: 確定
- **日付**: 2026-10-05
- **関連**: [Issue #22](https://github.com/yukimasui/ymcad/issues/22)、[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3)、[ADR-0016](#adr-0016-コマンド表を-match-からデータに変える)、[ADR-0032](#adr-0032-パラメータの操作はパネルへ寄せ文字入力は名前だけにする)

### 背景

「キー入力は常にコマンドラインへ流れる」ために、コマンドラインはフレームの最初に
`Enter` / `Space` / `Esc` / `Tab` / `↑↓` を `consume_key` で奪っている。これが 2 つの問題を起こしていた。

1. **Tab 補完の直後にフォーカスが外れる。** `TextEdit` の既定の `event_filter` は
   `tab = false` で、egui はフレームの最初（`Focus::begin_pass`）に Tab を
   「次の部品へフォーカスを移す」として処理する。こちらが奪うより先なので、
   `L` → `Tab` → `Z` の `Z` が入力欄に入らなかった
2. **パネルの入力欄のキーを奪う。** egui_kittest で実測したところ、LINE 実行中に
   レイヤ名を編集すると、`Space` で LINE が終わり、`Enter` で直前のコマンドが再実行され、
   `Esc` でコマンドが中断された。誰がフォーカスを持っているかを見ずに奪っていたため

### 決定

- **コマンドラインの入力欄は Tab・矢印・Esc を自分で受け取る**（`event_filter` で
  `tab` / `horizontal_arrows` / `vertical_arrows` / `escape` を真にする）。
  候補が無いときの Tab も入力欄から出ていかない。打ち間違いで入力先が黙って変わると、
  「キー入力は常にコマンドラインへ」という前提が崩れて気づきにくい
- Tab 補完はバッファを外から書き換えるので、`TextEdit` のキャレットは補完前の位置に残る。
  補完した次の描画で `TextEditState` のキャレットを末尾へ動かす
- **キーを扱うのは、フォーカスが入力欄にあるか、どこにも無いときだけ。**
  前のフレームのフォーカスも見る。パネルの入力欄で押した `Esc` は egui がフレームの最初に
  フォーカス解除として処理するので、このフレームの状態だけでは「誰も持っていない」に見える

### 追記: モーダルが出ている間もキーの持ち主はコマンドラインではない（Issue #24）

未保存確認のモーダルは、ボタンにフォーカスが無いと「誰も持っていない」に見えるため、
上の判定だけでは Enter / Space / Esc を奪い、文字も入力欄へ入っていた（egui_kittest で
実測。LINE 実行中に Ctrl+N → Enter で履歴が増えた）。`begin_frame` にモーダルの有無を渡し、
出ている間はキーと IME を扱わず、入力欄も `interactive(false)` にして文字を受けない。
キーだけ止めても、フォーカスを持ったままの入力欄に文字が入る。

レビューを受けた追加の判断:

- **Esc = キャンセル、Enter = 保存する。** 開いたとき「保存する」にフォーカスを置き、
  ボタンに「(Enter)」「(Esc)」を併記する。「保存しない」には Enter も 1 文字のキーも
  割り当てない（変更を失う操作を誤打で起こさない）。Esc は図面・未保存・実行中の
  コマンドを残してモーダルだけ閉じる
- **背景のクリックではキャンセルにしない。** egui の `should_close()` は背景のクリックでも
  真になるため使わず、Esc だけを自分で見る。誤クリックで閉じるのを避ける
- **Enter は必ず「保存する」、Space は何もしない（フォーカスの位置に関わらず）。**
  egui のボタンはフォーカスがあると Enter / Space で押されるため、Tab を 1 回押すと
  次の Enter が「保存しない」になり、図面が捨てられた（再レビューで発覚）。モーダルの
  中身を描く前に Enter / Space を消費する（Esc と同じ形）。「保存しない」はクリックだけ。
  採らなかった案: 「保存しない」を Tab の巡回から外す（キーボードだけでは押せなくなり、
  外し方も egui の内部に依存する）
- **フォーカスの枠は「保存する」から動かさない。** Enter が常に「保存する」なので、Tab で
  枠が「保存しない」へ動くと、枠と Enter の結果が食い違い、意図しない上書きが起きる
  （再々レビューで発覚）。Tab は egui がフレームの最初に処理するので、消費では間に合わない。
  「保存する」にフォーカスロックのフィルタ（`set_focus_lock_filter`、TextEdit と同じ仕組み）を
  掛けて、Tab・矢印をフォーカス移動に使わせない。採らなかった案: Tab を巡回させたまま
  Enter を枠のボタンにする（Tab 1 回後の Enter が「保存しない」になり、元の事故に戻る）
- **Enter のキーリピートは「保存する」を押したことにしない。** `NEW` + Enter の長押しで、
  出てきたモーダルが即座に保存してしまう。リピートは消費して捨てる
- F8 / F10（直交・極）も F3 / F12 と同じく止める。背景は既定より少し暗く（alpha 150）
- テストでは rfd を開く箇所が理由つきで panic する。ダイアログ待ちのハングを
  無言のまま残さないため（CI の各ジョブにも `timeout-minutes: 30`）
- モーダル表示中は入力欄が `request_focus` で取り直さない（取り直すと最初の Tab が空振りする）。
  F3 / F12 も扱わない。カーソル横の動的入力の枠は不透明度 0 で描く（描くのをやめると
  IME とフォーカスの制約に触れる）

**採らなかった案:** モーダルが出た瞬間に入力欄のフォーカスを外す。閉じたあとに
`request_focus` で戻す条件が増え、フォーカスを巡る既存の分岐と絡む。

### 採らなかった案

- **パネルの入力欄のほうに `event_filter` を付けて、フォーカスを外させない。**
  入力欄はパネルごとに増える。付け忘れた欄でまた同じことが起きる。
  キーを取る側（コマンドライン）で判断すれば 1 箇所で済む
- **このフレームのフォーカスだけを見る。** 上のとおりパネルの `Esc` を取りこぼす。
  この形にするとテストが `Esc` で落ちることを確かめた

### テスト

`app/behavior_tests.rs`（GPU なしの通常テスト）で、`L` → `Tab` → `Z` が `LINEZ` になること、
候補が無いときやコマンド実行中の Tab で次の文字が入ること、パネルの入力欄を編集中に
`Space` / `Esc` / `Enter` で LINE が進まず履歴も増えないことを固定した。

### 追記: IME のイベントもキーと同じく持ち主を確かめる（実機の不具合報告）

LINE 実行中にレイヤパネルのレイヤ名欄で日本語を変換すると、パネルには正しく入るのに、
カーソル横のコマンド入力欄に `[変換中]` が出た。`track_ime` が `egui::Event::Ime` を
**フォーカスの持ち主を見ずに**拾って `composing` を立てていたため。`composing` に依存する
カーソル横の位置固定・キーの扱い・候補の更新もすべて止まっていた。

- IME のイベントを `composing` に反映するのは、`owns_keys` が真（入力欄がフォーカスを
  持っているか、どこにも無い）のときだけにする。キーと同じ判定を使う
- 持ち主でなくなったフレームで `composing` を落とす。コマンドラインで変換している途中で
  パネルへフォーカスが移ると、確定・取り消しはパネルへ届くので、落とさないと
  変換中が立ちっぱなしになる

`app/behavior_tests.rs` に、パネルで Preedit → Commit してもコマンドラインが変換中にならず
カーソル横がマウスに追従し続けること、その後キャンバスへ戻ると LINE に点が入ること、
変換中にパネルへ移ると変換中が終わることを足した（修正前に 2 本とも落ちることを確認）。

## ADR-0036: 寸法入力（段階 B）はツールが参加を宣言し、入力欄は 1 つのまま 2 欄に見せる

- **状態**: 確定（見た目と操作感はユーザーの目視確認待ち）
- **日付**: 2026-10-05
- **関連**: [Issue #20](https://github.com/yukimasui/ymcad/issues/20)（段階 B）、[ADR-0002](#adr-0002-コマンドラインは変換中にパースしない-phase-3)、[ADR-0034](#adr-0034-動的入力段階-aは本物の-textedit-をカーソル横へ動かす)、[ADR-0035](#adr-0035-コマンドラインがキーを扱うのはフォーカスが自分か無いときだけ)

### 背景

段階 A でカーソル横に入力欄を出した。段階 B では、基準点がある点の指定待ちで
「長さ」「角度」の 2 欄を出し、Tab で値を固定できるようにする。あわせて
直接距離入力（長さだけ打って Enter すると、カーソルの向きにその長さで点を置く）を入れる。

難しいのは**数値の意味がツールごとに違う**こと。LINE の 2 点目なら長さだが、
ROTATE では角度、SCALE では倍率、CIRCLE では半径になる。

### 決定 1: ツールが参加を宣言する（`Tool::dimension_base`）

`Tool` に既定 `None` のメソッド `dimension_base()` を足し、`Some(base)` を返す間だけ
「次の点は base からの長さ・角度で指定できる」とする。参加するのは
LINE / PLINE の 2 点目以降と、MOVE / COPY / STRETCH の目的点だけ。

参加中に数値 1 つを確定すると、`Session` が「base からカーソル方向へその長さ」の点にして
`StepInput::Point` で送る。ツールは長さや角度を知らない。

**採らなかった案:**

- **`last_point()` があるツールすべてに一律で効かせる。** ROTATE・SCALE・CIRCLE にも
  `last_point()` がある（相対座標の基準）。数値が黙って長さに読み替えられ、
  `RO` → 基点 → `90` が「90 回転」ではなく「90 離れた点の方向へ回転」になる
- **参加しないツールを列挙して除外する。** 新しいツールを足すと既定で参加してしまう。
  既定は不参加にして、参加するツールが明示する方が事故が起きない
- **`StepInput::Length` を足してツールに解釈させる。** カーソル位置はツールが知らない
  （`preview` に渡されるだけ）ので、各ツールがカーソルの向きを受け取る口を増やすことになる。
  点にする計算も参加ツールの数だけ重複する。点にしてから渡せば、ツールの `step` は
  クリックや座標入力と同じ経路のまま

### 決定 2: 直接距離入力は動的入力のオン/オフに関係なく効かせる

参加中のツールでは、数値 1 つの入力は従来「座標を指定してください」というエラーだった。
**今まで意味を持たなかった入力に意味を与えるだけ**なので、既存の操作とは衝突しない。
動的入力をオフにしている人も、長さをキーボードで入れたい場面は同じようにある。

**採らなかった案: オンのときだけ効かせる。** 同じ `100` + Enter が F12 の状態で
「線が引かれる」と「エラー」に分かれる。何が起きるかを F12 の状態で覚えておく必要が出る。

座標の書式（`100,50` / `@10,0` / `@100<45`）と英字のオプションは従来どおりで、
**何も付けない座標は絶対のまま**（ADR-0034 決定 5）。

「数値 1 つ」の判定は、欄の表示と同じ `dimension::classify` を使う（決定 6）。
`coord::parse_number` は `1e3` も 1000 と読むが、それを使うと欄の表示（`1e3` は数値以外として
通常の入力欄に戻る）と Enter の結果が食い違う。`1e3` は以前どおり LINE などでは
「座標を指定してください」で止まる。`parse_number` 自体と、参加しないツール
（CIRCLE の半径など）の数値の読み方は変えない（PR #25 レビュー）。

長さだけ決まっている点（直接距離入力・長さだけ固定）は、カーソルへの単位方向を
そのまま伸ばして `base + dir * length` で作る。向きをいったん度に直して戻すと、
atan2 → 度 → cos/sin の往復で誤差が乗り、`1` と打った線の長さが 1.0000000000000047 に
なっていた（PR #25 レビュー）。角度が決まっている点だけ、度から単位ベクトルを作る（決定 5）。

### 決定 3: `TextEdit` は 1 つのまま、入力中の欄の位置に置く

バッファも `TextEdit` も 1 つのまま、入力中の欄の位置に本物の入力欄を置き、
もう片方の欄は値を描くだけにする。Tab で入力中の欄が替わると、入力欄が
その位置へ移る（ID が同じなのでフォーカスとキャレットは引き継がれる）。

**採らなかった案: 欄ごとに `TextEdit` を置く。** フォーカスと IME の出力先が 2 つになり、
候補ウィンドウがどちらに付くか定まらない（ADR-0034 決定 6 と同じ理由）。
Tab でフォーカスを移す方式だと、ADR-0035 で直した「Tab でフォーカスが外れる」問題を
自分で作り直すことになる。

何も打っていない欄には、基点からカーソル（スナップ・固定の後）までの長さと角度を
薄く出す。入力中の欄では `TextEdit` のヒント文字として出す。

### 決定 4: 固定した値はラバーバンドとクリックの両方に効かせる

Tab で固定した値（錠前）は、ラバーバンドの先にもキャンバスのクリックにも効く。

- 長さだけ固定 … 向きはカーソル、長さは固定値
- 角度だけ固定 … カーソルをその角度の半直線へ正射影する
- 両方固定 … 点が 1 つに決まる

ラバーバンドとクリックは同じ `dimension::constrain` を通す
（`Session::rubber_band` / `Session::constrain`。`canvas` のカーソル位置と `place_point`）。

**採らなかった案: ラバーバンドにだけ効かせ、確定は Enter だけにする。**
見えている線の先と、クリックで入る点がずれる。固定したのにクリックでは無視される、
という動きは錠前を付けた意味がない。

**固定値から点が決まらない位置では、クリックも `Enter` と同じくエラーで止め、点を入れない**
（ユーザー判断）。角度だけ固定してカーソルがその反対側か真横にある（射影の長さが 0 以下）、
長さだけ固定してカーソルが基点に重なっている（向きが無い）場合。
勝手に反対向きの点を作らない。固定は残すので、同じ側へ動かせばそのままクリックできる。

このときラバーバンドは**基点に縮める**（線が消え、長さの欄のライブ値は 0 になる）。

- **カーソルの位置のまま描く案は採らない。** 「クリックすればそこに入る」と見えるのに、
  実際のクリックは断られる。見えている線と入る点を一致させる、という決定 4 の主旨に反する
- **ラバーバンドを描かない（プレビューを消す）案も採らない。** `Session::preview` の
  呼び出しを分岐させることになり、MOVE / COPY ではプレビューが元の位置に重なって
  見えるだけなので、基点に縮めるのと見た目は変わらない。分岐を増やす意味が無い
- 当初の実装（PR 前）は、ラバーバンドもクリックもカーソルのまま通していた。
  そのため角度を固定していても、反対側をクリックすると固定を無視した点が入っていた

### 決定 5: 角度は度・+X から反時計回り・絶対角

`@100<45` と同じ約束にする。

**採らなかった案: 直前の線分からの相対角。** MOVE / COPY / STRETCH には「直前の線分」が無く、
LINE の 1 本目にも無い。ツールや段階で角度の基準が変わると、同じ `90` が
「真上」と「直前の線に直角」に分かれる。座標入力（`@100<45`）とも食い違う。

90° の倍数はちょうどの単位ベクトルにする。`cos(90°)` は浮動小数点では 0 にならず、
真上に 100 引いたつもりの線の終点 X が基点からわずかにずれるため。

### 決定 6: 数値以外を打ったら欄をやめ、固定も効かせない

バッファに `,` `@` `<` や英字が入ったら、欄の表示をやめて通常の入力欄に戻す
（座標・オプションとして従来どおり解釈する）。その間は固定値を拘束に使わない。
欄が見えないのに拘束が効くと、カーソルと違う点が入る理由が分からない。

`-` や `.` だけの打ちかけは「数値以外」にしない。`-45` を打ち始めた瞬間に欄が消え、
次の 1 文字でまた出て、入力欄が跳ねるため。`1e3` のような指数表記は英字を含み、
オプションの英字と見分けられないので「数値以外」に回す。

この分類は欄の表示だけでなく、Enter で直接距離入力にするかどうかの判定にも使う
（決定 2）。当初は Enter 側だけ `coord::parse_number` を使っていて、`1e3` が欄では
通常の入力に戻るのに、Enter では長さ 1000 の直接距離入力になっていた（PR #25 レビュー）。

### 決定 7: キーの扱い

- **Tab** … バッファが数値なら今の欄をその値で固定し、バッファを空にして次の欄へ移る。
  空なら固定せずに移るだけ。2 欄を巡回する。長さ 0 以下は固定せずにエラーを出す。
  **コマンド候補が出ているときの Tab は従来どおり補完**（ツール実行中は候補を出さないので
  実際には重ならないが、優先順位をテストで固定した）。
  **動的入力オフ**では欄が無いので固定しない。参加中のツールで Tab を押したら、入力は変えずに
  「長さ・角度の固定は動的入力（F12）がオンのときに使えます」を 1 行出す。何もしないままだと、
  AutoCAD の感覚で `100` Tab `90` と打った入力が `10090` につながり、長さ 10090 の
  直接距離入力になっていた（PR #25 レビュー）。オフでも Tab で固定する案は、
  固定値が見えない拘束になるので採らない。Tab を Enter と同じに扱う案は、
  角度を打つつもりで押した人の点がその場で入ってしまうので採らない
- **Esc** … 固定か入力があれば、まずそれを全部解除する。何も無ければ従来どおり中断。
  入力は数値に限らない。参加中のツールで動的入力がオンなら、`@10` のような数値以外の
  入力でも 1 回目の Esc は入力を消すだけで、中断は 2 回目になる（ユーザー判断）。
  入力の種類で Esc の意味を変えると、1 回で中断されるかどうかを打った文字で覚えることになる
- **Enter** … 固定値と入力中の値（無い欄はカーソルから）で点を作る。長さだけ打って
  Enter すれば直接距離入力と同じ結果になる。固定も入力も無ければ従来どおり空 Enter
- 固定は**基点が変わったとき**と、**ツールが点を受け取ったとき**に外す。COPY は基点が
  変わらないまま次の点へ進むので、基点の変化だけでは前の複写の固定が残る。
  ツールに断られたとき（同じ点など）は外さない

いずれも ADR-0035 の `owns_keys`（フォーカスが入力欄か無いときだけ）と、
変換中はキーを奪わない（ADR-0002）の内側で扱う。

### 決定 8: 変換中は欄の見た目を変えない

変換中のバッファには未確定文字列が入っているので分類しない（ADR-0002）。
欄を出すかどうかは、変換が始まる前の判断をそのまま使う。
切り替えると入力欄が角度の欄から左端へ跳び、入力欄に付いて出る IME の候補ウィンドウが
跳ねる（ADR-0034 決定 4）。錠前と `[変換中]` の幅も常に確保し、出ても入力欄を動かさない。

### 構造

- `cmdline/dimension.rs` … egui に依存しない純粋関数（長さ・角度から点、固定による拘束、
  バッファの分類、欄の巡回・解除・確定）。単体テストで固定した
- `Tool::dimension_base` … 参加の宣言。`Session::dimension_base` は選択待ちの間 `None`
- `dimension::constrain` … 固定値による拘束の唯一の計算。`Session::constrain`（クリック、決まらなければエラー）と `Session::rubber_band`（決まらなければ基点）が通す
- `Submission::Dimension` … 欄で確定した値。点にするのは基点とカーソルを知っている `Session`

### 決めずに残したこと

- **固定していない入力中の値はラバーバンドに効かせない。** `100` と打っただけでは
  ラバーバンドはカーソルのまま（Tab で固定すると従う）。AutoCAD は打った値で
  プレビューを動かす版もある。使ってみて欲しければ足す
- 角度の固定は半直線への射影で、反対側では長さが決まらない（反対向きにはしない。
  クリックも断る。決定 4）

## ADR-0037: リボン（タブつきアイコンバー）を足し、押すことはコマンド名を打つのと同じ扱いにする

- **状態**: 確定（見た目と操作感はユーザーの実機確認待ち）
- **日付**: 2026-10-05
- **関連**: [Issue #26](https://github.com/yukimasui/ymcad/issues/26)、[ADR-0016](#adr-0016-コマンド表を-match-からデータに変える)、[ADR-0032](#adr-0032-パラメータの操作はパネルへ寄せ文字入力は名前だけにする)、[ADR-0034](#adr-0034-動的入力段階-aは本物の-textedit-をカーソル横へ動かす)、[ADR-0035](#adr-0035-コマンドラインがキーを扱うのはフォーカスが自分か無いときだけ)

### 背景

操作はコマンド入力（とカーソル横の動的入力）が中心で、マウス中心の操作に難があった
（ユーザーの声）。コマンドを打つ体験は残したまま、アイコンからもコマンドを始められるようにする。

AutoCAD 2009 でリボンを嫌ったユーザーの不満（CAD Nauseam「Why do you hate the Ribbon?」ほか）は
「タブ切り替えでクリックが増える（65%）」「画面を取りすぎる（64%）」「道具が隠れる・見つけにくい」。
これらへの対策を構成の前提にした（Issue #26）。

### 決定 1: 構成

- 画面上端に `egui::Panel::top("ribbon")`。1 段目にタブ、2 段目にグループ（枠とグループ名）ごとの
  アイコンボタン。ボタンはアイコンの下にコマンド名だけを小さく出す（打つ名前を覚えられるように）。
  名前は英語のコマンド名のまま（オーケストレーターの決定。日本語名は説明としてツールチップに出る）
- 1 段目のタブの直後に、区切り線を挟んで、どのタブでも押せる **クイックアクセス**
  （UNDO / REDO / SAVE。アイコンだけ、16px）。決定 2 を参照。当初は行の右端に置いたが、1280px で
  タブから約 950px 離れて視線の外になった（PR #32 の操作レビュー、オーケストレーターの決定。
  AutoCAD のクイックアクセスも左上にある）
- 高さはアイコン 22px・名前 9pt・グループ名 9.5pt に抑え、中身は実測 72px（パネルの余白込みで画面上は約 76px。テストで中身 80px 以下を固定）
- 幅が足りないときは横スクロール。**普通のホイール（縦回転）でも横に動く**ようにした
  （egui の既定 `always_scroll_the_only_direction = false` では Shift が要り、横ホイールの無い
  マウスで右端に届かない。リボンの `Ui` の style だけを変える）
- **送れる側の端に、背景色へ消えるぼかしと山形（› / ‹）を出す。** egui のスクロールバーは
  マウスを乗せたときしか出ず、切れ目がグループの境目に重なると送れることに気づけなかった
  （PR #32 の操作レビュー）。山形は字形ではなく線で描く（フォントに依らない）。
  常に見えるスクロールバーにする案は、高さを数 px 取るうえ細くて目に入りにくいので採らなかった
- **その帯（端から 28px）は押せる。** 押すとその向きへ表示幅の 3/4 だけ送る（少し重ねて、どこまで
  見ていたかを残す）。乗せると指のカーソル。帯はボタンより後に `ui.interact` で登録するので、
  帯の上のクリックは下のボタンへ届かない。当初は絵だけで、山形は「次へ送る」ボタンの見た目そのもの
  なのに、押すと下に隠れたボタン（幅 800px では LAYER）が押され、ツールのボタンなら実行中の
  コマンドが中断されていた（PR #32 の操作再レビューのブロッキング）
- **はみ出している間は、左右両方の帯を常に置く。** 送れない側は山形を薄くし、クリックは受け取るが
  何もしない（指のカーソルも出さない）。はみ出していない幅では帯を置かない。
  送れる側だけに置いていたときは、端に着くとその側の帯が消えて同じ位置に端のボタンが現れ、
  続けて押した 1 回がボタンに当たった（「›」の連打で LAYER が開閉し、「‹」で実行中の POLYLINE が
  中断されて LINE が始まった。幅 600・700・800px。PR #32 の 3 回目の操作レビュー、
  オーケストレーターの決定）
- あわせて、はみ出している間は**ボタンの並びの両端に帯の幅の余白**を足す。端まで送ったとき、
  端のボタン（LINE・LAYER）が帯の下に隠れずに押せるように。はみ出しの判定は余白を足す前の幅で
  行うので、余白のせいで判定が切り替わり続けることはない（判定は前のフレームの結果を使う）
- 採らなかった案: 端に着いたら帯を消し、少しの間だけクリックを無視する（時間で振る舞いが変わり、
  ゆっくり押す人とすばやく押す人で結果が違う）。端に着いても送れる側と同じ見た目のままにする
  （押しても何も起きない理由が分からない）
- マウスを乗せると 2 行のツールチップ。1 行目 `TRIM — 線分を切り取る（他の全図形が境界）`、
  2 行目（弱い色）`打つ: TR / TRIM`（短い順）。当初の 1 行（`TRIM（TR）切り取り（…）`）は括弧が
  重なってどこまでが名前か分かりにくく、エイリアスの無いものは形が変わっていた
- 実行中のコマンドのボタンは選択色で強調する。強調は `Session::active_command`
  （実行中のツールの名前）から毎フレーム決めるので、打って始めたコマンドでも強調される。
  **そのコマンドが別のタブにあるときは、そのタブの名前の下に選択色の 2px の下線を引く**
  （タブを切り替えると、何が実行中かがリボンから見えなくなっていた）。当初はタブの横に点を
  出したが、タブとタブの間に来て区切り文字に見え、どちらのタブの印か分かりにくかった
- グループ名はボタン下の名前と同じ文字色。弱い文字色ではコントラスト比が約 2.7:1 で読みにくかった
- 選んでいるタブは `cad-app` 側（`Ribbon`）に持ち、`Document` には入れない

### 決定 2: タブとグループの割り当て

| タブ | グループ | コマンド |
|---|---|---|
| ホーム | 作図 | LINE / POLYLINE / CIRCLE / ARC / RECTANGLE / XLINE |
| | 修正 | ERASE / MOVE / COPY / STRETCH / ROTATE / SCALE / MIRROR / TRIM / EXTEND / FILLET / CHAMFER / EXPLODE |
| | グループ | GROUP / UNGROUP |
| | レイヤ | LAYER |
| コンポーネント | 定義・編集 | COMPONENT / REDEFINE / EDITCOMP / ENDCOMP |
| | 配置 | INSERT |
| | パラメータ | PARAM / BIND / PSET |
| | 一覧 | COMPONENTS |
| 表示・ファイル | 表示 | ZOOM |
| | ファイル | NEW / OPEN / SAVEAS |
| クイックアクセス（タブの直後、常に表示） | | UNDO / REDO / SAVE |
| （出さない） | | QUIT |

- **日常の作図・修正・グループ・レイヤはすべてホーム**、起動時もホーム。線を引いてすぐトリム
  するような操作でタブを切り替えさせない（不満の 65%）
- EXPLODE はポリラインの分解にも使うので、コンポーネントではなく修正に置いた
- **LAYER はホームの「レイヤ」グループ。** 当初は「表示・ファイル」の「表示」に置いていたが、AutoCAD に
  慣れた人はレイヤをホームタブで探す（PR #32 の操作レビュー、オーケストレーターの決定）
- **用語は「レイヤ」にそろえる。** グループ名・ステータスバー・レイヤパネルの見出しが「画層」、
  ツールチップとマニュアルが「レイヤ」と混在していた（PR #32 の操作再レビュー）。コマンド名 LAYER・
  既存のマニュアル・パネル名に合わせた（オーケストレーターの決定）
- **UNDO / REDO / SAVE はクイックアクセス**（AutoCAD のクイックアクセスツールバーに当たる）。
  どのタブでも要るのに、ymcad には `Ctrl+Z` が無く、ホーム以外のタブでは打つしかなかった。
  当初は UNDO / REDO をホームの「元に戻す」に、SAVE を「ファイル」に置いていた
- **1 つのコマンドの置き場所は 1 つ。** クイックアクセスに置いたものはタブには置かない
  （「SAVE はどこ」の答えが 1 つで、同じボタンが画面に 2 つ並ばない）。網羅のテストは
  「タブとクイックアクセスを合わせてちょうど 1 回」か「除外リストにちょうど 1 回」を検査する。
  ファイルのグループに SAVE が無いのは、同じ画面の右上に常に見えているので困らないと判断した
  （AutoCAD のリボンも上書き保存はクイックアクセスとアプリケーションメニューにある）
- **QUIT は出さない。** 押し間違えると（保存済みなら確認なしで）アプリが閉じる。
  ウィンドウの ✕ と、打って使う `QUIT` で足りる

### 決定 3: 押すことはコマンド名を打つのと同じ扱い

- 履歴に `> LINE` を残し、プロンプトを出し（動的入力がオンならカーソル横）、空 Enter での
  再実行の対象にする。即時実行のコマンド（UNDO）や UI 要求を出すコマンド（LAYER / SAVE）も
  同じ経路で動く（`start` に合流する）
- **実行中のコマンドがあれば `Esc` と同じく中断してから始める**（AutoCAD と同じ）。
  中断すると選択も外れる（`Esc` と同じ）。何も実行していなければ選択は残す
  （選んでから MOVE を押す使い方。名前を打ったときと同じ）
- コマンドラインに打ちかけの文字があれば捨てる
- 入口は `Session::start_command_from_ui`。**テキスト入力の経路（`handle_text`）には流さない。**
  実行中のツールに文字列として届くと「不明なオプションです: CIRCLE」になるため
- ボタンは `Sense::CLICK` で作り、キーボードのフォーカスを取らない（`Sense::click()` は
  `FOCUSABLE` を含み、Tab 移動で止まる。当初はこちらで「`Sense::click` だけ」と誤って書いていた。
  egui はクリックではフォーカスを渡さないので、クリックの振る舞いは変わらない）。押した後もキーは
  コマンドラインへ流れる（ADR-0035 の `owns_keys` はそのまま）。パネルの入力欄を編集中に
  押しても、egui がクリックでそのフォーカスを外すので、続けて打った座標はコマンドへ入る
- リボンはコマンドラインのキー処理（`begin_frame`）より前に描く。押した結果（実行中の
  ツール・候補を出すか・寸法入力の基点）を、同じフレームのコマンドラインの扱いに反映させるため

**例外 1: パネルを開閉するだけのコマンドは中断しない**（PR #32 のレビュー）。
当初は LAYER / COMPONENTS も中断していたので、POLYLINE を 5 点打った途中でレイヤパネルを開くと
確定前のポリラインが丸ごと消えた。AutoCAD でもレイヤのパレットは実行中のコマンドを中断しない
（透過コマンド）。

- 決め方: **図面にも実行中のツールの状態にも触れず、パネルを開閉するだけ**のもの。
  `Immediate::keeps_running_command` が `_` を使わずに全部の種類を並べて決めるので、
  即時コマンドの種類を足すとコンパイルでここの判断を求められる。今は LAYER と COMPONENTS だけ
- 中断しないときは、実行中のツール・選択・打ちかけの文字をそのまま残し、再実行の対象も
  実行中のコマンドのまま変えない（`> LAYER` は履歴に残す）。何も実行していないときは
  ほかと同じ（再実行の対象になる）
- 中断するもの: ツールとして動くもの（ZOOM を含む）、図面を変える UNDO / REDO、編集を終える
  ENDCOMP、ファイル操作（図面を入れ替える・保存の前に実行中の操作を確定させたい）。
  ZOOM を透過で動かすか（AutoCAD の `'ZOOM`）は、ZOOM がツールとして選択肢を待つので
  別の仕組みが要る。要否はユーザーに確認する
- 打った `LAYER` は今までどおり、実行中のツールへオプションとして届く（打つ経路は変えない）

**追記（PR #42 の操作レビュー）: 保存（SAVE / SAVEAS）も中断しない。** `Ctrl+S` は元から実行中のツールに
触れないのに、リボン・クイックアクセスの保存ボタンだけがコマンドを中断し、選択も外していた。
保存は図面の図形を変えないので、`keeps_running_command` の対象に足して `Ctrl+S` とそろえた
（MOVE の基点待ちや POLYLINE の途中で押しても、ツール・選択・置いた点が残る）。確定前の図形
（打っている途中のポリライン）は図面に入っていないので保存されない。これも `Ctrl+S` と同じ。
NEW / OPEN / 終了は図面を入れ替える（捨てる）ので、今までどおり中断する。

ファイルダイアログ（rfd、同期 API）が開いている間もツールが残って問題ないかをコードで確かめた。

- `FileDialog::save_file` は閉じるまで戻らず、その間 egui のフレームは回らない。ツール・選択・
  コマンドラインに届く入力は無く、状態は押した時点のまま止まっている
- 保存（`save_to`）が図面に対してするのは書き出しと `Document::mark_saved` だけで、`mark_saved` は
  未保存の印と保存先のパスを変えるだけ。図形にも `revision` にも触れないので、ツールが持っている
  `EntityId` や点、`revision` をキーにした派生データ（ラバーバンド・描画キャッシュ）はそのまま使える
- 保存の結果は図面を入れ替えない成功（`FileOutcome::Ok`、Issue #41）なので、選択やスナップも外さない
- キャンセル・失敗でも図面は変わらない（`Nothing` / `Failed`）

**例外 2: 変換中（IME）は何もしない**（PR #32 のレビュー）。コマンドラインのバッファには
未確定の文字列が入っている。当初は押すと入力欄を空にしていたので、入力欄が「変換中」のまま空になり、
以後の Enter が効かなかった（変換中は確定を止めているため）。押されても何もせず、
「変換中です。確定するか Esc で取り消してから押してください」をエラーとして出す。
バッファに触らない（ADR-0002）。パネルを開閉するだけのコマンドも同じ扱いにした（例外を重ねると
どれが押せるかを覚えることになる）。

**同じフレームの Enter（残した帰結）。** リボンは `begin_frame` より前に描くので、ボタンを離すのと
同じフレームに Enter が来ると、その Enter は始めたばかりのコマンドへ空 Enter として届く
（LINE ならすぐ終わる）。実機で同じフレームに重なることはまず無いので、手当てはしていない。

**採らなかった案: パネルの「配置」と同じ `start_tool_directly` を使う。** あちらは定義の決まった
ツールを渡す専用の入口で、何も実行していなくても `cancel` して選択を捨て、履歴にも名前を残さない。
「名前を打つのと同じ」にならない。

### 決定 4: 割り当ての表は `CommandSpec` と分け、網羅をテストで検査する

Issue #26 の設計方針は「`CommandSpec` にタブとグループを持たせる」だったが、**リボン側
（`ribbon/layout.rs`）に「タブ → グループ → コマンド名」の表を別に持つ**ことにした
（オーケストレーターの判断）。

- コマンド表はコマンドの定義（名前・エイリアス・説明・実体）で、どこに置くかは画面の都合。
  並びや見た目を変えるたびにコマンド表へ触ると、コマンドを足す別の作業と衝突する
- データは最初から 3 段（タブ → グループ → コマンド）で持つので、コマンドが増えても作り直さない

代わりに、食い違いをテストで検出する。

- コマンド表の全コマンドが「リボン（タブとクイックアクセスを合わせて）にちょうど 1 回」か
  「除外リスト（`EXCLUDED`）にちょうど 1 回」のどちらか一方に入っている
  （コマンドを足して置き忘れると落ちる。クイックアクセスとタブの両方に置いても落ちる）
- 割り当て表と除外リストに、コマンド表の正式名でない名前が無い（エイリアス・打ち間違い・消したコマンド）
- ツールの `name()` がコマンド表の正式名と一致する（一致しないと強調が外れる）

### 決定 5: アイコンは SVG ファイルを埋め込み、表示側で着色する

`crates/cad-app/assets/icons/<コマンド名>.svg` を 1 コマンド 1 ファイルで置き、`include_bytes!` で
埋め込む。表示は `egui_extras`（`svg` 機能のみ、`cad-app` だけの依存）の画像ローダーで行い、
`tint` で色を付ける（通常は文字色、実行中は選択色）。コード側の表は「名前 → バイト列」だけ。

- **ユーザーが 1 つずつ外部のツールで描き直して差し替えやすいように**（ユーザー判断）。
  ファイルを置き換えてビルドし直すだけで絵が変わる
- SVG は白一色（`#ffffff`）で描き、補助線は不透明度で薄くする。`tint` は乗算なので、
  どの色に着色しても形と濃淡が保たれる。作法は `assets/icons/README.md`
- 画像ローダーは `Ribbon::show` の先頭で入れる（入っていれば何もしない）。起動時だけに置くと、
  テスト用のハーネスで入れ忘れて絵が出ない
- 網羅のテスト: 置いた全コマンドに SVG がある / フォルダに対応の無い余分なファイルが無い /
  全 SVG が `usvg` で 24×24 にラスタライズでき何かが描かれる / **ラスタライズした画素がすべて白**
  （乗算済みアルファで `r == g == b == a`。24px と 72px の両方）。`currentColor` は使わない
- 白一色の検査は当初、属性の文字列（`fill="…"` など）を見ていた。`stroke="currentColor"`
  （`color` が無いと黒）と、ルートの `fill="none"` の書き忘れ（SVG の既定の塗りは黒）を通して
  しまい、差し替えた SVG が黒く描かれる穴があった（PR #32 のコードレビュー）。描いた結果の画素で
  見る形に変え、この 2 つで落ちることを確かめた

依存は増えるが `cad-app` だけで、`cad-core` の依存ゼロ（ADR-0026）と CI の依存方向の検査は
そのまま（`cargo tree -p cad-core` に egui 系・resvg 系が出ないことを確かめた）。
`Cargo.lock` に増えたのは `egui_extras` と `resvg` / `usvg` とその依存（`roxmltree` / `svgtypes` /
`tiny-skia` 系など）。既存の依存の版は変わっていない。

最初は egui の `Painter`（線・円・円弧・多角形）でアイコンを描いていた（Issue #26 の当初の決定）。
その絵を SVG に描き直して今の 37 ファイルにした。PR #32 の操作レビューで、等倍で名前を隠すと
当てにくいと判定された STRETCH・REDEFINE・EXPLODE と、XLINE・ROTATE・TRIM・コンポーネント系 5 個を
描き直した（箱を縮めて違いを示す印を大きく、など）。EXPLODE は再レビューでも等倍で POLYLINE と
見分けにくかったので、レビュアーの案（角が弾けて 2 本の線分に分かれ、角だった所に火花）にした。

### 採らなかった案

- **タブなしで全部を 1 段に並べる** … 今の 37 コマンドなら収まるが、コマンドが増えると
  作り直しになる（ユーザー指摘）
- **用途ごとに細かくタブを分ける（作図 / 修正 / …）** … 線を引いてすぐトリムするような
  日常操作でもタブの切り替えが要る
- **左端に縦のツールパレット** … グループ名を出す余地が少なく、右のパネルと合わせて
  作図領域の横幅が狭くなる
- **アイコンフォント（egui-phosphor など）** … 汎用の絵しかなく、TRIM・FILLET・STRETCH などが
  代用の絵になる
- **egui の描画命令でアイコンを描く**（当初の決定）… 依存は増えないが、絵がコードの中にあり、
  ユーザーが外部のツールで描いて差し替えられない
- **ビルド時に SVG を描画命令へ変換する自作の仕組み** … 依存は増えないが、扱える SVG が自作の
  変換器の対応した一部に限られ、外部ツールの書き出しがそのまま使えるとは限らない
- **多色の SVG をそのまま出す** … テーマ（明暗）と実行中の強調で色を変えられない
- **ボタンを押したらコマンド名をテキスト入力として流す** … 実行中のツールにオプションとして
  解釈される（決定 3）
- **グループを畳む仕組み** … 幅が足りないときは横スクロールで足りる。必要になってから

## ADR-0038: 直交モードと極トラッキングは独立したスイッチにし、カーソル点を拘束する 1 本の経路に載せる

- **状態**: 確定（操作感はユーザーの目視確認待ち）
- **日付**: 2026-10-05
- **関連**: [Issue #29](https://github.com/yukimasui/ymcad/issues/29)、[ADR-0036](#adr-0036-寸法入力段階-bはツールが参加を宣言し入力欄は-1-つのまま-2-欄に見せる)

### 背景

水平・垂直・決まった角度の線を、座標を打たずにマウスで引けるようにする。
AutoCAD の F8（直交）と F10（極トラッキング）にあたる。フォーラムでの不満は
「F8 を入れると F10 が勝手に切れ、F8 を切っても戻らない」「F3 と F8 が互いを消し合うように見える」
「極の刻みが分かりにくい」「直交とスナップがぶつかる」（Issue #29 の調査）。

### 決定 1: 2 つは独立したトグル。両方オンなら直交が優先

`drafting::Drafting` に `ortho` / `polar` の 2 つの真偽値を持ち、片方の切り替えは他方に触れない。
両方オンのときは直交が勝ち、極の補助線は出さない。ステータスバーの `POLAR` は
オンのまま**控えめの色**（オンとオフの中間）にし、ツールチップと履歴（「両方オンの間は直交が
優先されます」）で理由を出す。

**採らなかった案: AutoCAD と同じく排他にする（F8 で F10 を切る）。** まさにそれが不満の筆頭。
F8 を切った後に極トラッキングが戻らず、気づかないまま作図を続けることになる。
排他にしなくても、両方オンのときの勝ち負けが決まっていて表示に出ていれば混乱しない。

状態は UI の状態なので `cad-app` 側（`CadApp::drafting`）に持ち、`Document` には入れない。
保存もしない（起動時はどちらもオフ）。

### 決定 2: 優先順位は「寸法入力の固定 > スナップ吸着 > 直交 > 極」

| 順位 | 何が | 理由 |
|---|---|---|
| 1 | 寸法入力の固定（ADR-0036） | 打った値は明示的な指示。角度を固定していれば直交・極はかけない。**長さだけの固定では向きを直交・極が決める**（固定していない欄はカーソルから決まる、という ADR-0036 の約束と同じ） |
| 2 | スナップ吸着 | AutoCAD と同じ。直交のままで既存の端点・交点へつなげられないと、毎回 F8 を切ることになる（「osnaps and ortho」の不満） |
| 3 | 直交 | 両方オンのとき直交が勝つ（決定 1） |
| 4 | 極 | 刻みの近くでだけ吸い付く補助なので、いちばん弱くてよい |

角度を固定しているのに直交をかけると、固定した半直線へ射影する元の点が水平・垂直に
ずらされ、カーソルを半直線に沿って動かしても長さが不自然に変わる。だから「かけない」にした。

### 決定 3: 拘束は 1 本の経路に載せる（`drafting::track_cursor`）

スナップ → 直交・極（`track_cursor`）→ 寸法入力の固定（`Session::rubber_band` / `constrain`）の順。
キャンバスのラバーバンド（`CadApp::canvas`）とクリック（`CadApp::place_point`）の両方が
`CadApp::track` → `drafting::track_cursor` を通るので、見えている線の先とクリックで入る点が一致する。
`Session::set_cursor` には拘束後の点を渡すので、**直接距離入力と寸法入力の `Enter` の向き、
欄のライブ値も拘束後の点**から決まる。

**採らなかった案: 各ツールの `preview` / `step` に直交を効かせる。** ツールの数だけ計算が重複し、
ラバーバンドとクリックの片方だけ直し忘れる（ADR-0036 決定 4 と同じ理由）。

### 決定 4: 基準点は `Tool::tracking_base`（既定は寸法入力の基点、無ければ直前の点）

`Tool` に `tracking_base()` を足し、既定を `dimension_base().or_else(last_point)` にした。
寸法入力に参加する LINE / PLINE / MOVE / COPY / STRETCH は基点、参加しない
ROTATE / SCALE / MIRROR / CIRCLE / ARC / XLINE は直前の点で拘束がかかる。
MIRROR の軸や ROTATE の向きを水平・垂直・15° 刻みで指せるのは、AutoCAD でも
直交・極がいちばん使われる場面。**RECTANGLE だけは `None` で外す**（対角を水平・垂直に
すると面積 0 で必ず断られる）。`Session::tracking_base` は点の指定待ちで図形の指定待ちでない
ときだけ返す（選択中・TRIM のピック中には効かない）。

**採らなかった案:**

- **`dimension_base()` だけを使う。** ROTATE・MIRROR・XLINE で効かない。数値の意味が
  ツールごとに違うから寸法入力は参加制にした（ADR-0036）が、向きの拘束は数値を読み替えないので
  同じ制限を受ける理由が無い
- **`last_point()` だけを使う。** 参加ツールでは両者は同じ点なので結果は変わらないが、
  寸法入力と基準がずれうる形にしておく理由も無い。既定を「寸法入力の基点を優先」にして
  寸法入力の欄と同じ点から測ることを保証した
- **外すツールを `Session` 側で列挙する。** 新しいツールを足したときに漏れる。ツールが自分で宣言する
  （ADR-0036 の `dimension_base` と同じ形）

### 決定 5: 直交の射影と極の吸い付き

- **直交**: 基準点を通る水平線と垂直線のうち、カーソルに近い方へ正射影する。
  水平と垂直の差がちょうど同じ（45°）なら**水平**。境目で決め打ちしておかないと、
  浮動小数点の揺れでフレームごとに入れ替わりうる
- **極**: 刻みは 15°（定数 `POLAR_STEP_DEG`）。カーソルの向きに最も近い倍数の半直線を選び、
  カーソルからその半直線までの距離が**画面上で 10px**（`POLAR_SNAP_PX`、スナップの吸着半径と同じ）
  以内、かつ角度の差が **±3°**（`POLAR_MAX_DIFF_DEG`）以内なら半直線へ正射影する（±3° は追記を参照）。角度の差（度）で閾値を決めると、基準点から遠いほど画面上で
  大きく吸い寄せられ、狙った位置から指が離れたように感じる。半直線上の点は寸法入力の
  `point_at` で作り、90° の倍数はちょうどの単位ベクトルにする（真上・真横の線がぶれない）
- 吸い付いているときは吸い付いた点から先へ**点線の補助線**をキャンバスの端まで引き
  （基準点から引かない理由は追記を参照）、吸い付いた点の右上に `45°` を出す（右下はカーソル横の入力欄、ADR-0034）。補助線は画面の矩形で切ってから
  点線にする（基準点が画面のはるか外にあっても点の数が増えない）

**採らなかった案: 極の刻みを設定画面やコマンドで変えられるようにする。**
Issue #29 では「設定変更は今回はコマンドかパネルで最小限」としていたが、設定画面は無く、
設定を覚える仕組み（保存先）も無い。15° は 30°・45°・90° を含み、AutoCAD の既定の候補でもある。
使ってみて欲しければ足す（定数を `Drafting` の状態に移すだけで済む形にしてある）。

**採らなかった案: オブジェクトスナップトラッキング（OTRACK、スナップ点からの位置合わせ）も同時に入れる。**
AutoCAD では極トラッキングと並ぶ機能だが、基準点が「直前の点」ではなく「乗せたスナップ点」になる
別の仕組みなので、別 Issue にする。

### 決めずに残したこと

- 吸い付く距離（10px）と補助線・角度表示の色は、実機で使ってから調整する
- 直交 ON のとき、「水平に引きたいのにスナップが吸い付いて斜めになる」場面がありうる。
  AutoCAD と同じ振る舞いで、MANUAL に「マーカーから離すか F3」と書いた

### 追記: PR #35 のレビューを受けて決めたこと

**変換中は F8 / F10 で切り替えない。** 日本語 IME では F8 が半角カナ、F10 が半角英数への
変換キーで、名前（レイヤ名など、ADR-0032 で唯一打つもの）を打つときによく使う。
egui_kittest では、変換中の F8 / F10 がそのまま直交・極を切り替えていた。実機で IME が
先にキーを取るかは、X11（XIM）/ Wayland（text-input-v3）と ibus / fcitx5 の組み合わせ次第で確証が無い。
そこで、**いずれかの入力欄が変換中のフレームでは F8 / F10 を消費も反応もしない**（`take_key_toggles`）。

- 変換中かどうかは、フォーカスの持ち主を問わず IME のイベント（空でない Preedit で開始、
  Commit・空の Preedit で終了）から追う。コマンドラインの変換中フラグは、コマンドラインが
  キーの持ち主のときしか立たない（ADR-0035）ので、パネルの欄の変換が見えない
- フォーカスが移ったら変換は終わったとみなす（確定・取り消しは移った先へ届くため）
- 確定と F8 が同じフレームに来た場合も切り替えない（安全側）
- 状態はアプリに持たせず egui の一時データに置き、`drafting.rs` に閉じた
- **採らなかった案: コマンドラインの `is_composing` だけを見る。** パネルの欄で変換しているときに効かない
- F3 / F12 は IME の変換キーではないので、今回はそろえていない

**極は角度の差 ±3° 以内でだけ吸い付く（オーケストレーターの決定）。** 画面上の距離（10px）だけで
決めると、`距離 = r·sin(差)` なので基準点から約 76px 以内（15° 刻み）ではどの向きでも吸い付き、
補助線と角度の表示が 15° ごとにくるくる変わる。短い線を自由な角度で引けなくなる。
画面上の距離と角度の差の**両方**を満たすときだけ吸い付く。遠いところでの吸い付き方は変わらず
（10px が先に効く）、近いところの吸い付きすぎだけが消える。

- **採らなかった案: 既定の刻みを 45° にする。** 必ず吸い付く範囲は縮むが、15°・30° の線が引けなくなる
- **採らなかった案: 基準点から一定 px 以内では吸い付かない。** 近くで ±3° の範囲にあるときまで切れる。
  角度の差で決めれば、近くでも狙った角度には吸い付く

**補助線は吸い付いた点から先だけに引く。** 基準点から引くと、確定する区間（ラバーバンド）の上に
水色の点が乗って縞模様に見え、「ここまで引く」と「この向きに延びる」が見分けにくかった。
ラバーバンドの下に描く案もあるが、重なる区間ではどちらかが隠れるので採らなかった。

あわせて、MIRROR の「元を消すか Y/N」の段階でも基準点が返っていて補助線が出ていたので、
`MirrorTool::tracking_base` で軸が決まった後は `None` にした（点を指さない段階）。
他のツールも見直し、点を指さない段階で基準点を返すものは無かった。
直交を OFF にしたとき極がオンなら、履歴に「直交モード: OFF（極トラッキングが効きます）」と出す
（ON のときの「両方オンの間は直交が優先されます」と対にする）。

### 追記: ステータスバーの並び（Issue #38 / PR #39）

PR #35 で `ORTHO` / `POLAR` が増え、幅 800px では `POLAR` の後ろで切れて `DYN` から右が
画面外になっていた（クリックで切り替えられない）。並びと幅の決め方を次のようにした。

`X … Y …` | `OSNAP` | `ORTHO` | `POLAR` | `DYN` | `コマンド実行中` | `レイヤ` | `選択` | `要素` | `倍率` | （`日本語フォント未検出`） | `描画 平均…最大…`

- **クリックで操作する部品を、座標の直後（情報表示より先）に置く。** 右端から切れても、
  操作できなくなるのは情報表示だけになる。AutoCAD も座標の直後に作図補助のボタンを並べる
- **押す位置を状態で動かさない。** 「コマンド実行中」の欄は待機中も空のまま幅を確保し、
  `OSNAP` の欄は吸着中のいちばん長い表示（`OSNAP:最近点`）の幅で固定する（`fixed_width`）。
  当初は「コマンド実行中」が出るたびに後ろが約 110px、吸着で `OSNAP:端点` になるたびに
  ORTHO 以降が跳ね、押そうとした部品が逃げた（PR #39 の操作レビュー）
- **情報表示は項目ごとに、入らなければ区切り線ごと省く**（`show_while_fits`）。文字の途中で切らない。
  入らない項目に来たらそこから後ろはすべて省く（後ろの短い項目だけ出すと、並びの意味が崩れる）。
  並びは `レイヤ / 選択 / 要素 / 倍率`（オーケストレーターの決定）。右から省かれるので、
  作図中に見るレイヤと選択が最後まで残る。区切り線の幅はスタイルで決まるので、実際に描いた前後の位置から測る
- **「日本語フォント未検出」は描画時間より前に置き、英語を併記する。** フォントが無いとこの文言自体が □ になる
- **描画時間は最後。** 60fps の予算を確かめる開発者向けの情報で、作図には要らない。数値は固定幅
  （`{:>6.2}`）にした。桁が変わると文字列の幅が変わり、境目の幅でフレームごとに出たり消えたりしうるため
  （コードレビュー）。ほかの項目（レイヤ名・選択数・要素数・倍率）は操作したときにしか変わらないので、
  フレームごとに揺れることはない
- **座標の固定幅を 14 文字から 12 文字（±999999.9999 まで）に詰めた。** 800px で選択数が入らなかったため。
  それより大きい座標では欄が伸びて後ろが動くが、1 km（mm 単位）を超える図面は今の想定外

実測（日本語フォントあり）: 800px では部品 4 つと「コマンド実行中」・レイヤ・選択まで、640px では部品と
「コマンド実行中」まで出て、情報表示は途中で切れない。1280px では描画時間まで出る。待機中と LINE 実行中、
吸着の有無で部品とレイヤの位置が変わらない。`app/behavior_tests.rs` の振る舞いテストで固定した。
テストでも日本語フォントを読み込む。読み込まないと漢字が代替の □ になって幅が実機と変わり、
境目の幅で結果が変わる（元の並びの不具合は、640px ならフォント無しでも再現するが、800px では再現しなかった）。

**採らなかった案:**

- **X / Y の固定幅を詰めるだけで全体を収める。** 項目が増えるたびに同じことが起き、狭い幅では結局切れる。
  並び順と項目ごとの省略で「切れても困らないもの」を後ろにする方が長持ちする（詰めることは併用した）
- **「コマンド実行中」の欄を出すときだけ確保する。** 出たり消えたりするたびに後ろが跳ねる（上の理由）
- **OSNAP の吸着中の種別を別の場所（マーカー横だけ）に出してステータスバーは `OSNAP` 固定にする。**
  種別の確認がステータスバーでもできるのは既存の振る舞いなので残し、幅の固定で解決した

**追記（PR #39 の再レビュー）:**

- **幅のテストは日本語フォントを必須にした（fail-closed）。** CI にはフォントが無く、「日本語フォント未検出」が
  並びに入って 1280px でも描画時間が省かれ、テストが落ちていた。CI の apt に `fonts-noto-cjk` を足し
  （`/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc`。`jp_font::CANDIDATES` の先頭）、テストのハーネスは
  フォントが読めなければ理由つきで落ちる。**採らなかった案:** フォントが無いときはテストの期待を緩める。
  黙って検出力の落ちたテストが通り、800px の不具合のようにフォント無しでは再現しないものを見逃す
- **座標の欄は一度広がったら縮めない。** 12 文字（±999999.9999）を超える座標を指すと欄が広がり、その後は
  小さい座標に戻っても縮めない。境をまたぐたびに後ろの切り替え部品が約 78px 跳ねていたため（操作レビュー）。
  図面を入れ替えたら（新規・開く）最小の幅に戻す。保存では戻さない（下の Issue #41 の追記）
- **長いレイヤ名は 16 文字（省略記号を含む）で「…」に省き、全文はツールチップで見せる。** 長い名前で
  選択数などが押し出されないように

**追記（Issue #41）: 保存の成功は図面の入れ替えと分ける。** ファイル操作の結果 `FileOutcome` に
`Replaced`（NEW / OPEN）を足し、`Ok` は保存など図面がそのままの成功だけにした。選択の解除・スナップの解除・
座標の欄を最小の幅に戻すのは `Replaced` のときだけ。以前は保存の成功でも同じことをしていて、保存のたびに
選択が外れ、座標の欄が最小の幅に戻って切り替え部品が往復していた。

- **採らなかった案: `Ok` に「入れ替えたか」の真偽値を持たせる。** 未保存確認のモーダル（`show_confirm`）が
  `FileOutcome::Ok(msg)` を形で受けているので、形を変えると並行作業（PR #33）が触っているモーダルの行まで
  書き換えることになる。新しい腕を足せば、モーダルは「保存の結果は `Ok`、続く操作の結果はそのまま返す」ままで、
  NEW / OPEN の `Replaced` が素通りする
- あわせて、ステータスバーの情報表示（座標・レイヤ・選択・要素・倍率・描画時間など）のラベルを
  `selectable(false)` にした。文字を選ぶ必要は無く、乗せると I ビームになって切り替え部品（指のカーソル）と
  見分けにくかった

## ADR-0039: パネルが図面を変えた後に、実行中のツールと選択の前提を `Session` の 1 か所で確かめる

- **状態**: 確定
- **日付**: 2026-10-06
- **関連**: [Issue #37](https://github.com/yukimasui/ymcad/issues/37)、[ADR-0037](#adr-0037-リボンタブつきアイコンバーを足し押すことはコマンド名を打つのと同じ扱いにする)（パネルの開閉は中断しない）

### 背景

パネルの開閉（LAYER / COMPONENTS）と保存は実行中のコマンドを中断しない（ADR-0037）。そのため、
コマンドの途中でパネルから図面が変わる（レイヤの削除・ロック・非表示など）場面が増えた。
ツールが覚えている図形や選択が無効になったときの振る舞いを egui_kittest で実測した。

| 場面 | 修正前に起きたこと |
|---|---|
| FILLET で 1 本目を拾った後、そのレイヤを削除 | 消えた ID を `Command` に渡し「FILLET: エンティティが見つかりません」。ツールは続く |
| 同、ロック・非表示 | **ロック・非表示の線分を丸めた** |
| MOVE / ROTATE の目的点待ちで、選んだ図形のレイヤをロック・非表示 | **その図形を動かした・回した** |
| COPY の同じ場面 | **ロック・非表示のレイヤに複写を作った** |
| MOVE / COPY / ROTATE で、選んだ図形のレイヤを削除 | 案内なしにコマンドが終わった |
| TRIM / EXTEND の途中で対象のレイヤを削除・ロック・非表示 | 拾えないだけ（「図形の上をクリックしてください」）。図形は変わらない |
| 同、境界のレイヤをロック | ロックした図形も境界として効く。非表示・削除なら境界にならない |
| EDITCOMP の編集中に中身のレイヤを削除 | ENDCOMP が「中身がすべて消されています」で断り、編集は続く |
| 同、ロック・非表示・パラメータの宣言を変更 | ENDCOMP で書き戻せる |
| FILLET で 1 本目を拾った後に NEW（Ctrl+N） | **前の図面の ID を覚えたまま FILLET が続いた**（新しい図面で同じ番号の別の図形を指しうる） |

どの場面でもパニックはしなかった。

### 決定

**`Session::apply_external`（パネルが図面を変える唯一の入口）の後に、`Session::revalidate` で前提を確かめる。**
各ツールには散らさない。

- 選択から、削除・ロック・非表示になった図形を外す（`Selection::retain_editable`。選ぶときと同じ
  `is_entity_editable` を使う）
- ツールは、次の手のために覚えている図形を `Tool::held_entities` で宣言する（既定は空。今は FILLET / CHAMFER の
  1 本目と、PSET が指したインスタンス）。どれかが編集できなくなっていたら**ツールを中断**し、
  「{コマンド名}: 対象の図形が削除・ロック・非表示になったため中断しました」を出す
- 選択を対象にするツール（`wants_selection`。MOVE / COPY / ROTATE など）は、対象が**すべて**外れたら中断する。
  **一部だけ**外れたら、残りで続けて「{コマンド名}: 削除・ロック・非表示になった N 個を対象から外しました」を出す
- 選択待ちの段階（ERASE / MOVE の「オブジェクトを選択」）で選択から外れたら、**中断はせず**
  「{コマンド名}: 削除・ロック・非表示になった N 個を選択から外しました」を出す（選び直せる。全部外れても同じ。
  Issue #48）。文言に「選び直すと戻せます」は足さない（ロックを外しただけでは選択に戻らず誤解を招く）
- 何も実行していないときに選択から外れても、案内は出さない（選ぶときと同じ規則で外れるだけ）
- UNDO / REDO は `apply_external` を通らないが、レイヤのロック・非表示もコマンドなので、戻った結果で
  ロック・非表示になる図形がありうる。実行後に同じ `retain_editable` で選択を確かめ直す（何も実行していない
  状態なので案内は出さない）。実行中のツールについては、リボンの UNDO は先にツールを中断し、キーボードで
  打った `U` はツールのオプションになるので、扱いは要らない

**図面を入れ替えた（NEW / OPEN）ときは、実行中のツール・選択・コンポーネントの編集を捨てる**
（`Session::document_replaced`）。ID は図面ごとに振り直されるので、前の図面の ID を残すと
新しい図面の別の図形を指しうる。

### 採らなかった案

- **各ツールの `step` で、受け取るたびに ID とレイヤを確かめる。** ツールの数だけ同じ確認が要り、
  足し忘れたツールで同じことが起きる（ADR-0036 の参加制と同じく、ツールは宣言だけをして `Session` が判断する）
- **`Command` 側（`cad-core`）でロックされたレイヤの図形の変更を断る。** 防御としては強いが、
  エンティティを変えるすべてのコマンドの振る舞いが変わる（コンポーネントの書き戻しなど、ロックされた
  レイヤの図形を扱う正当な経路もある）。`cad-core` の方針の変更なので、必要になったらユーザーに確認する
- **一部が外れたときも中断する。** 残りの図形でそのまま続けたい場面の方が多い。外した数は案内する
- **中断せずに、ツールに「覚えている図形を忘れろ」と通知する。** FILLET なら 1 本目からやり直すだけだが、
  ツールごとに戻り先を決めることになり、散らばる。中断は `Esc` と同じで分かりやすい

### 拾わないこと（テストで固定）

- TRIM / EXTEND は図形を覚えずにクリックのたびに拾い直すので、追加の扱いは要らない
- コンポーネントの編集（EDITCOMP）は「印を持たずに追う」（ADR-0033）ので、中身が消えても ENDCOMP が分かる
  案内で断る。ロック・非表示でも書き戻せる
- 定義を消す操作（`DeleteDefinition`）はパネルにも UI にも無い。INSERT / BIND / PARAM が覚えている
  `DefinitionId` は、PURGE などに UI を付けるときに同じ仕組み（`held_definitions` のような宣言）で確かめる

## ADR-0040: 既存の図形の形は `ReplaceGeometries` で丸ごと置き換え、同じ種類どうしに限る

- **状態**: 確定
- **日付**: 2026-10-07（2026-10-08 改訂: [Issue #55](https://github.com/yukimasui/ymcad/issues/55) で 1 周の円弧を受け付け、ポリラインの頂点数の変更を拒むようにした）
- **関連**: [Issue #30](https://github.com/yukimasui/ymcad/issues/30)（グリップ編集）、[Issue #31](https://github.com/yukimasui/ymcad/issues/31)（プロパティパネル）、[Issue #55](https://github.com/yukimasui/ymcad/issues/55)、[ADR-0029](#adr-0029-コンポーネントの定義は実エンティティ--疎な式の束縛にする)、[ADR-0033](#adr-0033-インプレース編集は中身を図面へ出して印を付けずに追う)

### 背景

グリップ編集（#30）とプロパティパネル（#31）は、どちらも「選んだ図形の形を、アプリ側で
計算した新しい形に変える」操作で、1 回の操作 = Undo 1 回にしたい。既存のコマンドは
MOVE / STRETCH など**変形の種類ごと**にあり、「線分の終点をこの点へ」「円の半径を 7 に」を
表せるものが無い。エンティティを変えられるのは `Command` だけ（設計原則 4）なので、
`cad-core` にこの 2 つが共用する汎用のコマンドを足す（ユーザー承認済み。図形の種類は増やさない）。

### 決定 1: `(EntityId, Geometry)` の列を受け取り、形を丸ごと差し替える

`command::ReplaceGeometries::new(name, Vec<(EntityId, Geometry)>)`（1 つなら `::one`）。
`execute` は `EditCtx::entity_mut` で `Entity::geom` だけを `mem::replace` し、元の形を退避する。
`undo` は退避した形を**そのまま書き戻す**（逆変換を計算しない。MOVE / STRETCH と同じく
浮動小数点の往復誤差を持ち込まないため）。

- **ID は変えない。** 削除 + 追加にすると選択や Undo スタックに残る他のコマンドの参照が切れる
  （ADR-0004 / ADR-0022 と同じ理由）
- **形以外（レイヤ・色・グループ）は触らない。** レイヤは `MoveEntitiesToLayer` の経路がある
- `EditCtx` には何も足していない。既存の `entity_mut` で足りる（封印はそのまま）

**採らなかった案:**

- **フィールド単位の差分コマンド（「線分の終点 x を 5 に」）。** 種類 × フィールドの組み合わせぶん
  型が要り、グリップ（点を動かすと複数のフィールドが同時に変わる。円弧の端点なら角度 2 つと半径）と
  パネル（1 つの値）で別の表現が要る。新しい形はアプリ側で計算できるので、丸ごと渡す方が 1 本で済む
- **種類ごとの専用コマンド（`SetLineEndpoints`、`SetCircleRadius` …）。** 同じ「退避して差し替える」
  処理が種類の数だけ重複し、検証の漏れが種類ごとに出る
- **`Geometry` 以外（レイヤ・色・グループ）も一緒に変える万能コマンド。** グループの所属は
  `CreateGroup` / `Ungroup` が `GroupTable` と合わせて保っている（ADR-0022）ので、ここから
  書き換えると表と食い違う。レイヤは既に専用コマンドがあり、#31 で「複数選択時にレイヤだけ変える」
  のもそちらで足りる。形と属性を 1 回の Undo にまとめたければ `MacroCommand` で組める
- **`Document` に「形を差し替える」メソッドを生やす。** 設計原則 4 に反する

### 決定 2: 同じ種類どうしに限る（線分 → 円などは `NotEditable`）

`std::mem::discriminant` で元と新しい形の種類を比べ、違えば拒む。

- #30・#31 のどちらも種類を変える操作を持たない
- インプレース編集中（ADR-0033）の図形には束縛が付いていて、束縛は種類ごとのスロット
  （`LineAx`、`CircleR` …）を指す。種類が変わると `ExitDefinitionEdit` で `Binding::fits` に
  落ちて**束縛が黙って消える**。種類を変える操作が要るなら、そのとき削除 + 追加として明示的に扱う
- 許す方向へは後から緩められるが、許したものを禁止に戻すと呼び出し側が壊れる

**ポリラインは頂点の数も同じであること（#55 で追加）。** 種類が同じでも、頂点の数が変わる
置き換えは `NotEditable` で拒む。束縛の `PolylineVx(i)` / `PolylineVy(i)` は頂点を**添字**で
指すので、頂点を減らすと `ExitDefinitionEdit` で `Binding::fits` に落ちて束縛が黙って消え
（種類の変更と同じ問題）、途中に頂点を足すと束縛が**別の頂点を指す**ようになる（消えるより
気づきにくい）。この決定は呼び出し側に制約を課す: #30 のグリップは頂点を動かすだけにし、
#31 のパネルの「頂点数」は表示の項目にとどめる（数を変える入力にはしない。2026-10-08 に
#31 の計画でユーザーが確認）。
頂点の追加・削除が要るなら、そのとき束縛の付け替えと合わせて別の操作として設計する。

- **開閉（`closed`）の切り替えは許す。** 頂点の添字は変わらず、束縛の指す先も変わらない。
  閉じたときの頂点 3 以上は `Geometry::validate` が見る。#31 のパネルは「閉じ」を項目に
  挙げていて、この経路で切り替えられる必要がある
- **採らなかった案: 束縛が付いているときだけ拒む。** このコマンドは今がインプレース編集中か、
  どの図形がどの束縛に対応するかを知らない（対応は編集を抜けるときに `cad-app` が `origins` で
  渡す）。知らせる経路を足すより、種類の検査と同じく常に拒む方が単純で、#30・#31 も困らない
- **採らなかった案: 呼び出し側の責任として ADR に書くだけ。** 決定 2 が種類の変更を拒む理由と
  同じ問題を、片方だけコマンドで止めてもう片方を呼び出し側に任せると約束が一貫しない

### 決定 3: インスタンスは配置（基点・回転・倍率・反転）だけ

インスタンスどうしの置き換えでは、**参照する定義とパラメータの上書きが元と同じ**であることを
要求し、違えば `NotEditable`。変えてよいのは `Placement` だけ。

- 定義の差し替えは「別の部品に置き換える」で、意味が違う操作。循環の検査（`DefineComponent` /
  `InsertInstance` の約束）もこの経路では行わない
- 上書きは `SetInstanceOverride` が**型と範囲を検証**してから入れている。ここで上書きを
  受け付けると、検証を通らない値が図面に入る抜け道になる
- 配置の変更は MOVE / ROTATE / SCALE / MIRROR が既にインスタンスへ行っていることと同じなので安全

**採らなかった案: インスタンスを対象外にする。** グリップで挿入点を動かす・パネルで回転や倍率を
直すのは #30・#31 の自然な用途で、対象外にするとアプリ側に別の経路が要る。

### 決定 4: 検証は書き換える前に全件。不正は `Geometry::validate` で止める

`execute` は次の順に**全件**確かめてから 1 件目を書き換える。1 件でも通らなければ何も変えずに
`Err`（`Document::apply` は履歴に積まず、版番号も進めない）。

| 検査 | エラー |
|---|---|
| 列が空 | `NotEditable` |
| 同じ ID が 2 回 | `NotEditable` |
| ID が存在しない（削除済み・世代違い） | `EntityNotFound` |
| 種類が変わる / ポリラインの頂点の数が変わる / インスタンスの定義・上書きが変わる | `NotEditable` |
| 形が成立しない（`Geometry::validate`） | `DegenerateGeometry` |

`Geometry::validate` は `entity/kind.rs` に置いた（判定を図形の側に集め、他の経路からも使えるように）。
非有限の座標・角度、半径 0 以下（`is_zero_len` も含めトレランスで判定）、長さ 0 の線分
（`Line::is_degenerate`）、単位ベクトルでない作図線の方向、頂点不足のポリライン（開いて 2 未満・閉じて 3 未満。PLINE の
「閉じる」と同じ約束）と全頂点が同一点のポリライン（`Polyline::is_degenerate`）、
`Placement::new` に通らない配置を拒む。判定はすべて既存の `is_degenerate` と
`geom::tolerance` を通し、数値を直書きしない。

**開始角と終了角が一致する円弧は 1 周の円弧として受け付ける（#55 で改訂）。** 当初は
「掃引 0 と 1 周の区別がつかない」として拒んでいたが、既存の `Arc::sweep` は一致を「1 周」
（`2π`）と約束していて、描画・距離・範囲もその約束で動いている。掃引 0 の円弧という解釈は
図面のどこにも無いので、区別がつかないという根拠は成り立たなかった。拒んだままだと、DXF から
読んだ 0°→360° の円弧（開始角 0・終了角 `2π`）は中心を動かすだけ・半径を変えるだけでも
置き換えられない。角度が非有限のときは引き続き `DegenerateGeometry`。
その帰結として、#30 のグリップで円弧の終点を始点に重ねたり、#31 のパネルで開始角を終了角と
同じ値にしたりすると、エラーにならず 1 周の円弧になる。利用者の意図とずれやすいので、避けたい
ときは呼び出し側で止める（#31 のパネルは、元が 1 周でなければ「掃引が 0° になります」で拒む）。

**採らなかった案: 不正な形を黙って直す（作図線の方向を正規化する、負の半径を絶対値にする等）。**
渡した値と入った値が食い違い、パネルの表示と図形がずれる。拒んで呼び出し側に理由を出させる方が
原因を追える（設計原則 6 の「`NaN` は作らせずエラーで止める」と同じ考え）。

### 決定 5: ロックされたレイヤは呼び出し側が除く

`MoveEntities` / `StretchEntities` など既存の変形系コマンドはレイヤのロックを見ていない
（選択の段階で `cad-app` が除いている）。このコマンドも同じにし、ドキュメントコメントに明記した。
ここだけでロックを見ると、同じ図形が MOVE では動くのにグリップでは動かない、のような
食い違いの原因になる。

### 補足: 形が変わらない置き換え

元と同じ形を渡しても `Ok` になり、履歴に 1 件積まれる。値を確定しても形が変わらないときに
Undo を増やしたくなければ、呼び出し側で比べて適用しない（コマンドが「変わっていない」を
`Err` にすると、パネルが「確定に失敗した」と誤って表示する）。

## ADR-0042: ホバーの強調とクリックは `Session::click_target` の 1 か所で「何が拾われるか」を決める

- **状態**: 確定（見た目はユーザーの目視確認待ち）
- **日付**: 2026-10-08
- **関連**: [Issue #34](https://github.com/yukimasui/ymcad/issues/34)（段階 1）、[Issue #51](https://github.com/yukimasui/ymcad/issues/51)、[Issue #61](https://github.com/yukimasui/ymcad/issues/61)、[ADR-0011](#adr-0011-空間インデックスは-document-ではなく-cad-app-側の派生キャッシュに置く)、[ADR-0022](#adr-0022-グループの所属はエンティティ側だけが持つ)、[ADR-0024](#adr-0024-コマンド実行中の図形ピックは-session-が担いツールには拾い半径を渡さない)、[ADR-0038](#adr-0038-直交モードと極トラッキングは独立したスイッチにしカーソル点を拘束する-1-本の経路に載せる)

（ADR-0041 は Issue #31 用に予約。）

### 背景

クリックするまで、どの図形が拾われるか分からなかった。重なった図形・グループ・ロックされた一員が
絡むと、拾われるものを予想しにくい。AutoCAD の「選択プレビュー」にあたる強調を足す。
強調が**クリックの結果と食い違うと、無いより悪い**（強調を信じてクリックした結果が違う）。

### 決定 1: クリックとホバーは同じ関数を通す

`Session::click_target(model, pick_tolerance, doc, picker) -> ClickTarget` を作り、
`Session::handle_click` は `click_target` の結果を実行するだけにした。ホバー（`hover::Hover`）も
同じ関数を呼び、`ClickTarget::highlighted()` を強調する。

| 段階（`PickStage`） | `ClickTarget` | 強調 |
|---|---|---|
| 待機中・選択待ち（`Select`） | `Select(グループを展開した一員)` / `Nothing` | 展開した一員すべて |
| 図形を指す段階（`Entity`、`Tool::wants_entity`） | `Entity { id, at }` / 拾えなければ `Point` | その 1 つ（グループに広げない） |
| 点・値の入力待ち（`Point`） | `Point` | なし |

グループの展開（ADR-0022）と、ロック・非表示の一員の除外（#51 案 A）は `expand_to_group` にあり、
`click_target` の中で呼ぶので、強調にも自動的に効く。拾う位置はクリックと同じ `cursor_model`
（スナップ・直交・極・寸法の固定を通した後の点）、拾い半径も同じ `PICK_RADIUS_PX`。
クリックもホバーと同じ `hover::PickIndex` で拾う。

**採らなかった案: ホバー用に別の拾い方を書く。** グループの扱いや同じ距離の決め方の片方だけを
直し忘れると、強調とクリックがずれる。ずれは見ても気づきにくい。

### 決定 2: 拾うのは候補の採点（`pick_among`）、候補は空間インデックスで絞る

`selection::pick_at`（全走査）を、候補の列を採点する `pick_among(doc, candidates, pos, tol)` に分けた。
**同じ距離のときは候補の並び順ではなく `EntityId` の大きい方**（後から作った = 手前に描かれる方）。
空間インデックスが返す順は木の形で変わるので、並び順に頼ると全走査と結果が変わる。
`EntityId` の大小は全走査の順（スロット順）と常に同じなので、今までの「走査で後に来た方が勝つ」と一致する
（ふだんはスロット順 = 作成順だが、`clear_history` で末尾の空きを詰めた後は作成順とは限らない）。

ピック用の `SpatialIndex` は `hover.rs` に `Document::revision()` をキーに持つ（ADR-0011）。
`pos ± 2 × 拾い半径` の正方形で候補を引く（距離の丸めで境界ぎりぎりの図形を落とさないための余裕。
候補が増えるだけで、結果は `pick_among` が決める）。索引で絞った結果が全走査と一致することは、
線分・円・円弧・ポリライン・作図線・インスタンス・ロック・非表示・同じ距離の重なりを混ぜた
乱数テストで確かめている。

図面・位置・拾い半径・段階が前フレームと同じなら、前フレームの結果を使い回す。

**図面を入れ替えたら（NEW / OPEN、`FileOutcome::Replaced`）索引も結果も捨てる。** `revision` は
図面ごとの値で、別の図面どうしで一致しうる（読み込みはコマンドの適用回数で版が決まり、レイヤ数などの
構造だけで同じ値になる）。一致したまま前の図面の索引を引くと、新しい図面の図形を強調もクリックも
できなかった（PR #63 のレビューで発覚。クリックも索引を通るようにしたので、以前の全走査には無かった回帰）。

**採らなかった案: `SnapState` の索引を共有する。** スナップは点の入力待ちでしか更新しないので、
待機中のホバーが古い索引を引く。作り直しの時期を片方の都合で決めると取り違えが起きる。
1 万図形の構築は数ミリ秒なので、2 つ持っても困らない。

**性能。** 1 万図形で 1 回の計算は µs の桁（デバッグビルド）。作図線が 1 本あると索引の分割が止まり
ほぼ線形になる（#61）が、それでも 1 回 0.3ms 程度で 1 フレームの予算（16ms）に十分収まる。
ホバーの計算と描画は描画時間の計測区間（ステータスバーの「描画」）に入れた。

### 決定 3: 図形を指す段階では OSNAP を効かせない（ユーザー判断 1）

TRIM / EXTEND / FILLET / CHAMFER（と EDITCOMP・BIND・PSET・XLINE のオフセットの図形を指す段階）では
スナップを更新しない。交点の近くで TRIM すると交点へ吸い付き、交点では 2 本が同じ距離なので
**切断エッジの方が拾われ**、しかも交点ちょうどでは「どちら側を切るか」が決まらなかった。
これらのツールが欲しいのは図形と、そのどちら側かであって、点ではない。

直交・極トラッキングは、`Session::tracking_base` がこの段階で `None` を返す（ADR-0038 決定 4）ので
もともと効かない。図形を指す段階に参加する寸法入力のツールも無い。どちらも変えていない。
直交を入れていても交点の近くで TRIM が成功することはテストで固定した。

### 決定 4: 強調する場面・しない場面

- 強調する: 待機中、選択待ち、図形を指す段階。TRIM / EXTEND 中に線分以外へ乗せても強調する
  （クリックで拾われるのは事実なので。切れないことはクリック後の案内で分かる。ユーザー判断 2）
- 強調しない: 点・値の入力待ち（`click_target` が `Point` を返す）、矩形選択のドラッグ中
  （離すと矩形で選ばれるので、乗せた図形とは関係ない）、カーソルがキャンバスの外

### 決定 5: 見た目

`render::draw_hover` が、`draw_entities` の**前**に**半透明の紫の太い縁取り（7px、アルファ 0x90）を
線の下に敷く**。選択色（水色）・ラバーバンド（琥珀）・スナップ（黄緑）のどれとも違う色にし、
「選んである」と「乗せている」を見分けられるようにした。線の下に敷くので、線そのものの色
（選択中なら選択色、そうでなければレイヤ色）は変わらず、乗せたままでも「もう選んだか」が分かる。
線種によらず実線で縁取る（破線の隙間で強調が途切れると読みにくい）。

**採らなかった案: 線の上に重ねる（最初の実装）。** 半透明の紫が線の芯にかかり、選択済みの水色が
藤色に、白がピンクに変わった。アルファ 0x60 では背景とのコントラストも 1.5:1 程度で暗かった
（PR #63 の操作レビュー）。
インスタンスは `ResolvedInstances` の展開結果を描く。`draw_entities` のシグネチャは変えていない。
